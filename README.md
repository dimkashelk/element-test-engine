# Element Test Engine

Локальный движок проверки учебных проектов 1С:Предприятие.Элемент.
Основной движок написан на **1С:Элемент Скрипт (SBSL)**. Он выполняет проверки,
сравнивает результаты и считает баллы. Python используется для преобразований
архивов, YAML и индекса XBSL в JSON IR, подготовки временного скрипта,
управления Docker и оформления отчёта. Бизнес-логика студента выполняется в
Script executor, а не переводится в Python.

## Что работает

- `inspect`: каталог / ZIP / TAR / TAR.GZ → JSON-модель метаданных и индекс методов.
- `validate`: диагностика повторяющихся имён, некорректных типов, недоступных и
  отсутствующих ссылочных типов. Это базовый анализ, не замена компиляции платформой.
- `test` / `run`: элементы, поля, табличные части, элементы перечисления, свойства,
  модули, аннотации, параметры и результат метода. Ресурсы и измерения проверяются
  как поля с указанием `collection: Ресурсы` или `collection: Измерения`.
- Runtime PoC: запуск оригинального чистого метода `СформироватьФИО` из `Движок.tar`
  в Docker, сравнение ожидаемого и фактического результата **в SBSL**.
- JSON/HTML-отчёты, баллы, продолжение после ошибки отдельной проверки.

Исходные проекты открываются только на чтение. Архивы распаковываются во временный
каталог, который удаляется после запуска. Отчёт внутри исходного каталога запрещён.
Загрузчик отклоняет ссылки, выход за пределы каталога, повторяющиеся пути архива,
неоднозначные корни проекта, YAML с повторяющимися ключами и якорями.
Лимиты: 10 000 файлов, 128 MiB распакованного содержимого, 4 MiB на YAML.

## Запуск

Нужны Bash, Python 3.10+, PyYAML 6 и Java 11+ (проверено с Java 17).
Для runtime-тестов нужен Docker. Дистрибутив Script executor 10.0.2-1 уже лежит
локально в `script_u_10.0.2_1/`; он исключён из Git.

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
export ELEMENT_TEST_PYTHON="$PWD/.venv/bin/python"

bin/element-test inspect Движок.tar --output result/inspection.json
bin/element-test validate Движок.tar
bin/element-test test --project Движок.tar --assignment assignments/demo --output result/demo

docker pull eclipse-temurin:17-jre@sha256:34d6aaf0fa4ef553c470234ec23c32c7d5c0f370c2bd4b0bf8a16838052d85f0
bin/element-test test --project Движок.tar --assignment assignments/poc-fio --output result/poc-fio
```

Без установки пакета можно использовать системный Python с установленным PyYAML.
Обёртка `bin/script-runtime` исправляет запуск executor из пути с пробелами,
не изменяя предоставленный дистрибутив.

`run` — псевдоним `test` с теми же флагами. Коды CLI: `0` — успешно,
`1` — не прошли проверки, `2` — ошибка входных данных/окружения или неполная
проверка с `UNSUPPORTED`/`SKIPPED`. Возвращаемое число метода Скрипт executor
печатает в stdout; преобразование в реальный код CLI выполняет обёртка.

## Задания

Задание хранится отдельно от студенческой работы: `assignment.yaml` с `checks`,
дополнительные проверки можно положить в `structural/*.yaml` и `runtime/*.yaml`.
Пример структурной проверки:

```yaml
checks:
  - id: order_client
    type: field
    element: Заказ
    field: Клиент
    expectedType: Контрагенты.Ссылка?
    points: 2
  - id: order_sum
    type: field
    element: Заказ.Товары
    field: Сумма
    expectedType: Число
    scale: 2
    points: 1
```

Через `properties` проверяются любые явно заданные свойства YAML, включая
`СозданиеНаОсновании`, `Импорт`, `ЗначениеПоУмолчанию` и `Автонумерация`.
Имена можно квалифицировать: `Продажи::Заказ`. Поиск по краткому имени при
неоднозначности даёт диагностику. UUID и порядок реквизитов не влияют на результат.
Порядок членов union-type нормализуется; точность/длина задаётся отдельно от типа.

Статусы: `PASS`, `FAIL`, `ERROR`, `SKIPPED`, `UNSUPPORTED`, `TIMEOUT`.
`UNSUPPORTED` и `SKIPPED` исключаются из доступного `maxScore`, их баллы сохраняются
в `unavailablePoints`; отчёт помечается `incomplete`, если нет других ошибок.
Это препятствует автоматическому снижению оценки за ограничение среды.

## Изоляция и совместимость runtime

Каждый runtime-тест выполняется в отдельном контейнере: сеть отключена, root FS,
executor и сгенерированный SBSL подключаются только для чтения, рабочий `/tmp`
ограничен 64 MiB. Код работает от непривилегированного пользователя без capabilities,
с `no-new-privileges`, 1 CPU, 384 MiB RAM, 64 PID и лимитом CPU-времени 8 секунд.
Heap JVM ограничен 128 MiB. Timeout задания включает запуск контейнера; вывод
ограничен 1 MiB. Контейнер удаляется в `finally`, включая timeout и ошибку.
Студенческий архив и весь проект в контейнер не подключаются — только выделенный метод.

`config/runtimes.json` задаёт соответствие режима проекта и executor; сейчас
экспериментально подтверждена пара **проект 9.0 → executor 10.0.2-1 в режиме 9.0**
для метода ФИО. Это не доказывает совместимость всех platform API.
Для ненастроенного режима возвращается `UNSUPPORTED`.

Настройки окружения:

| Переменная | Назначение |
|---|---|
| `ELEMENT_SCRIPT_HOME` | Каталог executor, заменяет локальный путь |
| `ELEMENT_TEST_PYTHON` | Python для преобразований |
| `ELEMENT_TEST_RUNTIMES` | Путь к JSON-конфигурации runtime |
| `ELEMENT_TEST_DOCKER_IMAGE` | Явная замена Docker-образа из конфигурации |

## Проверка разработки

```bash
python3 -m unittest discover -s tests -v
ELEMENT_TEST_DOCKER_TESTS=1 python3 -m unittest discover -s tests -p 'test_docker.py' -v
```

Тесты проверяют загрузку архивов, безопасность путей, неизменность исходников,
грамматику типов, индекс сигнатур и настоящее SBSL-оценивание: ошибки продолжают
обработку, `UNSUPPORTED` не штрафует студента, неверный результат даёт `FAIL`.
Интеграционные тесты автоматически пропускаются без локального executor/архива.

## Ограничения первого этапа

PoC выделяет чистый метод со скалярными параметрами/результатом без вложенных блоков
и зависимостей от других модулей. Копирует тело метода без изменения бизнес-логики;
убирает только внешние аннотации платформы и добавляет технический entry point.
Индекс XBSL — лексический анализ сигнатур, не полный AST/компилятор.
Пространство имён определяется каталогами подсистем; разрешение импорта библиотек
и полная проверка доступности ещё не реализованы.

Генерация проектных типов, объектный контекст, табличные части в runtime,
моки регистров/запросов, dependency closure, persistent cache, массовые workers
и LMS пока не реализованы. План — [docs/roadmap.md](docs/roadmap.md).
