# Element Test Engine

Локальный движок проверки учебных проектов 1С:Предприятие.Элемент.
Основной движок написан на **1С:Элемент Скрипт (SBSL)**. Он выполняет проверки,
сравнивает результаты и считает баллы. Python используется для преобразований
архивов, YAML и индекса XBSL в JSON IR, подготовки временного скрипта,
управления Docker и оформления отчёта. Бизнес-логика студента выполняется в
Script executor, а не переводится в Python.

## Что работает

- `inspect`: каталог / ZIP / TAR / TAR.GZ / XDUMP → JSON-модель метаданных и индекс методов.
- `validate`: диагностика повторяющихся имён, некорректных типов, недоступных и
  отсутствующих ссылочных типов. Это базовый анализ, не замена компиляции платформой.
- `test` / `run`: элементы, поля, табличные части, элементы перечисления, свойства,
  модули, аннотации, параметры и результат метода. Ресурсы и измерения проверяются
  как поля с указанием `collection: Ресурсы` или `collection: Измерения`.
- `batch`: партия работ из JSON manifest с 1–4 отдельными процессами,
  независимыми пакетами, потоком событий и локальным кэшем структурных проверок.
- Runtime PoC: запуск оригинального чистого метода `СформироватьФИО` из `Dvizhok.xdump`
  в Docker, сравнение ожидаемого и фактического результата **в SBSL**.
- Эксперимент №2: оригинальный `ЗаказФормаОбъекта.РассчитатьИтоги` с циклом по
  `Массив<Заказ.Товары>`; типы строк и необходимых ссылок генерируются из YAML.
- Реальные `ФизическиеЛица.ПередЗаписью` и `Заказ.ПриСозданииНаОсновании`:
  локальные зависимости методов, тестовые параметры записи и загрузка fake-ссылок.
- Реальные `Номенклатура.ПослеЗаписи` и `Отгрузка.ПередЗаписью`: моки регистра,
  журнал вызовов, подставные строки запроса и проверка исключений.
- JSON/HTML-отчёты, баллы, продолжение после ошибки отдельной проверки.

## Запуск

### Извлечение проекта из xdump

Скрипт требует только Python 3.10+ и стандартную библиотеку:

```bash
python3 extract_xdump.py Dvizhok.xdump
python3 extract_xdump.py Dvizhok.xdump --output result/imported
```

По умолчанию результат — `result/xdump/Движок/` со структурой как в
`Движок.tar`: `Проект.yaml`, `Проект.xbsl` и папки подсистем. Также рядом с исходным
дампом создаётся архив с тем же именем и расширением `.tar`: например,
`Dvizhok.xdump → Dvizhok.tar`. Внутри архива сохраняется папка проекта `Движок/`.
Используется обычный tar, как в эталоне (без gzip). Существующий архив не
перезаписывается. Исходники берутся
из `application.zip → src/<поставщик>/<проект>/`; служебная `.asm` исключается.
Содержимое файлов, включая пустые, сохраняется без изменений; имена приводятся
к Unicode NFC. Данные приложения и пользователи не извлекаются. Уже существующая
папка проекта не перезаписывается. Если в дампе несколько проектов, каждый
извлекается в свою папку; совпадающие имена отклоняются.

### Проверка проекта

Все команды принимают `.xdump` напрямую, в том числе с приложением и библиотеками.
Загрузчик извлекает исходники из
`application.zip`, создаёт промежуточный tar во временном каталоге и передаёт его
обычной проверке. Временные файлы удаляются после запуска, исходный дамп и tar
рядом с ним не изменяются. Единственное приложение выбирается автоматически;
для явного выбора используйте `--project-name Имя` или
`--project-name Поставщик::Имя`. Объявленные библиотеки сверяются по поставщику,
имени, версии и виду проекта. Их исходники учитываются в `sourceHash`, а точная
идентичность видна в модели и пакете оценки. Критерий может выбрать подключённую
библиотеку через `library: {provider, name, version}`; структурные и runtime
проверки используют её собственную модель и исходники. В текущем наборе все
проекты имеют режим совместимости 9.0. Ошибка YAML в исходном `autocheck` на
строке 112 исправлена, составной архив проходит `inspect`.
Текущий корпус из четырёх дампов, оставшиеся предупреждения и следующие задачи описаны в
[отчёте от 30 сентября](docs/xdump-corpus-2026-09-30.md). История исправления
первых трёх — в [ранней оценке](docs/xdump-assessment-2026-09-29.md) и
[отчёте по runtime и библиотекам](docs/tasks/019-library-checks-and-runtime-verification.md).

Нужны Bash, Python 3.10+, PyYAML 6 и Java 11+ (проверено с Java 17).
Для runtime-тестов нужен Docker. Дистрибутив Script executor 10.0.2-1 уже лежит

### Массовый запуск

Manifest преподавателя хранится отдельно от работ. Пути `assignment` и `project`
разрешаются относительно файла manifest; каждая работа имеет уникальный
`studentId`. Пример:

```json
{
  "schemaVersion": "1.0",
  "assignment": "assignments/demo",
  "assignmentId": "demo",
  "submissions": [
    {"studentId": "student-001", "project": "incoming/001.tar"},
    {"studentId": "student-002", "project": "incoming/002.xdump", "projectName": "Поставщик::Приложение"}
  ]
}
```

```bash
bin/element-test batch --manifest batch.json --output result/batch --workers 2
bin/element-test batch --manifest batch.json --output result/batch-sql --workers 2 --integration
```

Выходной каталог должен быть пустым. `batch-result.json` содержит счётчики и
относительные ссылки на `submissions/000001/{result.json,grading.json,report.html}`;
`events.jsonl` можно читать во время работы. `inputError` для повреждённого
входа не создаёт `grading.json` и не останавливает остальные работы. Коды
возврата: 0 при всех `passed`, 1 при `failed`/`incomplete`/`inputError`, 2 при
ошибке manifest, 130 при прерывании. По умолчанию используется один worker;
интеграционный PostgreSQL запускается только с `--integration`.

Локальный кэш по умолчанию находится в `.element-test-cache` рядом с output;
путь можно задать через `ELEMENT_TEST_CACHE_DIR`. В кэш попадают только
завершённые структурные результаты с `PASS`/`FAIL`. Runtime-проверки, включая
SQL, каждый раз запускаются заново. Форматы:
[manifest](docs/batch-manifest-v1.schema.json),
[индекс](docs/batch-result-v1.schema.json),
[событие JSONL](docs/batch-events-v1.schema.json).

При промахе кэша worker передаёт уже открытый проект и результат анализа в
`run_test`, поэтому архив открывается и анализируется один раз. Замеры и
проверка совпадения с одиночным запуском — в
[отчёте по пункту 8](docs/tasks/016-batch-analysis-reuse.md).

Без установки пакета можно использовать системный Python с установленным PyYAML.
Обёртка `bin/script-runtime` исправляет запуск executor из пути с пробелами,
не изменяя предоставленный дистрибутив.

`run` — псевдоним `test` с теми же флагами. Коды CLI: `0` — успешно,
`1` — есть `FAIL`, `2` — ошибка входных данных/окружения или неполная
проверка с `ERROR`/`TIMEOUT`/`UNSUPPORTED`/`SKIPPED`. Возвращаемое число метода Скрипт executor
печатает в stdout; преобразование в реальный код CLI выполняет обёртка.

## Задания

Подробный контракт и примеры для преподавателя/ИИ: [руководство по тестам](docs/test-authoring-guide.md).
Готовый промпт генерации: [ai-test-generation-prompt.md](docs/ai-test-generation-prompt.md).

Задание хранится отдельно от студенческой работы: `assignment.yaml` с `checks`,
дополнительные проверки можно положить в `structural/*.yaml` и `runtime/*.yaml`.
Пример структурной проверки:

```yaml
checks:
  - id: order_client
    type: field
    element: Заказ
    field: Клиент
    expectedType: Контрагенты.Ссылка?
    points: 2
  - id: order_sum
    type: field
    element: Заказ.Товары
    field: Сумма
    expectedType: Число
    scale: 2
    points: 1
```

Через `properties` проверяются любые явно заданные свойства YAML, включая
`СозданиеНаОсновании`, `Импорт`, `ЗначениеПоУмолчанию` и `Автонумерация`.
Имена можно квалифицировать: `Продажи::Заказ`. Поиск по краткому имени при
неоднозначности даёт диагностику. UUID и порядок реквизитов не влияют на результат.
Порядок членов union-type нормализуется; точность/длина задаётся отдельно от типа.

Статусы: `PASS`, `FAIL`, `ERROR`, `SKIPPED`, `UNSUPPORTED`, `TIMEOUT`.
`ERROR`, `TIMEOUT`, `UNSUPPORTED` и `SKIPPED` исключаются из доступного `maxScore`,
их баллы сохраняются в `unavailablePoints`; отчёт помечается `incomplete`, если
нет `FAIL`.
Это препятствует автоматическому снижению оценки за ограничение среды.

## Изоляция и совместимость runtime

Каждый runtime-тест выполняется в отдельном контейнере: сеть отключена, root FS,
executor и сгенерированный SBSL подключаются только для чтения, рабочий `/tmp`
ограничен 64 MiB. Код работает от непривилегированного пользователя без capabilities,
с `no-new-privileges`, 1 CPU, 384 MiB RAM и 64 PID. Лимит CPU-времени равен
wall timeout, округлённому вверх до целых секунд (не более 30 секунд);
для SQL executor оба лимита — 30 секунд. Бюджет включает запуск JVM и компиляцию.
Heap JVM ограничен 128 MiB. Timeout задания включает запуск контейнера; вывод
ограничен 1 MiB. Контейнер удаляется в `finally`, включая timeout и ошибку.
В контейнер подключается только временный каталог с выделенным методом и
сгенерированными контрактами типов. Студенческий архив остаётся снаружи.

`config/runtimes.json` задаёт соответствие режима проекта и executor; сейчас
экспериментально подтверждена пара **проект 9.0 → executor 10.0.2-1 в режиме 9.0**
для метода ФИО. Это не доказывает совместимость всех platform API.
Для ненастроенного режима возвращается `UNSUPPORTED`.

Настройки окружения:

| Переменная | Назначение |
|---|---|
| `ELEMENT_SCRIPT_HOME` | Каталог executor, заменяет локальный путь |
| `ELEMENT_TEST_PYTHON` | Python для преобразований |
| `ELEMENT_TEST_RUNTIMES` | Путь к JSON-конфигурации runtime |
| `ELEMENT_TEST_DOCKER_IMAGE` | Явная замена Docker-образа из конфигурации |

## Проверка разработки

```bash
python3 -m unittest discover -s tests -v
ELEMENT_TEST_DOCKER_TESTS=1 python3 -m unittest discover -s tests -p 'test_docker.py' -v
```

Тесты проверяют загрузку архивов, безопасность путей, неизменность исходников,
грамматику типов, индекс сигнатур и настоящее SBSL-оценивание: ошибки продолжают
обработку, `UNSUPPORTED` не штрафует студента, неверный результат даёт `FAIL`.
Docker- и SQL-тесты запускаются только с соответствующими opt-in переменными;
без них они штатно пропускаются.

## Генерация проектных типов

Python-адаптер создаёт подключаемые SBSL-модули: например, `Заказ.sbsl` с
глобальной структурой `Товары`. Так сохраняется исходное имя `Заказ.Товары`.
Генерируются типы из сигнатур выбранного метода и вызываемых локальных методов,
зависимости их полей и явно заданные контракты fake-объектов.
Поддерживаются строки табличных частей документов/справочников, минимальные
`Объект`/`Данные` с реквизитами и массивами строк, системное поле `Объект.Ссылка`,
`Ссылка` с полем
`Идентификатор: Строка`, перечисления, а также массивы и типы результата `Соответствие`.
Эти структуры — тестовые контракты. Запись в базу отсутствует; отдельные системные методы доступны через явные моки; `ЗагрузитьОбъект()` доступен при явной настройке `mocks.objects`.

Аргумент строки задаётся объектом YAML; неизвестные поля и неверные скалярные
значения отклоняются. Пропущенные поля получают значения по умолчанию Скрипта
либо явно заданное `ЗначениеПоУмолчанию` YAML. Пример:

```yaml
checks:
  - id: totals
    type: runtime
    target: {module: ЗаказФормаОбъекта, method: РассчитатьИтоги}
    args:
      - - {Количество: 2, Цена: 100, Сумма: 200}
        - {Количество: 3, Цена: 50, Сумма: 150}
    expected: {Строк: 2, Товаров: 5, Сумма: 350}
```

Эксперимент №2 подтверждён на `Движок.tar`: 3/3 проверки (пустой массив,
несколько строк, дробные значения). Метод суммирует переданное поле `Сумма`;
пересчёт `Количество × Цена` не добавляется адаптером.

## Перечисления и объектный контекст

Перечисления генерируются из `Элементы` YAML. Вход задаётся именем элемента
(`Новый`) или полным именем (`СтатусЗаказа.Новый`); неизвестные значения отклоняются.
Поддержаны nullable, массивы перечислений, `ПоУмолчанию` у элемента и
`ЗначениеПоУмолчанию` у поля. Полные контракты `Заказ.Объект` и `Заказ.Данные`
из `Движок.tar` проверены в executor, включая `СтатусЗаказа` и все реквизиты.

Для вызова метода модуля `Заказ.Объект` передайте `context` с начальными полями.
Адаптер помещает оригинальный метод внутрь структуры `Объект`; разрешение `этот`,
неявных полей, параметров и локальных переменных выполняет компилятор Скрипта.
Тело метода, включая строковую интерполяцию, сохраняется. Чистые методы объектных
модулей по-прежнему можно вызывать без `context`.

```yaml
checks:
  - id: close_order
    type: runtime
    target: {module: Заказ.Объект, method: Закрыть}
    context: {Номер: " 001 "}
    args: []
    expected: {Ссылка: {Идентификатор: ""}, Номер: "001!", Статус: Закрыт, Товары: [], Итог: 0}
```

Пример соответствует доверенному fixture в `tests/test_object_context.py`,
а не обработчику из исходного архива. Для метода без результата `actual` содержит
состояние объекта после вызова; для метода с результатом —
`{return: результат, context: состояние}`. `expected` использует ту же структуру.
Сравнение и баллы по-прежнему вычисляет SBSL-движок. Один тест создаёт один объект;
состояние между тестами не сохраняется.

SBSL-модули требуют квалифицированного имени типа перечисления. Адаптер использует
в сгенерированных полях и сигнатуре `СтатусЗаказа.Значение`, а глобальные константы
сохраняют обращения `СтатусЗаказа.Новый` в исходном теле. Синтаксис перечислений и
областей видимости сверялся с документацией 1С:
[перечисления](https://1cmycloud.com/console/help/lang/docs/topics/enumeration-type/),
[модульная разработка](https://1cmycloud.com/console/help/executor/6.0/docs/topics/modular-programming-in-1c-executor/).

## Зависимые методы и fake-ссылки

Адаптер автоматически подключает транзитивно вызываемые методы того же модуля:
вызовы по имени и через `этот`, в том числе внутри `${...}`. Повторные и рекурсивные
вызовы включают метод один раз. Комментарии, строковый текст и вызовы через другой
объект не подключают одноимённые методы. Это лексический анализ, без разрешения
динамических вызовов, импортированных модулей и полного анализа затенения имён.
Тела всех подключённых методов сохраняются; адаптируются объявления типов и разрешённые токены типов конструкторов `новый` (см. эксперимент №8).

`<Объект>.ПараметрыЗаписи` генерируется как пустая структура, аргумент — `{}`.
Она позволяет вызвать обработчик, не использующий свойства параметров. Флаги,
отказ записи и другие платформенные свойства этого типа пока не моделируются;
неизвестные поля во входном аргументе отклоняются.

`observe` ограничивает проверяемое состояние заданными реквизитами или табличными
частями. Без него возвращается полный контекст, как прежде. Для метода с результатом
проекция находится в `actual.context`, результат — в `actual.return`.

```yaml
checks:
  - id: before_write
    type: runtime
    target: {module: ФизическиеЛица.Объект, method: ПередЗаписью}
    context: {Фамилия: " Иванов ", Имя: Иван, Телефон: " 123 ", Почта: " a@b.ru "}
    args: [{}, {}]
    observe: [ФИО, Телефон, Почта]
    expected: {ФИО: Иванов Иван, Телефон: "123", Почта: a@b.ru}
  - id: from_deal
    type: runtime
    target: {module: Заказ.Объект, method: ПриСозданииНаОсновании}
    context: {}
    args: [{Идентификатор: deal-1}]
    mocks:
      objects:
        Сделка.Ссылка:
          deal-1: {Клиент: {Идентификатор: client-1}}
    observe: [Клиент, Сделка]
    expected: {Клиент: {Идентификатор: client-1}, Сделка: {Идентификатор: deal-1}}
```

Fake-ссылка хранит только строковый `Идентификатор`. Её `ЗагрузитьОбъект()`
возвращает новый типизированный снимок из `mocks.objects`; повторная загрузка
не сохраняет изменения предыдущего снимка. Неизвестный идентификатор вызывает
ошибку выполнения (`ERROR`), без подстановки пустого объекта. Набор fake-объектов
изолирован в пределах одной проверки. Значения проходят ту же проверку полей,
типов и экранирование строк, что и обычные аргументы.

В сигнатурах поддержаны квалифицированные проектные типы: `CRM::Сделка.Ссылка`
и `Поставщик::Проект::CRM::Сделка.Ссылка`. Поставщик и проект должны совпадать
с `Проект.yaml`; объект разрешается по точному namespace. Для SBSL имя сокращается
до `Сделка.Ссылка`; конфликт кратких имён отклоняется. Это не разрешение внешних библиотек.

Эксперимент №5: `assignments/poc-handlers` — **5/5 PASS** в Docker на исходном
`Движок.tar`: нормализация ФИО/контактов, пустые значения, две разные сделки и
сделка без клиента. Интеграционные тесты дополнительно проверяют неверное ожидание
(`FAIL`), отсутствующую ссылку (`ERROR`) и безопасную передачу `${...}` в fake-ID.

## Регистры, запросы и ожидаемые исключения

`assignments/poc-platform` запускает оригинальные обработчики из `Движок.tar`:
запись цены, достаточный остаток, точное равенство, недостаточный остаток
и отсутствующий товар. Все пять сценариев сравниваются SBSL-движком.

`Объект.Ссылка` — системное поле типа `<ИмяОбъекта>.Ссылка`. По умолчанию
его тестовый идентификатор пуст; задайте его в `context`, когда обработчик
записывает ссылку в регистр. В `Данные` это поле автоматически не добавляется.
У справочника `Наименование` без явно заданного типа YAML получает тип `Строка`.

```yaml
mocks:
  registers: [РегистрЦеныНоменклатуры]
captureCalls: true
observeCallArguments: [Номенклатура, Цена, Замещать]
```

Для указанных регистров сведений из YAML генерируются `НаборЗаписей`,
`Фильтр.Установить`, `ДобавитьЗапись` и `Записать`. Набор сохраняет добавленные
типизированные строки; методы передают снимки аргументов в журнал stdout.
`Записать` по умолчанию получает `Замещать = Истина`. Это наблюдаемые вызовы,
без хранения данных, замещения и запуска обработчиков самого регистра.
Поддержана периодичность `Момент` и непериодические регистры сведений.
Регистры накопления `Остатки` поддержаны для формирования движений (см. ниже);
остальные периоды регистров сведений пока не поддержаны.

При `captureCalls: true` результат метода без возвращаемого значения имеет вид
`{context: наблюдаемое состояние, calls: [{owner, method, args}, ...]}`.
Порядок вызовов значим. `observeCallArguments` необязателен: он ограничивает
аргументы в сравнении, например исключает непредсказуемый `Период` от
`Момент.Сейчас()`. Без него сравниваются все аргументы. События сериализуются
в SBSL, Python разбирает журнал и собирает JSON, SBSL сравнивает его с `expected`.
Для метода с результатом `context` этой оболочки содержит прежнюю пару
`{return, context}`. Каждый контейнер имеет собственный журнал.

`mocks.queries` — список контрактов с `text`, `fields`, `rows` и одним из двух
полей для параметров:

- `text`: точное содержимое `Запрос{...}`, с учётом строковых литералов;
  пробельное оформление и комментарии не влияют на сопоставление.
- `fields`: отображение имени поля строки результата на тип.
- `rows`: типизированные подставные строки; пустой список означает отсутствие результатов.
- `parameterType`: тип единственного параметра `%{...}` (прежний формат).
- `parameterTypes`: список типов для `%{...}` и `%Имя` в порядке появления;
  `[]` для запроса без параметров. Число типов должно совпадать с числом параметров.

Литерал запроса заменяется вызовом тестовой фабрики; выражение `%{...}` или `%Имя`
выполняется исходным Скриптом и сохраняется в вызове `queryN.Создать`.
`Выполнить` возвращает новый типизированный массив и также фиксирует вызов.
Последующий `ВСоответствие` — настоящий метод коллекции Скрипта.
Каждому литералу нужен ровно один совпадающий контракт; неподставленный,
неоднозначный или неиспользованный контракт даёт `UNSUPPORTED`.
Вложенные фигурные скобки в выражениях `%{...}` не поддержаны. Для
`parameterTypes` событие `Создать` содержит `Параметр1`, `Параметр2`, ...;
для `parameterType` имя `Параметр` сохранено.
Запрос без параметров задаётся через `parameterTypes: []` и фиксирует
`Создать` с пустыми аргументами. Пример на исходном `ДемоСРМ` —
[задание стадий сделки](assignments/demo-srm-stages/assignment.yaml).
SQL/XBQL не выполняется: правильность выборки, группировки и виртуальных таблиц
этими тестами не проверяется.

`captureException: true` для объектного обработчика без результата возвращает
`{result: обычный результат проверки, exception: null | {type, message}}`.
Тип записывается полным именем runtime (например, `Std::IllegalStateException`),
сообщение — свойством `Описание`. Так проверяется ожидаемый отказ записи;
неожиданный тип исключения или отсутствие отказа дают `FAIL` при сравнении.
Без этого флага исключения по-прежнему приводят к `ERROR`.

Обработчик номенклатуры помещается в отдельный модуль `ТестКонтекст`, чтобы
избежать цикла импорта «объект → регистр → ссылка объекта». Его поля,
сигнатура и исходное тело сохраняются. Имена `ТестКонтекст` и `ТестПлатформа`
зарезервированы адаптером.

PostgreSQL может быть отдельным интеграционным окружением, но прямое SQL-соединение
не предоставляет объектный API Элемента: наборы регистров, фильтры, виртуальные
таблицы и обработчики записи. Для текущих проверок подставные зависимости
позволяют задавать состояние склада и проверять вызовы без базы.
Наследование может помочь реализовать тестовую зависимость при наличии точки
подстановки; само по себе оно не перехватывает `новый КонкретныйТип()` внутри
обработчика и не задаёт тестовые результаты запросов.

## Движения регистра накопления

Эксперимент №7: `assignments/poc-movements` запускает оригинальный
`Отгрузка.ПослеЗаписи` из архива. Пустая табличная часть, одна строка,
несколько строк и дробное количество — **4/4 PASS** в Docker.
Проверяются порядок фильтра/движений/записи, ссылка отгрузки у фильтра,
период, расход, номенклатура, склад и количество каждого движения.
Пустой набор также вызывает запись. Тело обработчика копируется без изменений;
сравнение и баллы остаются в `src/ДвижокТестирования.sbsl`.

```yaml
runtimeDateTime: Дата
context:
  Ссылка: {Идентификатор: shipment-1}
  Товары: []
# Поле Дата не указывается в context — его заполняет runtime.
expected:
  context:
    Дата: __runtimeDateTime__
```

По уточнению пользователя дата получается **внутри Docker** вызовом
`ДатаВремя.Сейчас(ЧасовойПояс{UTC})` непосредственно перед обработчиком.
Она сохраняется один раз; независимый снимок `execution.runtimeDateTime`
передаётся SBSL, который заменяет точные строковые маркеры
`__runtimeDateTime__` в `expected`. В отчёте показаны реальные даты.
Значение берётся до вызова обработчика, поэтому его изменения даты или неверный
период не меняют ожидание. Это заменяет первоначальное требование
фиксированной даты. Отдельный вход `ДатаВремя` всё ещё
можно задать строкой `YYYY-MM-DDTHH:MM:SS` (валидируется календарь, часовой пояс
и код в строке не принимаются).

Union-типы генерируются со всеми вариантами. Для неоднозначного входа,
например `Отгрузка.Ссылка|ПоступлениеТоваров.Ссылка|?`, требуется:

```yaml
type: Отгрузка.Ссылка
value: {Идентификатор: shipment-1}
```

`null` допустим только для nullable-типа. Неправильный вариант, неизвестное
поле или несовместимое значение отклоняются до запуска студенческого кода.
Без тега принимается только значение, подходящее ровно одному варианту.
В данном обработчике ссылку отгрузки передаёт сам Скрипт; тег нужен для
внешних входов, а не для исходного тела метода.

Контракт сверён с официальным [API набора регистра накопления](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/DeveloperName/ProjectName/SubsystemName/AccumulationRegisterName.RecordSet_ru/)
(сигнатура добавления для версии 9.0 и выше): `Период: ДатаВремя`,
`ВидЗаписи: ВидЗаписиРегистраНакопления`, затем измерения/ресурсы/реквизиты
с умолчаниями из YAML либо умолчаниями типа. Поля `Период` и `ВидЗаписи`
обязательны у `ДобавитьЗапись`; остальные параметры имеют умолчания.
Поддержанная перегрузка записи — `Записать(Замещать: Булево = Истина)`;
в журнале оригинального вызова без аргументов фиксируется `Замещать: true`.
Этот параметр подтверждён API регистра накопления, а не перенесён по аналогии.
Перегрузка с `ПараметрыЗаписи` пока не реализована.
Системное перечисление адаптировано SBSL-модулем с `Приход`/`Расход`,
с сохранением имён констант в исходном методе и сериализацией имени в JSON.

Docker-тест дополнительно проверяет семь неверных ожиданий: регистратор,
склад, количество, вид движения, номенклатура, период и порядок. Все дают
`FAIL` в SBSL. Неподдержанный контракт даёт `UNSUPPORTED`, следующая проверка
даёт `PASS`. JSON/HTML: `result/poc-movements` и
`result/poc-movements-negative` (отрицательный отчёт ожидаемо имеет статус
`failed`; тест проверяет именно эти исходы).

Мок наблюдает формирование записей и вызов записи. Хранение движений,
повторная запись, очистка по регистратору, пересчёт остатков, транзакции,
активность и полная семантика инициализации фильтра не реализованы.
Регистры `Обороты` отклоняются с `UNSUPPORTED`. Исходный архив не меняется;
студенческая бизнес-логика исполняется только в изолированном Docker.

## Поступление на основании отгрузки

Эксперимент №8: `assignments/poc-receipt` выполняет оригинальный
`ПоступлениеТоваров.ПриСозданииНаОсновании` из `Движок.tar` в Docker.
Пять сценариев: пустая ТЧ, одна строка, несколько товаров с сохранением порядка,
дробные количество/цена/сумма и дописывание в заполненную ТЧ.
Начальный склад отличается от склада отгрузки. `observe: [Склад, Товары]`
проверяет замену склада и все четыре поля каждой строки. Ожидаемые суммы
намеренно отличаются от количества × цены: обработчик переносит готовую сумму.
Две fake-ссылки содержат разные данные; отдельные проверки после ошибок
подтверждают изоляцию состояния и продолжение выполнения.

Обнаружение зависимостей теперь включает конструкторы в телах достижимых
методов того же модуля: `новый Документ.ТабличнаяЧасть(...)`,
`новый Подсистема::Документ.ТабличнаяЧасть(...)`,
`новый Поставщик::Проект::Подсистема::Документ.ТабличнаяЧасть(...)`,
а также поддержанные `Массив<...>` и `Соответствие<..., ...>`.
Строковые литералы и комментарии игнорируются; код внутри `${...}` анализируется.
Контракт типа подключается и в импорт модуля контекста, даже если тип отсутствует
в сигнатурах и полях контекста. Студенческие модули целиком не импортируются.

Квалифицированные имена сокращаются только в разрешённых токенах типов
между `новый` и `(`; содержимое строк, комментариев и аргументов не переписывается.
В оригинальном обработчике поступления таких адаптаций нет: весь метод сохраняется.
Неизвестные, неоднозначные, конфликтующие краткие имена и неподдержанные
YAML-контракты дают `UNSUPPORTED`. Проверка владельца выполняется и для
уже созданного контракта, чтобы кэш не скрывал конфликт namespace.
Конструктор стандартного `ИсключениеНедопустимоеСостояние` явно разрешён
без YAML-контракта для прежних сценариев отказа записи.

Анализ лексический: не разрешает внешние методы/библиотеки, динамические типы,
алиасы импортов, полное затенение имён, приведения и произвольные локальные
объявления типов. Для краткого имени используется существующее разрешение
по namespace модуля и однозначному имени проекта; при неоднозначности требуется
явная квалификация. Многострочные generic-токены пока не поддержаны.

Отрицательный Docker-набор проверяет неверные склад, номенклатуру, количество,
цену, сумму и порядок строк: все шесть дают `FAIL` при сравнении в SBSL.
Неизвестный fake-ID даёт `ERROR`, неподдержанный контракт — `UNSUPPORTED`;
после каждого отрицательного случая выполняется успешный сценарий.
Отчёты JSON/HTML: `result/poc-receipt` и `result/poc-receipt-negative`.
Журнал полной регрессии: `result/poc-receipt/tests.log`.

Проверяется создание документа в памяти. У поступления в архиве нет
`ПослеЗаписи`; обработчик прихода не добавляется. Хранение документов,
движения прихода, повторное проведение, транзакции и реальное выполнение XBQL
остаются отдельным интеграционным этапом. Исходный архив не меняется;
бизнес-логика исполняется только в Docker с прежними ограничениями.

## Интеграционное окружение (этап №9)

Добавлен явный `--integration` и доверенный **SQL smoke** на одноразовом
PostgreSQL 17 в закрытой Docker-сети. Script executor выполняет настоящие
INSERT/SELECT/UPDATE/DELETE через `СоединениеSql`; сравнение и баллы вычисляет SBSL.
Два независимых запуска проверяют фильтрацию по набору/складу, дробные значения,
изменение одного набора, отсутствие исходных данных, удаление и ограниченную роль.
После ошибки запроса БД и сеть также удаляются; следующие проверки продолжаются.
Прежние студенческие runtime-тесты сохраняют Docker с `--network none`.

```bash
docker pull postgres:17@sha256:d74eeac9a635390a49bc21bd49fccd973de707e2a53a76ac49b552b8712ec46f
export ELEMENT_TEST_INTEGRATION_PASSWORD="$(python3 -c 'import secrets; print(secrets.token_hex(24))')"
bin/element-test test --project Dvizhok.xdump \
  --assignment assignments/poc-integration-environment \
  --integration --output result/poc-integration-environment
unset ELEMENT_TEST_INTEGRATION_PASSWORD
```

Конфигурация — `config/integration.json`; переопределение

## Текущие ограничения

Адаптер выделяет методы с типизированными параметрами; объектные методы могут не возвращать результат,
включая вложенные блоки `если`, `для`, `пока`, `выбор`, `попытка`, закрываемые
отдельной строкой `;`. Подключаются достижимые методы того же модуля,
внешних модулей проекта и объявленных библиотек.
Копирует тело метода без изменения бизнес-логики;
убирает внешние аннотации платформы, адаптирует разрешённые токены типов
и добавляет технический entry point.
Индекс XBSL строит дерево выражений и вызовов, но не является полным
компилятором языка. Обнаруженные четвёртым xdump ошибки разбора исправлены;
осталось одно предупреждение о вызове функционального параметра.
См. [диагностику корпуса](docs/xdump-corpus-2026-09-30.md).
Пространство имён определяется каталогами подсистем. Квалифицированные
статические вызовы, алиасы и импорт библиотек разрешаются с учётом видимости;
динамические вызовы и полная семантика доступности платформы не реализованы.

Union-типы поддержаны для генерируемых типов; неоднозначные входы требуют
`{type, value}`. Циклические зависимости типов/модулей и прочие платформенные
типы дают `UNSUPPORTED`. Из временных типов поддержаны входы `Время` и
`ДатаВремя`; с №32 также поддержан вход `Дата` в формате YYYY-MM-DD.
Входы `Момент` и соответствия пока не преобразуются.
`Ууид` поддержан как native вход/выход runtime с этапа №29;
`Обходимое<T>` принимает типизированный массив, а простые локальные структуры
с полями `Строка`, `Число`, `Булево` копируются из исходного модуля.
Границы и проверенная сумма `Обходимое<ДанныеТовара>` описаны в
[отчёте №27](docs/tasks/027-practical-total-cost.md). `ЧитаемыйМассив<T>`
с поддержанным элементом принимается из YAML-списка и сериализуется как результат;
фильтрация, сортировка и представления товаров проверены в
[отчёте №28](docs/tasks/028-practical-stock-presentations.md).
Явные объявления локальных переменных с проектным типом и приведения `как`
адаптируются; dependency closure типов из тела также охватывает конструкторы `новый`.
Полная семантика параметров записи, произвольное исполнение XBQL и формы
запросов вне [ограниченного AST №31](docs/storage-backed-queries.md),
dependency closure динамических вызовов и прочих форм типов внутри тела и LMS
пока не реализованы. Массовый запуск и ограниченный структурный кэш описаны
в [задании №12](docs/tasks/012-batch-runner.md). Последняя локальная регрессия
после задания представлений: 157 тестов, из них 16 штатных opt-in пропусков;
целевой набор с Docker — 4/4. Ранее отдельные
Docker runtime/SQL партии с двумя workers прошли и совпали с одиночным CLI
(`result/poc-batch-runner`).
План — [docs/roadmap.md](docs/roadmap.md). В задании №13 выполнены пункты 1–6 и 8,
а также один сценарий P2; дальнейшие runtime-контракты пункта 7 остаются открытыми.
[План дальнейшей работы](docs/next-task.md): сумма стоимости товаров выполнена,
следующий сценарий выбирается по независимому требованию.
LMS и микросервис приёма архивов отложены.
Разрешение статических внешних вызовов и границы анализа описаны в
[отчёте №22](docs/tasks/022-cross-module-resolution.md).
