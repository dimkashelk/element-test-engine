# Универсальные критерии: обновление worker

Один выпуск worker добавляет декларативные проверки поверх метаданных,
исходников и результатов исполнения. После установки состав проверок
задаёт YAML. Для включения этого формата достаточно заменить **только worker**.
Описание полей есть в [инструкции по интеграции](autocheck-integration.md).

Если выпуск меняет HTTP-контракт, обновите `api` и `worker` вместе.
Для скрипта `tools/ci/autocheck_update_worker.py` передайте `--include-api`.

На общем сервере с бюджетом 1 CPU полный набор требует увеличенного
операторского лимита времени: `limits.maxCheckWallSeconds: 1800` в
`/srv/element-autocheck/config/service.yaml`. При прежних 900 секундах
сервер успел создать 82 из 140 runtime-контейнеров и завершил работу с
`check_timeout`. CPU, память и одна одновременно исполняемая работа сохраняются.
После изменения этого лимита пересоздаётся только worker; значения CPU/RAM
и конфигурации остальных контейнеров не меняются.

Пакет `output/programming/Сервис_Программирование.tar.gz` содержит исходники
сборки и проверки; секретов, SSH-ключей, данных БД и дистрибутива Script в нём
нет. Значение `ENGINE_REVISION` записано в `output/programming/engine-revision.txt`.
Архитектура образа должна соответствовать серверу: сборка выполняется на нём.

Порядок обновления:

1. Проверить реальный `/opt/element-autocheck/compose`, расположение env-файла,
   текущий image worker и подключённые конфигурацию/секреты. Сохранить состояние
   остальных контейнеров (ID, StartedAt, RestartCount).
2. Распаковать выпуск в новый каталог releases, собрать образ по команде
   `buildCommand` из `package-manifest.json` (он также находится рядом с пакетом).
   Старый образ сохранить для отката.
3. Через `/v1/admin/settings` временно отключить приём новых работ, сохранив
   прежнее значение и ETag. Дождаться `occupiedSlots=0`. Текущую работу не прерывать.
4. Сохранить конфигурацию worker и резервную копию управляющей БД. Настроить
   `SERVICE_IMAGE` и `ENGINE_IMAGE_DIGEST` на новый образ, сохранив остальные
   env-параметры и прежние host mounts. Сначала проверить итоговый `compose config`.
5. Выполнить только:

   ```bash
   sudo /opt/element-autocheck/compose up -d --no-deps --force-recreate --wait worker
   ```

   `compose down`, общий `restart` и `up` без указания сервиса здесь не нужны.
6. Проверить worker/readiness и восстановить прежнее состояние приёма через
   API с актуальным ETag. Отправить эталонный дамп с новым файлом критериев.
   Ожидается `completed`, `passed`, `score=320`, `maxScore=320`,
   `unavailablePoints=0`, 320 записей feedback, JSON-артефакт и освобождённый слот.
7. Проверить обычную проверку по прежнему YAML и неизменность остальных контейнеров.

При проблеме с запуском вернуть прежний image/digest и пересоздать только worker
той же командой с `--no-deps`. Результаты API и БД сохраняются.

Локальная приёмка HTTP выполняется отдельным временным Compose-проектом:

```bash
.venv/bin/python tools/ci/autocheck_smoke.py \
  --image element-checker/service:local \
  --runtime script_u_10.0.2_1 \
  --dump output/programming/Эталон_Программирование.xdump \
  --criteria output/programming/Критерии_Программирование.yaml \
  --run-mode isolated --expected-score 320 --timeout 880 \
  --report result/programming-http-acceptance.json
```

Тестовый сценарий удаляет только свой случайно названный Compose-проект.
Ни один существующий серверный контейнер он не изменяет.
