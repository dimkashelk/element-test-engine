# Контракт оценки v1

ТЗ требует `result.json`, понятный отчёт, веса критериев, продолжение после
отдельной ошибки и передачу `student`, `assignment`, `score`, `feedback` в LMS.
Этот этап задаёт локальный транспортный пакет без соединения с LMS. Вход — один
архив, каталог или xdump и одно задание; приложение студента не требуется.

## Файлы и версии

Публичная команда `test` (или `run`) создаёт прежний `result.json` со
`schemaVersion: 1`, `report.html` и новый `grading.json` со
`schemaVersion: "1.0"`. Стандартный вывод и коды возврата сохраняют прежний
формат. Схема пакета: [grading-v1.schema.json](grading-v1.schema.json);
пример: [grading-v1.example.json](grading-v1.example.json).

До следующей major-версии можно добавлять только необязательные поля. Изменение
смысла поля или удаление поля требует новую major-версию и отдельный файл схемы.
Получатель должен проверять `schemaVersion` и отклонять незнакомую major-версию.

`studentId`, `assignmentId`, `runId` необязательны в CLI и равны `null`, если не
переданы. Это идентификаторы запуска, не входы оценки. Они принимают только
буквы ASCII, цифры, `.`, `_`, `:`, `-`, максимум 128 символов. `project`,
`sourceHash`, `compatibilityVersion`, `runMode` также описывают запуск и не
участвуют в начислении баллов. `runMode` равен `isolated` или `integration` в
зависимости от флага `--integration`.

`feedback` имеет одну запись на проверку и сохраняет порядок задания.
`criterionId` — `id` проверки; `group` передаётся, если указан у проверки.
Каждая запись содержит `status`, `points`, `score`, `expected`, `actual`,
`message`. Для проверок без сравниваемого значения `expected`/`actual` равны
`null`. Сообщение по умолчанию описывает статус. Пакет не содержит путей к
файлам, паролей, строк подключения, сырых Docker-логов и свидетельств БД.
Очевидные пути и секреты в текстовых значениях заменяются `[redacted]`; поэтому
`grading.json` не следует использовать как архив полных диагностик.

## Оценка

SBSL вычисляет `score`, `maxScore`, `unavailablePoints` и статус каждой
проверки. Python только переносит эти факты в транспортный пакет.

| Проверка | Баллы | Итог |
|---|---|---|
| `PASS` | Весь вес в `score` и `maxScore` | `passed`, если остальные тоже `PASS` |
| `FAIL` | 0, вес в `maxScore` | `failed` |
| `ERROR`, `TIMEOUT`, `UNSUPPORTED`, `SKIPPED` | 0, вес в `unavailablePoints` | `incomplete`, если нет `FAIL` |

`failed` имеет приоритет над `incomplete`, когда набор содержит и `FAIL`, и
недоступную проверку. `maxScore + unavailablePoints` равен сумме весов задания.
Только `FAIL` утверждает невыполнение критерия. `ERROR` может быть связан с
входом, исполнением или инфраструктурой, поэтому требует разбора и повтора.
Отрицательные ожидания приводят к `FAIL` после сравнения в SBSL; следующие
проверки продолжаются.

## Воспроизведение

```bash
bin/element-test test --project Dvizhok.xdump --assignment assignments/demo \
  --output result/demo --student-id student-001 --assignment-id demo --run-id local-001
```

Для воспроизводимости пакет фиксирует `sourceHash`, версию совместимости,
имя задания, режим и идентификатор запуска. Задание и версия движка должны
храниться вместе с пакетом во внутренней инфраструктуре; пакет не включает
тестовые сценарии целиком. Внешняя отправка, очередь и LMS API здесь отсутствуют.
