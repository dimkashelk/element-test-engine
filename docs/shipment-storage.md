# Отгрузка с хранением: ограниченный SQL-адаптер

Итерация №10. По уточнению пользователя от 27.09.2026 система проверяет
студенческие исходники без доступа к приложениям Элемента. Платформенный эталон
не требуется и не планируется. Основание API — документированные сигнатуры,
перечисленные в [integration-environment.md](integration-environment.md);
эксперимент подтверждает **поведение нашего SQL-адаптера**, а не платформы.

`assignments/poc-shipment-storage` выполняет исходные
`Отгрузка.ПередЗаписью` и `Отгрузка.ПослеЗаписи` в Script executor / Docker.
Архив и бизнес-условия не меняются. Техническая адаптация заменяет единственный
литерал XBQL вызовом SQL-адаптера и передаёт SQL-соединение конструктору набора.
Типы берутся из YAML. Набор использует генерацию прежних типов mocks, но операции
набора полностью заменены SQL-записью: подставных строк и журнала spy-вызовов нет.
Прежний mocks-режим продолжает работать отдельно.

## Воспроизведение и контракт задания

```bash
export ELEMENT_TEST_INTEGRATION_PASSWORD="$(python3 -c 'import secrets; print(secrets.token_hex(24))')"
bin/element-test test --project Dvizhok.tar \
  --assignment assignments/poc-shipment-storage --integration \
  --output result/poc-shipment-storage/cli
unset ELEMENT_TEST_INTEGRATION_PASSWORD

ELEMENT_TEST_DOCKER_TESTS=1 ELEMENT_TEST_INTEGRATION_TESTS=1 \
  python3 -m unittest discover -s tests -v \
  > result/poc-shipment-storage/tests.log 2>&1
```

Конфигурация, digest образов, runtime 9.0 и preflight сохранены из этапа №9.
Без `--integration` результат UNSUPPORTED; fallback к mocks отсутствует.
Операция задаётся как `integration: {backend: postgres, operation: shipment-storage}`.
`target`, `args`, `context`, `mocks`, `runtimeDateTime` не принимаются.
Схема Отгрузки и РегистрТовары должна совпадать с поддержанным контрактом;
дополнительные поля, другой регистр и другие литералы запроса — UNSUPPORTED.

Начальное состояние задаётся доверенными `stock`-fixtures. Каждое движение:

```yaml
reference: {type: ПоступлениеТоваров.Ссылка, value: {Идентификатор: receipt-1}}
period: '2026-09-27T12:30:45'
direction: Приход
item: product-1
warehouse: main
quantity: 8.125
```

Fixture записывается доверенным сгенерированным кодом с параметрами SQL до
вызова студентов. У `ПоступлениеТоваров` нет `ПослеЗаписи`; он не добавлен.
Ссылки — тип + строковый ID fixture, а не реальные платформенные UUID.
Для `stock` допускаются оба вида движения и оба типа регистратора.
Набор очищает/замещает только совпадающую пару тип/ID; одинаковые ID разных
типов не смешиваются. Имена типов в колонке регистратора проверяются БД.

`steps` содержит от 1 до 40 операций; `stock` — до 100 движений:

- `write` + `document`: начальные поля Отгрузки, обязательны `Ссылка` и `Дата`.
  Выполняется `ТестКонтекст.Объект.Записать()`, возвращает `written`/`rejected`.
- `load` + `reference`: типизированная ссылка Отгрузки; возвращается свежий
  снимок или null для отсутствующего документа.
- `load-fresh` + `reference`: снимок, очистка его ТЧ в памяти, новая загрузка.
  Обе возвращённые копии сохраняют исходные строки; БД не меняется.
- `clear` + типизированная `reference`: пустой набор с фильтром и `Записать()`.
  Удаляет движения выбранного регистратора, сохраняет документ и другие наборы.

Неизвестные действия и конфликты типов отклоняются до создания Docker-ресурсов.
Неверные значения и неизвестные поля документа не превращаются в исполняемый код.
Даты задаются точной строкой без часового пояса; runtime-дату можно использовать
в прежних mocks-сценариях. Фиксированные даты здесь позволяют независимо
проверить сохранение периода в БД.

## Хранение, запись и граница транзакции

Таблицы `smoke.documents`, `smoke.lines`, `smoke.movements` хранят:
тип документа/ID, дату и номер, склад; порядок строк, номенклатуру, количество,
цену и готовую сумму; период, Приход/Расход и индекс движения в регистраторе.
Количества/цены/суммы — PostgreSQL `numeric`, без округления к шести знакам.
Дата и период — `timestamp` без часового пояса. Nullable-измерения сохраняются
SQL Null; их отличают от `Неопределено` через штатный SQL API.

Запись контекста использует одно JDBC-соединение:
`BEGIN → загрузка До → ПередЗаписью → документ/строки → ПослеЗаписи → COMMIT`.
Исключение вызывает `ROLLBACK`. Для нового документа До содержит текущее
состояние; для существующего — предыдущий снимок из БД. ПараметрыЗаписи пусты.
Повторная запись набора по умолчанию замещает движения; `Замещать = Ложь`
дописывает с новыми индексами и очищает набор в памяти. Пустой набор при
замещении удаляет прежние движения. Неинициализированный фильтр вызывает ошибку.

Это атомарность PostgreSQL для **одного сгенерированного контекста**.
Платформенные блокировки, вложенные транзакции, параллельные записи, уникальность
номера, автонумерация, все ограничения YAML, активность набора и системные
обработчики регистра не моделируются. `ЗагрузитьОбъект(Заблокировать = Истина)`
не поддерживается. Загруженный `Отгрузка.Объект` является снимком данных;
общий API записи загруженных объектов не реализован. Метод записи принадлежит
техническому контексту, который содержит исходные обработчики.
`Представление()` использует базовое представление SBSL, без платформенного
справочника представлений. Текст ошибки недостатка не является эталоном платформы.

## Ограниченный запрос остатков

Принимается только исходный литерал `ПередЗаписью`, с нормализацией пробелов
и комментариев. Иные поля, условия, параметры и виртуальные таблицы —
UNSUPPORTED. Это трансляция одного литерала, **не исполнение XBQL**.

SQL суммирует Приход минус Расход по **всем измерениям**, номенклатуре и складу,
отбрасывает нулевые группы и возвращает только запрошенные номенклатуры.
Пустой список даёт пустой результат; отсутствующий товар остаётся отсутствующим.
Исходный код использует умолчание 0 и исходное сравнение `<`, поэтому равенство
остатка и количества допускается. Склад исходного документа не добавлен в фильтр:
остаток другого склада того же товара также участвует в запросе.

Если запрошенный товар имеет ненулевые остатки на нескольких складах, проекция
теряет склад и даёт повторяющийся ключ для `ВСоответствие`. Такой сценарий
возвращает UNSUPPORTED с откатом записи: порядок SQL-строк не должен определять
оценку студента. Разные товары на разных складах поддержаны. Дубли строк ТЧ,
повторное проведение при малом остатке и исходный контроль до замещения сохраняют
бизнес-условия исходного обработчика; алгоритм не исправляется ради теста.

## Изоляция и проверка результата

Каждая проверка имеет отдельные UUID, закрытую сеть, PostgreSQL в tmpfs и executor.
Admin-пароль берётся из `ELEMENT_TEST_INTEGRATION_PASSWORD`; пароль ограниченной
роли генерируется отдельно на запуск и никогда не совпадает с admin.
Студенческий контейнер видит только ограниченную роль, runtime, сгенерированные
модули и read-only файл подключения. Bootstrap, admin, Docker socket, исходная
рабочая папка и внешняя сеть недоступны. Сохраняются непривилегированный пользователь,
read-only rootfs, ограничения памяти/CPU/pids, 30 секунд wall time и 1 MiB вывода.
Роль не имеет SUPERUSER/CREATEDB/CREATEROLE или прав создания схем.

После executor доверенный Python независимо читает **committed** документы,
строки и движения через `psql`. Состояние БД присоединяется к `actual.database`;
баллы и сравнение с `expected` определяет SBSL. При runtime-ошибке/неоднозначности
состояние доступно как `storageEvidence` и не оценивается как PASS.
Аудит ограничен 1000 строк на таблицу. Вывод с JDBC-строкой или секретом запуска
отбрасывается; raw Docker/driver diagnostics в отчёт не попадают.
Это изоляция ресурсов, а не защита от всех способов обмана тестов: студент
может обращаться к разрешённым таблицам своей одноразовой БД через SQL API.

В `finally` удаляются executor, БД и сеть и проверяется отсутствие ресурсов.
Ошибка очистки — ERROR. SIGKILL по-прежнему требует удаления ресурсов конкретного
runId. ERROR/UNSUPPORTED не останавливают следующие проверки задания.

## Проверки и артефакты

Восемь положительных сценариев: дробные строки и независимые снимки, пустая ТЧ,
равенство, недостаток, отсутствующий товар, повторная запись с пустым замещением,
изоляция двух документов и одинаковых ID разных типов, несколько приходов/расходов.
Отрицательный набор: неверное количество — FAIL в SBSL; сбой после записи
документа и движений — ERROR с независимым подтверждением отката;
неизвестная операция и неоднозначная проекция складов — UNSUPPORTED.
После ошибочных/неподдержанных проверок выполняются успешные сценарии.
Архив проверяется побайтно до и после; контейнеры/сети опрашиваются независимо.

Артефакты: `result/poc-shipment-storage/result.json`, `report.html`,
`negative.json`, `negative.html`, `tests.log`; публичная CLI — каталог `cli`.
Полная регрессия — **70/70**, без пропусков (268.994 секунды); отдельный
интеграционный набор — 4/4; публичная CLI — 8/8 PASS, код 0.
Без opt-in — 8 UNSUPPORTED, код 2. История проверки — [roadmap.md](roadmap.md).
Штатный SQL Null и параметры сверены с официальными
[ЗапросSql](https://1cmycloud.com/console/help/lang/docs/stdlib/Std/Database/Sql/SqlQuery_ru/)
и [Null](https://1cmycloud.com/console/help/lang/docs/stdlib/Std/Database/Null_ru/),
затем проверены в установленном executor с `-c 9.0`.
