# Промпт для генерации тестов Element Test Engine

Передать ИИ этот промпт вместе с [руководством](test-authoring-guide.md),
требованиями задания и исходными материалами проекта. Заполнить раздел «Вход».
Руководство следует прикладывать целиком: одного промпта недостаточно для
подробных контрактов mocks и всех форм expected.

---

Ты составляешь оценочные тесты учебного проекта 1С:Предприятие.Элемент
для локального Element Test Engine. Итог — файлы assignment.yaml и при
необходимости structural/*.yaml, runtime/*.yaml.

- Название задания: <заполнить>.
- Требования и правила правильного поведения: <вставить>.
- Общий бюджет баллов: <заполнить>.
- Имя каталога задания: <например receipt-training>.
- Проект.yaml и режим совместимости: <приложить>.
- YAML проверяемых и зависимых объектов: <приложить>.
- XBSL проверяемых модулей и эталонных зависимых методов: <приложить>.
- Модель inspect, если доступна: <приложить>.
- Источник кода: <эталон / студенческое решение / иной источник>.
- Руководство test-authoring-guide.md: <приложить целиком>.

## Обязательные правила

1. Считай приложенное руководство контрактом текущего движка. Не переноси
   возможности полной платформы автоматически на тестовый адаптер.
2. Expected выводи из требований. Не повторяй ошибки студенческого решения.
   Противоречия требований и эталона обозначь явно до генерации спорного теста.
3. Используй только type: element, field, tableSection, enumValue, module,
   method, runtime. Не придумывай assert, expectedStatus, tolerance,
   beforeEach, afterEach и другие неподдержанные механизмы. `steps` допустимо
   только для `integration: {backend: postgres, operation: shipment-storage}`,
   не в обычном runtime.
4. Не задавай execution: его формирует runner.
5. Все id уникальны; points — конечные неотрицательные числа.
   Общую сумму баллов согласуй с бюджетом. Не используй anchors/aliases YAML.
6. Реквизиты объекта и ТЧ проверяй отдельными field по имени.
   Не требуй порядок реквизитов и UUID без явного требования задания.
7. Args — список в порядке сигнатуры. Context — только для модуля *.Объект.
   Для void нужен context. Observe — непустой список существующих полей
   верхнего уровня, без повторов и вложенных путей.
8. Выбирай правильную форму expected по возвращаемому значению, context,
   captureCalls и captureException. Сравнение полное, порядок массивов значим.
   Ожидай все сериализуемые поля строк наблюдаемой ТЧ, включая умолчания.
9. Входы задавай как данные: true/false, числа без кавычек, null только
   для nullable, ссылки как {Идентификатор: "id"}, union через {type, value}
   при неоднозначности. Не задавай XBSL-выражения в args.
10. Текущую дату проверяй runtimeDateTime с независимым снимком и маркером
    __runtimeDateTime__. Не вычисляй expected повторно на хосте.
11. Mocks задавай явно. Objects возвращают новые снимки, registers наблюдают
    вызовы, queries возвращают rows. Они не обеспечивают хранение или XBQL.
    Текст запроса бери из метода, сохраняя значимые строки и выражения.
12. Не создавай тест несуществующего метода. В Dvizhok.xdump у
    ПоступлениеТоваров отсутствует ПослеЗаписи.
13. Если критерий неподдержан, вынеси его в ограничения. Не подменяй его
    проверкой другого поведения и не объявляй автоматически пройденным.
14. Не включай заведомо неверные expected в оценочный набор.
    Контрольные FAIL/ERROR/UNSUPPORTED сценарии движка описывай отдельно.
15. Не изменяй бизнес-логику и исходный архив. Студенческий код выполнять
    только в изолированном Docker, не на хосте.
16. Не утверждай, что тесты выполнены, если ты только сгенерировал YAML.
    Загрузка assignment не доказывает runtime-совместимость и правильность ожиданий.

## Порядок работы

1. Составь перечень объектов, реквизитов, ТЧ, методов, сигнатур и зависимостей.
2. Сопоставь требования с поддержанными видами проверок.
3. Отдели неподдержанные требования и критические недостающие сведения.
4. Составь матрицу: требование, id, вход/состояние, ожидаемый эффект, баллы.
5. Подбери обычные, пустые, многострочные, дробные и граничные сценарии
   только в рамках требований. Данные должны различать типичные ошибки.
6. Сформируй YAML. Проверь точность имён, поля схемы, формы expected,
   вложенность args, типы, умолчания, сумму баллов и уникальность id.
7. Если есть среда, загрузи через load_assignment и выполни на эталоне
   через bin/element-test test. Прочитай каждое несовпадение в отчёте.
   Не подгоняй ожидания под ошибочный результат: проверь требования.
8. Отдельно предложи контроль чувствительности к неверным значениям
   и перестановке строк, не меняя оценочные файлы.

## Формат ответа

1. Матрица покрытия требований и баллов.
2. Для каждого файла — путь и полный YAML, без многоточий и заглушек
   в исполняемой части. Используй один assignment.yaml, если разделение не нужно.
3. Команды проверки загрузки и запуска. Пути приведи относительно корня проекта.
4. Ограничения и недостающие сведения. Если они препятствуют правильному
   expected, не выдавай спорный тест за готовый.
5. Перечень допущений и отдельные предложения контроля самого движка.
6. Что реально проверено: генерация / загрузка / адаптация / Docker-запуск.
   Если выполнен запуск — число проверок, исходы и пути к JSON/HTML-отчётам.

Начни с анализа предоставленных материалов и матрицы требований.
