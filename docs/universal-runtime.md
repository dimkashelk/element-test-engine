# Универсальная подготовка XBSL: контракты этапов №29–37

Один `plan_execution` готовит проверяемые корни и их исходные зависимости;
`renderer` компонует SBSL, executor выполняет бизнес-код, SBSL оценивает
наблюдения по независимому `expected`. Команды `test`, `run` и workers `batch`
используют этот же путь. Legacy SQL-профиль выбирает обработчики через planner
и использует общие операции хранения; его прежний формат задания сохраняется.

## ExecutionPlan

План содержит `entry`, `symbols`, `dependencies`, `bindings`, `transforms`,
`sourceTransforms`, `resources`, `exceptionContracts`, `declarations`,
`typeRequirements`, `observations`, `unavailable`, `queries`.
Типизированные AST запросов сохраняют источники/поля, диапазоны параметров,
backend и тип строки; [контракт №31](storage-backed-queries.md).
СрезПоследних дополнительно хранит периодичность, все измерения, диапазон даты
и captured boundary; [контракт №33](storage-backed-information-register-slices.md).
Идентичность символа состоит из поставщика/проекта/версии, namespace, владельца,
декларации и исходного файла. Каждый символ сохраняет исходный срез, диапазон,
типы параметров и аннотации. Коллизии кратких имён получают стабильное имя
по хешу полной разрешённой идентичности. Владельцы локальных структур различаются
по файлу объявления. Возвращаемые и локальные типы, конструкторы, поля метаданных,
константы и обработчики записи включаются по зависимостям.

Граф выбирает объявления для компоновки, а порядок вызовов и выбранную ветвь
определяет исходный код. Ни топологический обход, ни Python не исполняют
бизнес-формулы. Замыкание методов и проверка циклов итеративны: ограничения
глубины со стороны движка нет. В Docker подтверждено исполнение 1200 методов
цепочки с итогом `17`. Рекурсивные вызовы в одном модуле сохраняются; циклический
импорт SBSL-модулей отклоняется как неподдержанная компоновка.
Ресурсные лимиты executor остаются: 384 MiB, 1 CPU, CPU ulimit 8 секунд,
wall timeout до 30 секунд. Предел native стека не объявляется бесконечным.

В рабочем временном каталоге `execution-plan.json` содержит внутренний IR.
Публичный `execution-plans.json` вместо тел методов содержит SHA-256,
идентичность и диапазоны; `runtime-evidence.json` отделяет техническую трассу,
статусы и аудит от оценки. Существующие `result.json`, `grading.json` v1 и HTML
сохраняют прежний контракт. План не содержит `expected`.

Реестр отличает проектную декларацию, функциональный вызов, native API и
адаптер метаданных. Native сигнатуру окончательно проверяет компилятор.
Ошибка компиляции поддерживаемой среды даёт `UNSUPPORTED`, сбой Docker/SQL —
`ERROR`/`TIMEOUT`. Инфраструктурное исключение не превращается в ожидаемое
бизнес-исключение. Reachable неподдержанное обращение не даёт частичный `PASS`;
объявление недостижимого метода само по себе не блокирует подготовку.

## Новые поля runtime-критерия

Прежние `target`, `args`, `context`, `observe`, `captureCalls`,
`observeCallArguments`, `captureException` сохранены.
`captureException: true` работает для свободного и объектного метода любого
вида результата: прежний actual оборачивается в `{result, exception}`.
Только подтверждённое бизнес-исключение входит в эту оболочку.

`trace: true` записывает вход/выход исходных символов, аргументы и результат.
Для void-метода событие `leave` фиксируется в finally при обычном выходе,
раннем возврате и исключении; оно само по себе не означает успешный результат.
Трасса сохраняется в evidence, не добавляет скрытых требований к реализации
студента и не входит в `expected`.

`sequence` — 1..40 `{method, args}` того же целевого модуля. `target` задаёт
владельца и корень подготовки; его `args` также должны соответствовать сигнатуре.
Каждый шаг выполняется в общей сессии, result/context фиксируется до следующего.
Actual вместо одного результата содержит `{actions: [...]}`. С
`captureException` каждый шаг содержит `{result, exception}`.

```yaml
target: {module: Ledger, namespace: Biz, method: Write}
args: [one, Initial, 1]
captureException: true
storage: {backend: memory, transaction: true}
sequence:
  - {method: Write, args: [one, Initial, 1]}
  - {method: Read, args: [one]}
```

`storage` принимает `backend: memory|postgres`, `transaction: Булево`,
`idType: Строка|Ууид` (по умолчанию Строка), `registers: [Namespace::Register]`
и `initial: [{type: Namespace::Object, value: {...}}]` до 100 записей.
Состав объекта/строк и типы генерируются из YAML; схемы с другими именами
не требуют ветки backend. `storage` и `mocks` в одном критерии запрещены.
Actual при storage: `{result: прежнийActual, storage: [{type, id, value}]}`.
Ожидание обязательно включает сохраняемые поля/строки: одинаковая возвращённая
ссылка сама по себе не доказывает корректную запись.

Memory хранит JSON-снимки через native файловое API во временном tmpfs Docker.
Каждая загрузка десериализует новый объект, изменённая копия не меняет состояние
до записи. `ПередЗаписью` получает прежние сохранённые данные при обновлении;
для новой записи — данные создаваемого объекта. Затем выполняется запись и
оригинальный `ПослеЗаписи`, если он объявлен.
Наборы регистров используют идентичность регистра и сериализованный фильтр
как ключ; значения — реальные строки набора, а не spy-журнал.

PostgreSQL требует `--integration` и
`integration: {backend: postgres, operation: metadata-storage}`.
Сессия проходит те же операции и публикует снимки на успешных границах исходного ресурса
или внешнего driver; неизменённый снимок повторно не публикуется;
доверенная инфраструктура независимо считывает аудит из БД. Это не контракт
конкурентного доступа: блокировки относятся только к изолированной staging-сессии,
наблюдение промежуточных снимков другой SQL-сессией не реализовано. Старый shipment-storage выполняет прежние шаги,
но load/save/record-set и таблицы `smoke.objects`/`smoke.records` общие;
представления сохраняют его прежний аудит. Литерал поддержанного запроса
разбирается в AST; выражение `%{...}` берётся из оригинального источника.

## Воспроизведение

```bash
bin/element-test test --project tests/corpus/universal/chain \
  --assignment assignments/universal-chain --output result/universal-runtime/chain
bin/element-test test --project tests/corpus/universal/crud \
  --assignment assignments/universal-crud --output result/universal-runtime/crud
ELEMENT_TEST_DOCKER_TESTS=1 ELEMENT_TEST_INTEGRATION_TESTS=1 \
  python3 -m unittest discover -s tests -v
```

В универсальных заданиях намеренно присутствуют независимые `PASS`, `FAIL` и
`UNSUPPORTED`: общий exit code 1 ожидаем. SQL-примеры требуют случайного
`ELEMENT_TEST_INTEGRATION_PASSWORD` в окружении, как прежние интеграционные
задания. Пароли не входят в исходники, план, трассу и публичный пакет.
Корпус, действительные исходы и ограничения описаны в
[отчёте №29](tasks/029-universal-runtime.md#отчёт-о-реализации).

Расширенный контракт исходного ресурса, UUID, исключений и блокировки —
[этап №30](transactions-and-business-exceptions.md). Ресурсы и проверенные
sourceTransforms теперь также входят в ExecutionPlan.


Этап №31 добавляет staged-выборку по фактическим сохранённым Справочникам/Документам.
Один источник, равенство/И, параметры, проекции, сортировка и ПЕРВЫЕ исполняются
в Script по текущей транзакционной сессии. Nullable-предикаты, JOIN, IN/иерархия,
агрегаты и общий XBQL остаются недоступны. Результат — detached-массив;
native cursor API не воспроизводится. Файловый отказ остаётся инфраструктурным
даже при общем catch. Полный контракт — [storage-backed-queries.md](storage-backed-queries.md).


Этап №32 добавляет `НаборЗаписей.Прочитать()` и обход доказанного metadata-типа
по AST с сохранением исходных зависимостей. Полные фильтры, native Дата для День,
новые строки, teacher `initialRegisters`, замещение/добавление, транзакции,
коллизии типов регистратора и independent SQL audit описаны в
[storage-backed-record-sets.md](storage-backed-record-sets.md). Частичные
фильтры и неподтверждённый native API остаются UNSUPPORTED; прежние mocks и
legacy-контракты сохраняются.

Этап №33 расширяет общий query AST источником СрезПоследних для День.
Все измерения образуют ключ группы; включительная граница предшествует выбору
максимального периода, ГДЕ следует после среза. Поддержаны nullable-ссылка с
заполненным параметром и сортировка Дата. Пустая дата фиксирует текущую дату
UTC из Docker при создании запроса. Это объявленный адаптер, поскольку native
XBQL отсутствует, а поведение будущих строк платформы не подтверждено.
Полный [контракт №33](storage-backed-information-register-slices.md) описывает
свежие снимки, повторное чтение, rollback и SQL-аудит. СрезПервых, JOIN,
ЗАПОЛНИТЬ, остальные NULL-операции и периодичности остаются UNSUPPORTED.


## Контекст форм объектов — №34

Общий planner/renderer поддерживает контекст `КомпонентИнтерфейса`,
наследующего `ФормаОбъекта<T.Объект>`: собственные YAML-свойства, типизированный
Объект, именованные вложенные Надписи. Обязателен `lifecycle: {isNew: true/false}`;
observe задаёт пути, например `Компоненты.Caption.Значение`. Командный аргумент —
пассивное `{}`. `{contextPath: Объект.Товары}` передаёт объявленную таблицу
экземпляра в параметр с совпадающим типом; её изменения доступны observe. Sequence сохраняет один экземпляр; критерии и batch изолированы.
Исходные helper исполняются, expected не входит в IR. JVM локаль форм фиксирована
в en-US (дробные числа в надписях с точкой); ссылки используют native UUID.
Без formEffects Записать/Открыть из формы недоступны; вычисление YAML-выражений и браузерный UI не реализованы.

Контракт и границы: [form-context.md](form-context.md).
Публичный корпус: `assignments/dvizhok-form-context`, переносимые проекты —
`tests/corpus/form-context/ledgers` и `accounts`.

Воспроизводимая карта файлов/методов/планов/фактов:

```sh
python3 -m element_test.coverage --project Dvizhok.xdump --assignments assignments \
  --evidence result/dvizhok-form-context/test \
  --evidence result/dvizhok-form-context/run \
  --evidence result/dvizhok-form-context/legacy \
  --output result/dvizhok-form-context/coverage
```

Карта отделяет ограниченную статическую проверку, объявленный критерий,
подготовленный план, фактический вызов и независимую оценку. Пустой модуль
не получает runtime PASS; вызов зависимости не подтверждает все её ветки.


Этап №35 расширяет декларативный адаптер обычной Формой, константами и
часами. IR сохраняет `constants`, `clock`, `executorLocale`, диапазоны
аннотаций и AST-преобразований. `snapshotArgs` наблюдает реальные аргументы,
`snapshotConstants` независимо читает подготовленные данные.
`captureExceptionTypes: [ИсключениеНедопустимыйАргумент]` разрешён только
с `captureException`, для подтверждённого missing-key контракта; прежний
набор перехватываемых ошибок сохраняется.
Подробности — [welcome-calendar.md](welcome-calendar.md).

Контракт эффектов формы №36: [form-effects.md](form-effects.md). IR хранит
formOpenings/openFormContexts, диапазоны и разрешённые типы параметров;
публичный пакет заменяет их выражения на expressionHash. PostgreSQL проверяет
последовательность фиксаций независимым sqlSnapshots-аудитом.
