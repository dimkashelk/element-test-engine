# Запросы по состоянию storage — контракт №31

Контракт `storage-staged-executor-v1` реализован в общем ExecutionPlan.
Это адаптер запросов в Script 9.0, использующий текущее staging-состояние
memory/PostgreSQL. Python разбирает и связывает AST, генерирует типы и код;
фильтрация, сравнение, сортировка, проекция, вычисление параметров и исходные
зависимости исполняются в executor. Оценивание выполняет SBSL.

## Семантика и основания

Официальная документация Элемента 9.1 проверена 1 октября 2026 года через
авторизованный браузер: [ВЫБРАТЬ](https://1cmycloud.com/console/help/element/9.1/docs/topics/select-statement/),
[ТипизированныйЗапрос](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/Std/Database/TypedQuery_ru/),
[РезультатЗапроса](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/Std/Database/QueryResult_ru/).
Адрес соответствующего раздела `/element/9.0/` возвращает 404. Поэтому документация
9.1 служит описанием платформенного API, а не доказательством наличия этого API
в executor. Проверенный дистрибутив 10.0.2-1 запускается с `-c 9.0`.

Native-проба `Query.sbsl` установила отсутствие литерала `Запрос` в Script.
`Values.sbsl` проверяет обход/пустоту массива, единственный/отсутствующий результат,
исключение при нескольких строках, сравнение native UUID и структур ссылок.
`Parameters.sbsl` проверяет порядок вызовов аргументов и фиксацию значений
конструктором. `Readonly.sbsl` подтверждает отказ изменения readonly-поля.
Исходники сохранены в `tests/corpus/storage-queries/native-probes/`, журналы —
`result/storage-backed-queries/native-probes/`. Это отдельные доверенные пробы;
студенческие методы запускаются только в Docker.

| Операция | Поддержанный контракт адаптера |
|---|---|
| Источник | Один обычный Справочник/Документ, разрешённый через namespace/import/alias |
| Проекция | Сохранённые Строка, Число, Булево, Ууид и типизированная Ссылка, включая nullable; КАК либо имя поля |
| Предикаты | Равенство `=`/`==` поля параметру, конъюнкция `И`; без nullable-предикатов |
| Параметры | `%Имя` и `%{выражение}` с проверенными границами, включая вложенные скобки/строки/комментарии |
| Вычисление | При создании запроса, слева направо; повтор простой переменной использует один captured slot; каждое отдельное выражение вычисляется один раз |
| Повтор Выполнить | Новое чтение текущего staging, с ранее captured параметрами |
| Сортировка | Несколько не-nullable полей Число/Строка, ВОЗР/УБЫВ; допускается псевдоним проекции |
| Лимит | ПЕРВЫЕ с положительным целым литералом, после сортировки/фильтрации |
| Результат | Массив только спроецированных readonly-строк; свежие десериализованные значения |
| ЕдинственныйИлиНеопределено | Нет строк → Неопределено; одна → строка; несколько → native ИсключениеНедопустимоеСостояние (`Std::IllegalStateException`) |
| Пусто/обход | Native массив Script; результат является фиксированным снимком |
| Ссылка | Native UUID/строковый ID согласно storage.idType и отдельно разрешённый тип владельца |

У платформенного РезультатЗапроса обход однократный и связан с освобождением
ресурсов. Адаптер материализует detached-массив, допускающий повторный обход,
и не создаёт курсор. Только доказанный `исп R = Q.Выполнить()` понижается
в `знч` и получает отдельную capability-привязку; закрытие этой области не
изменяет материализованный снимок. Явный API `Закрыть` и иные ресурсные
получатели не подменяются. Этот контракт не воспроизводит native курсор.

Без УПОРЯДОЧИТЬ ПО порядок и выбор конкретной строки среди нескольких совпадений
не гарантируются. Ожидания ПЕРВЫЕ без сортировки должны иметь единственное
совпадение. Сортировка одинаковых ключей также не задаёт порядок между ними.
Сравнение nullable-поля, SQL Null, JOIN, IN/иерархия, литералы в предикатах,
вычисляемые проекции, агрегаты, виртуальные таблицы и общий XBQL честно
отклоняются. Nullable-проекция сериализуется в JSON null; это не перенос правил
SQL NULL в XBSL. Неопределено отсутствующего результата остаётся JSON null.

## Состояние и отказы

ЧитатьВсе читает актуальный файл сессии при каждом Выполнить; в исходной
транзакции это включает ещё не опубликованные записи. Исходные обработчики
и зависимости пользуются тем же состоянием. Rollback восстанавливает staging;
раньше завершённые записи и соседние типы сохраняются. Запрос не вызывает commit.
PostgreSQL получает состояние на прежних границах публикации, а независимый
SELECT по `smoke.objects` проверяет реально опубликованные записи. SQL SELECT
не используется для самой staged-выборки. Возврат и SQL-аудит оцениваются отдельно.

Файловые ошибки чтения/записи сохраняют sticky-маркер `.failed`, который не
очищается rollback и проверяется driver после исходного метода. Executor также
пишет служебный признак отказа в вывод: даже если файл маркера недоступен,
ответ не принимается как успешный. Общий catch
не превращает файловый/SQL-сбой в оцениваемый бизнес-результат. Timeout остаётся
TIMEOUT; после каждого сценария sandbox/контейнер удаляется. Публикация SQL
сохраняет прежний sticky-контракт №30.

`storage` включает чтение состояния явно. Совместный `storage` и `mocks`
отклоняется как invalid_test; fallback к мокам при ошибке отсутствует.
Прежние `mocks.queries` и отдельный legacy-контракт остатков сохранены.

## Примеры для преподавателя

```
bin/element-test test --project tests/corpus/storage-queries/catalog \
  --assignment assignments/storage-queries-catalog --output result/query-catalog
bin/element-test test --project Prakticheskie-primery-2026-09-30-15-20.xdump \
  --assignment assignments/storage-queries-real --output result/query-real
```

Для PostgreSQL используйте задание с суффиксом `-sql` и `--integration`.
Общая схема:

```yaml
storage:
  idType: Ууид
  initial:
    - type: Data::Product
      value:
        Ссылка: {Идентификатор: 12345678-1234-4234-8234-123456789abc}
        Label: A
        Amount: 3
```

`expected` должен независимо включать `result` и `storage`. Планы записывают
источник/диапазон литерала, AST с владельцами и типами полей, все диапазоны
параметров, backend и rowType; преподавательских ответов в плане нет.
Имена методов/таблиц/полей и expected не выбирают адаптер.

Три практических fixture недоступности теперь используют неизменённый
`ИерархическийСправочник::Задачи.ЗадачиПроектаЗавершены` с `В ИЕРАРХИИ`.
Поиск по артикулу вынесен в новое положительное задание. Основные практические
задания и их максимумы не менялись; контрольный fixture по-прежнему отдельный
и имеет один недоступный балл. Прежнюю недоступность поиска нельзя использовать
как свидетельство границы №31.
