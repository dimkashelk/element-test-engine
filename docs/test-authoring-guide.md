# Руководство по созданию тестов Element Test Engine для генерации через ИИ

Актуализировано 30 сентября 2026 года. Описывает формат заданий текущего
движка, включая P2 для `Примеры_new` и ограниченный интеграционный режим.
Это контракт учебного движка, а не полный стандарт тестирования платформы 1С:Элемент.
При изменении движка руководство нужно сверять с кодом.

Документ предназначен преподавателю и ИИ, который формирует задания проверки.
Его можно передать ИИ целиком вместе с требованиями учебного задания, YAML
метаданных и нужными XBSL-модулями. Готовый промпт: [ai-test-generation-prompt.md](ai-test-generation-prompt.md).

## 1. Что именно проверяет движок

Движок решает две разные задачи:

1. **Структурные проверки:** наличие объекта, реквизита, табличной части,
   элемента перечисления, модуля, метода, а также их заданные свойства.
2. **Runtime-проверки:** вызов выделенного оригинального метода и сравнение
   его результата, состояния объекта, вызовов подставных API и исключений.

Python безопасно читает проект и готовит контракты. Студенческая бизнес-логика
исполняется Script executor в изолированном Docker. Сравнение и баллы выполняет
SBSL-движок. Код студента не переводится в Python.

Проверка метаданных не доказывает корректность поведения. Проверка результата
с подставным запросом не доказывает корректность самого XBQL-запроса.
Отдельный opt-in режим поддерживает SQL smoke и ограниченное хранение отгрузки;
его контракт описан в [интеграционном окружении](integration-environment.md) и
[адаптере отгрузки](shipment-storage.md). Произвольный XBQL не исполняется.

## 2. Какие материалы передать ИИ

Для генерации нужны:

| Материал | Для чего нужен |
|---|---|
| Требования учебного задания | Определяют правильное поведение и критерии оценки |
| `Проект.yaml` | Режим совместимости, поставщик и имя проекта |
| YAML проверяемых объектов | Имена, типы, свойства, табличные части и перечисления |
| XBSL проверяемых модулей | Сигнатуры, зависимости и доступность runtime-адаптации |
| YAML зависимых объектов | Контракты ссылок, регистров и возвращаемых снимков |
| Это руководство | Поддержанный формат и ограничения движка |
| Общий бюджет баллов | Распределение весов проверок |

При необходимости сначала получить модель проекта:

```bash
bin/element-test inspect Dvizhok.xdump --output result/inspection.json
bin/element-test validate Dvizhok.xdump
```

`inspect` содержит метаданные, namespace и индекс сигнатур, но не заменяет текст
тел методов. `validate` — базовая диагностика, а не компиляция всей конфигурации.

Ожидания нужно выводить из **требований задания**. Код эталона помогает понять
контракт и зависимости. Если предоставлен код студента, не копировать его ошибки
в `expected`. Если требования и эталон противоречат друг другу, описать расхождение
до создания оценочных тестов. Если данных не хватает, перечислить недостающие
материалы; не придумывать имена объектов, методы или платформенные возможности.

## 3. Размещение файлов

Минимальное задание:

```text
assignments/my-task/
└── assignment.yaml
```

Для большого задания проверки можно разделить:

```text
assignments/my-task/
├── assignment.yaml
├── structural/
│   ├── objects.yaml
│   └── fields.yaml
└── runtime/
    ├── normal.yaml
    └── boundaries.yaml
```

`assignment.yaml` обязателен при передаче каталога. Движок берёт его `checks`,
затем YAML из `structural`, затем YAML из `runtime`; внутри каждого каталога —
по имени файла. Рекурсивный поиск в подкаталогах не выполняется.

Дополнительный YAML может содержать `checks: [...]` или одну проверку с `id`
и `type` на верхнем уровне. Название папки не задаёт тип проверки автоматически.
Все `id` должны быть уникальны во всём задании, включая дополнительные файлы.

Если передать путь к одному YAML вместо каталога, дополнительные файлы не читаются.
Не дублировать проверки одновременно в главном и дополнительном файле.

## 4. Общий формат

```yaml
name: Проверка учебного задания
checks:
  - id: order_exists
    type: element
    name: Заказ
    elementType: Документ
    points: 2
```

| Поле | Значение и правило |
|---|---|
| `name` верхнего уровня | Название задания; рекомендуется задавать явно |
| `checks` | Список проверок; объединённый набор должен содержать хотя бы одну |
| `id` | Обязательная уникальная строка, лучше латиница с `_` |
| `type` | Обязательная строка из поддержанных видов |
| `points` | Конечное неотрицательное число; по умолчанию `1` |
| `weight` | Запасное имя веса, используется при отсутствии `points`; предпочтительнее `points` |
| `skip` | `true` пропускает проверку, баллы переходят в `unavailablePoints` |
| `properties` | Для структурных проверок — ожидаемые свойства; по умолчанию `{}` |
| `library` | Необязательный точный выбор объявленной библиотеки: `provider`, `name`, `version` строками |

Поддержанные `type`: `element`, `field`, `tableSection`, `enumValue`, `module`,
`method`, `runtime`. Для регистра или запроса нет отдельного вида проверки:
метаданные регистра проверяются через `element`/`field`, а поведение через `runtime`.

Не добавлять придуманные поля `assert`, `expectedStatus`, `tolerance`, `beforeEach`,
`afterEach`, `setup`, `schemaVersion`, `requiredFields` в надежде, что движок
их исполнит. `steps` допустимо только у отдельной операции
`integration: {backend: postgres, operation: shipment-storage}`; для обычного
runtime оно не задаёт последовательность вызовов. Часть неизвестных полей
может быть проигнорирована: успешная загрузка YAML ещё не доказывает, что все
задуманные утверждения будут проверены.
`execution` заполняет runner; преподаватель и ИИ не должны задавать его сами.

### Проверка подключённой библиотеки

Без `library` проверка относится к выбранному приложению. Для прямой проверки
объекта, сигнатуры или runtime-метода библиотеки задайте её точную идентичность:

```yaml
- id: library_admin_method
  type: method
  library: {provider: e1c, name: БазаЗнаний, version: "1.1.1"}
  module: ПраваБиблиотеки
  namespace: ПраваДоступа
  name: ЭтоАдминистраторБиблиотеки
  returnType: Булево
  points: 1
```

Тот же `library` можно указать у `runtime`; `target.module`, `target.namespace`
и `target.method` тогда ищутся в исходниках библиотеки. Версию пишите строкой
в кавычках. Селектор должен совпасть с зависимостью в `Проект.yaml` по всем
трём полям; произвольную одноимённую библиотеку движок не подставляет. В
`result.json` проверяемым проектом остаётся приложение, а общий `sourceHash`
включает исходники библиотеки. Интеграционный SQL runtime для библиотечных
методов пока не поддержан; он даёт `UNSUPPORTED`.

## 5. YAML и значения

- UTF-8, отступы пробелами; для переносимости использовать два пробела.
- Повторяющиеся ключи, якоря `&...`, ссылки `*...` и YAML merge не поддержаны.
- Все ключи отображений должны быть строками.
- Булевы входы runtime писать `true`/`false`, пустое значение — `null`.
  Строки `"Истина"` и `"Ложь"` во входах runtime не заменяют булевы значения.
- Числа писать без кавычек и с точкой: `2`, `0.125`, `12.5`.
- Пустой список — `[]`, пустая структура — `{}`. Они не взаимозаменяемы.
- Строковые идентификаторы, номера и коды лучше заключать в кавычки: `"001"`.
- Не использовать `NaN`, бесконечности и произвольные YAML-теги.
- `ДатаВремя` во входах runtime — строка `"2026-09-27T12:34:56"`, без часового
  пояса и долей секунды. Проверяется календарная корректность.
- `Время` во входах runtime — строка `"09:30"`, `"09:30:40"` или
  `"09:30:40.123"`. Часы, минуты и секунды проверяются по диапазонам.
- `null` допустим только для nullable-типа. Пустая строка не означает `null`.

Нормализация `Истина`/`Ложь` существует для метаданных и структурных `properties`,
но не распространяется на все поля задания. Поэтому генератору лучше везде
использовать стандартные YAML `true`/`false`.

## 6. Структурные проверки

### 6.1. Наличие и вид объекта — `element`

Поля: `name`, необязательные `elementType`, `properties`, `exists`.
По умолчанию проверяется наличие. `exists: false` требует отсутствия.

```yaml
name: Объекты
checks:
  - id: order_exists
    type: element
    name: Заказ
    elementType: Документ
    points: 1
  - id: unwanted_catalog_absent
    type: element
    name: СтарыйСправочник
    exists: false
    points: 1
```

В `elementType` используются значения YAML проекта: `Документ`, `Справочник`,
`Перечисление`, `РегистрСведений`, `РегистрНакопления` и другие виды метаданных.
Это проверка строкового свойства, а не обещание runtime-поддержки всех этих видов.

### 6.2. Реквизит, ресурс, измерение — `field`

Поля: `element`, `field`, необязательные `expectedType`, `collection`,
`properties`, `exists` и сокращения свойств из раздела 7.

```yaml
name: Реквизиты и ресурсы
checks:
  - id: order_client
    type: field
    element: Заказ
    field: Клиент
    expectedType: Контрагенты.Ссылка?
    points: 1
  - id: goods_sum
    type: field
    element: Заказ.Товары
    field: Сумма
    expectedType: Число
    scale: 2
    points: 1
  - id: stock_quantity_resource
    type: field
    element: РегистрТовары
    collection: Ресурсы
    field: Количество
    expectedType: Число
    points: 1
  - id: stock_warehouse_dimension
    type: field
    element: РегистрТовары
    collection: Измерения
    field: Склад
    expectedType: Склады.Ссылка?
    points: 1
```

`collection` по умолчанию — `Реквизиты`. Для других коллекций указывай точное
название из YAML, например `Ресурсы`, `Измерения`, `Константы`.
Неизвестное имя коллекции даёт `ERROR`. Если одно имя есть одновременно в
`Реквизиты` и другой коллекции, укажи `collection` явно: без него проверка
получит `ERROR` как неоднозначная.

`expectedType` — точный тип с учётом nullable и массива. Формат структурных типов:
`Строка`, `Число`, `Булево`, `Время`, `ДатаВремя`, `ИмяПеречисления`, `Объект.Ссылка`,
`Объект.Ссылка?`, `Массив<Объект.Ссылка?>`, квалифицированные ссылки.
Union записывается без пробелов: `Отгрузка.Ссылка|ПоступлениеТоваров.Ссылка|?`.
Порядок вариантов такого union нормализуется. Самостоятельная `?` — не тип.

Грамматика `expectedType` уже, чем грамматика runtime-контрактов:
не задавать здесь `Заказ.Товары`, `Заказ.Объект` или `Соответствие<...>`.
Для полей с неявным системным типом структурная проверка смотрит YAML как есть;
например, runtime дополнит `Наименование` типом `Строка`, но это не гарантирует
наличия свойства `Тип` у такого поля в структурной модели.

`exists: false` можно использовать для запрещённого реквизита. Однако если
отсутствует сама родительская ТЧ, проверка поля `Объект.ТЧ` завершится FAIL:
отсутствие родителя лучше проверять отдельной проверкой.

### 6.3. Табличная часть — `tableSection`

```yaml
name: Табличные части
checks:
  - id: order_goods
    type: tableSection
    element: Заказ
    name: Товары
    points: 1
```

Проверяются наличие и заданные `properties`. Реквизиты ТЧ проверять отдельными
`field` с `element: Заказ.Товары`, а не сравнением всего массива `Реквизиты`.

### 6.4. Элемент перечисления — `enumValue`

```yaml
name: Статусы заказа
checks:
  - id: status_new
    type: enumValue
    element: СтатусЗаказа
    name: Новый
    points: 1
```

Это поиск элемента перечисления по `Имя`, затем проверка указанных свойств.
Если задание требует явное `ПоУмолчанию: true` в YAML, добавь
`properties: {ПоУмолчанию: true}`. В приведённом архиве у элемента `Новый`
это свойство явно не задано, поэтому пример проверяет только наличие.

### 6.5. Модуль — `module`

```yaml
name: Модуль объекта
checks:
  - id: person_module
    type: module
    module: ФизическиеЛица.Объект
    points: 1
```

Для `module` проверяется наличие по имени и, при необходимости, точному
`namespace`. `exists: false` требует отсутствия модуля. `properties` для
модуля не проверяются.

### 6.6. Метод и его сигнатура — `method`

```yaml
name: Методы
checks:
  - id: person_before_write
    type: method
    module: ФизическиеЛица.Объект
    name: ПередЗаписью
    annotations: [Обработчик]
    parameterCount: 2
    points: 1
  - id: fio_signature
    type: method
    module: ФизическиеЛица.Объект
    name: СформироватьФИО
    returnType: Строка
    parameterCount: 3
    parameters:
      - {name: ФамилияЧеловека, type: Строка}
      - {name: ИмяЧеловека, type: Строка}
      - {name: ОтчествоЧеловека, type: Строка}
    points: 1
```

`annotations` — требуемые аннотации без `@`; дополнительные аннотации не запрещаются.
`parameters` — список требуемых имён и типов. Параметры ищутся **по имени**:
эта структурная проверка не проверяет их позицию. `parameterCount` отдельно
проверяет общее количество. `returnType` сравнивается с текстом типа из индекса;
нормализация union для него и `parameters[].type` не выполняется загрузчиком задания.
Для отсутствия возвращаемого типа отдельного надёжного утверждения нет:
`returnType: null` не означает «обязателен метод без результата».

Индекс методов лексический. Наличие метода не доказывает правильность его тела.
`exists: false` для `method` требует отсутствия метода. Если индекс выбранного
модуля неполон, отсутствие метода получает `UNSUPPORTED`, а не `FAIL` или `PASS`.
Для `module` и `method` можно указать точный `namespace`; без него одинаковые
имена модулей остаются неоднозначными. При несовпадении сигнатуры результат
содержит причину и, где применимо, `expected` и `actual`.

## 7. Свойства и их сокращения

`properties` проверяет только перечисленные свойства объекта/поля.
Не требуется, чтобы у объекта отсутствовали все прочие свойства.
Но значение каждого указанного свойства сравнивается целиком. Неявные
платформенные умолчания свойств автоматически не достраиваются: отсутствие
ключа в YAML не равнозначно явному `false`, `0` или пустой строке.

```yaml
name: Свойства документа
checks:
  - id: receipt_basis
    type: element
    name: ПоступлениеТоваров
    elementType: Документ
    properties:
      СозданиеНаОсновании: [Отгрузка.Ссылка]
    points: 1
```

Здесь список оснований должен совпасть полностью. Это не утверждение
«содержит хотя бы Отгрузка.Ссылка». Для вложенного отображения также требуется
совпадение его полного значения, а не только вложенных ключей из ожидания.

| Сокращение на уровне проверки | Ключ внутри `properties` |
|---|---|
| `scale` | `ДлинаДробнойЧасти` |
| `precision` | `ДлинаЦелойЧасти` |
| `length` | `МаксимальнаяДлина` |
| `visibility` | `ОбластьВидимости` |
| `default` | `ЗначениеПоУмолчанию` |
| `min` | `МинимальноеЗначение` |
| `max` | `МаксимальноеЗначение` |
| `hierarchical` | `Иерархический` |
| `unique` | `Уникальность` |
| `periodicity` | `Периодичность` |

Сокращение механически задаёт именно этот ключ. Оно не понимает альтернативные
имена свойств. Например, `length: 13` проверяет `МаксимальнаяДлина`, а не `Длина`.
Если в YAML есть `Длина: 13`, использовать `properties: {Длина: 13}`.
Не смешивать сокращение и его полный ключ с разными значениями: сокращение
перезапишет полный ключ при загрузке задания.

## 8. Имена и порядок

| Что сравнивается | Учитывается ли порядок |
|---|---|
| Реквизиты объекта через отдельные `field` | Нет, поиск по имени |
| Реквизиты ТЧ через отдельные `field` | Нет, поиск по имени |
| Табличные части через отдельные `tableSection` | Нет, поиск по имени |
| Ключи отображений в `expected` | Нет |
| Строки ТЧ, массивы результатов | Да |
| События в `calls` | Да |
| Входные аргументы `args` | Да, порядок параметров метода |
| Параметры структурного `method.parameters` | Поиск по имени, позиция не проверяется |
| Список, заданный целиком в `properties` | Да |

Для структурных элементов можно указать `Продажи::Заказ`, а для поля его ТЧ —
`Продажи::Заказ.Товары`. Префикс поставщика/проекта в структурном поиске элементов
не обрабатывается как в runtime-типах: использовать namespace из `inspect`.

В runtime целевой модуль выбирается по `target.module`; при необходимости добавить
`target.namespace` с точным namespace из модели. Квалификация в самом имени
`target.module` вместо отдельного поля не является поддержанным способом поиска.

Квалифицированные **типы** runtime поддерживают `Подсистема::Объект.Ссылка`
и `Поставщик::Проект::Подсистема::Объект.Ссылка`. Это отдельная возможность,
которую нельзя переносить автоматически на поля выбора структурного модуля.

UUID не нужны в обычных критериях: не проверять `Ид`, если задание не требует
именно конкретный UUID. Не требовать определённого пути файла вместо имени объекта.

## 9. Runtime: общая схема

| Поле | Назначение |
|---|---|
| `target.module` | Имя модуля, например `Заказ.Объект` |
| `target.method` | Имя вызываемого метода |
| `target.namespace` | Необязательный точный namespace для выбора модуля |
| `args` | Список аргументов; количество должно совпасть с сигнатурой; по умолчанию `[]` |
| `context` | Начальные поля объекта; только для модуля с именем `*.Объект` |
| `observe` | Непустой список уникальных полей контекста для сравнения |
| `expected` | Полное ожидаемое значение результата в соответствующей форме |
| `timeout` | По умолчанию `5s`; число секунд должно быть больше 0 и не больше 30 |
| `mocks` | Только `objects`, `registers`, `queries` |
| `captureCalls` | Записывать вызовы подставных API; по умолчанию `false` |
| `observeCallArguments` | Глобальная проекция аргументов событий при `captureCalls: true` |
| `captureException` | Перехват исключения объектного метода без результата |
| `runtimeDateTime` | Поле `ДатаВремя`, которое runtime заполняет перед вызовом |

Текущий адаптер требует явно типизированные параметры без значений по умолчанию.
Методы с результатом должны иметь явный возвращаемый тип. Для метода без результата
нужен объектный `context`, даже если пустой: `{}`.

`observe` выбирает поля только верхнего уровня: `Товары` допустимо,
`Товары.Количество` — нет. Строки наблюдаемой ТЧ сравниваются со всеми полями,
включая умолчания полей, не заданных во входе.

Для изоляции каждый обычный runtime-тест получает новый контейнер и новый контекст.
Обычный runtime-тест описывает один вызов; произвольной последовательности
`steps` и общего состояния между разными тестами нет. Отдельная интеграционная
операция отгрузки имеет свой ограниченный формат `steps`.

### 9.1. Чистый метод

Без `context` в `expected` находится само возвращаемое значение.


```yaml
name: 'Пример: fio_trim'
checks:
- id: fio_trim
  type: runtime
  target:
    module: ФизическиеЛица.Объект
    method: СформироватьФИО
  args:
  - ' Иванов '
  - ' Иван '
  - ' Иванович '
  expected: Иванов Иван Иванович
  timeout: 5s
  points: 1.0
```

### 9.2. Аргумент-массив строк

`args: [[]]` — один аргумент, пустой массив. `args: []` — нет аргументов.

```yaml
name: 'Пример: several_rows'
checks:
- id: several_rows
  type: runtime
  target:
    module: ЗаказФормаОбъекта
    method: РассчитатьИтоги
  args:
  - - Количество: 2
      Цена: 100
      Сумма: 200
    - Количество: 3
      Цена: 50
      Сумма: 150
  expected:
    Строк: 2
    Товаров: 5
    Сумма: 350
  points: 1.0
```

### 9.3. Объектный метод без результата

`context` — входное состояние; `expected` — наблюдаемое состояние после вызова.

```yaml
name: 'Пример: person_before_write'
checks:
- id: person_before_write
  type: runtime
  target:
    module: ФизическиеЛица.Объект
    namespace: CRM
    method: ПередЗаписью
  context:
    Фамилия: ' Иванов '
    Имя: ' Иван '
    Отчество: ' Иванович '
    ФИО: устаревшее значение
    Телефон: ' +7 999 123-45-67 '
    Почта: ' ivan@example.com '
  args:
  - {}
  - {}
  observe:
  - ФИО
  - Телефон
  - Почта
  expected:
    ФИО: Иванов Иван Иванович
    Телефон: +7 999 123-45-67
    Почта: ivan@example.com
  points: 1.0
```

### 9.4. Отдельный интеграционный режим

У проверки с `type: runtime` можно указать
`integration: {backend: postgres, operation: sql-smoke}` или
`integration: {backend: postgres, operation: shipment-storage}`. Запуск требует
`--integration`, локального Docker и настроенного PostgreSQL-окружения.
Это два фиксированных контракта, а не общий способ вызвать метод проекта:
`target`, `args`, `context`, `mocks` и `runtimeDateTime` здесь не принимаются.
`shipment-storage` использует собственные `stock`, `steps` и `expected`;
формат и ограничения приведены в [документе адаптера](shipment-storage.md) и
[готовом задании](../assignments/poc-shipment-storage/assignment.yaml).
Для обычных учебных методов используйте схему выше.

## 10. Fake-ссылки

`mocks.objects` задаёт тип ссылки, затем ID и типизированный снимок объекта.
В этом примере склад заменяется, а сумма 23 переносится без пересчёта 2 × 10.
Второй ID содержит отличающиеся данные; нужен также отдельный тест его загрузки.

```yaml
name: 'Пример: receipt_one'
checks:
- id: receipt_one
  type: runtime
  target:
    module: ПоступлениеТоваров.Объект
    method: ПриСозданииНаОсновании
  context:
    Склад:
      Идентификатор: old-warehouse
    Товары: []
  args:
  - Идентификатор: shipment-a
  mocks:
    objects:
      Отгрузка.Ссылка:
        shipment-a:
          Склад:
            Идентификатор: warehouse-a
          Товары:
          - Номенклатура:
              Идентификатор: product-a
            Количество: 2
            Цена: 10
            Сумма: 23
        shipment-b:
          Склад:
            Идентификатор: unused-warehouse
          Товары:
          - Номенклатура:
              Идентификатор: unused-product
            Количество: 99
            Цена: 99
            Сумма: 1
  observe:
  - Склад
  - Товары
  expected:
    Склад:
      Идентификатор: warehouse-a
    Товары:
    - Номенклатура:
        Идентификатор: product-a
      Количество: 2
      Цена: 10
      Сумма: 23
  points: 1.0
```

## 11. Регистры и журнал вызовов

`mocks.registers` создаёт подставные API, а не реальную базу. При `captureCalls: true`
результат без возвращаемого значения имеет форму `{context: состояние, calls: события}`.
`observeCallArguments` ограничивает ключи args во всех событиях.

```yaml
name: 'Пример: price_after_write'
checks:
- id: price_after_write
  type: runtime
  target:
    module: Номенклатура.Объект
    method: ПослеЗаписи
  context:
    Ссылка:
      Идентификатор: product-1
    Цена: 125.5
  args:
  - {}
  - {}
  observe:
  - Ссылка
  - Цена
  mocks:
    registers:
    - РегистрЦеныНоменклатуры
  captureCalls: true
  observeCallArguments:
  - Номенклатура
  - Цена
  - Замещать
  expected:
    context:
      Ссылка:
        Идентификатор: product-1
      Цена: 125.5
    calls:
    - owner: РегистрЦеныНоменклатуры
      method: Фильтр.Установить
      args:
        Номенклатура:
          Идентификатор: product-1
    - owner: РегистрЦеныНоменклатуры
      method: ДобавитьЗапись
      args:
        Номенклатура:
          Идентификатор: product-1
        Цена: 125.5
    - owner: РегистрЦеныНоменклатуры
      method: Записать
      args:
        Замещать: false
  points: 1.0
```

## 12. Runtime-дата

`runtimeDateTime: Дата` заполняет поле ДатаВремя внутри Docker UTC-временем
и сохраняет независимый снимок до обработчика. Поле нельзя одновременно задавать
в начальном context. В expected используется маркер `__runtimeDateTime__`.
Не вычислять ожидаемое текущее время на хосте.

```yaml
name: 'Пример: movements_one'
checks:
- id: movements_one
  type: runtime
  target:
    module: Отгрузка.Объект
    method: ПослеЗаписи
  context:
    Ссылка:
      Идентификатор: shipment-1
    Склад:
      Идентификатор: warehouse-1
    Товары:
    - Номенклатура:
        Идентификатор: product-1
      Количество: 5
  args:
  - {}
  - {}
  observe:
  - Ссылка
  - Дата
  - Склад
  mocks:
    registers:
    - РегистрТовары
  captureCalls: true
  expected:
    context:
      Ссылка:
        Идентификатор: shipment-1
      Дата: __runtimeDateTime__
      Склад:
        Идентификатор: warehouse-1
    calls:
    - owner: РегистрТовары
      method: Фильтр.Установить
      args:
        Регистратор:
          Идентификатор: shipment-1
    - owner: РегистрТовары
      method: ДобавитьЗапись
      args:
        Период: __runtimeDateTime__
        ВидЗаписи: Расход
        Номенклатура:
          Идентификатор: product-1
        Количество: 5
        Склад:
          Идентификатор: warehouse-1
    - owner: РегистрТовары
      method: Записать
      args:
        Замещать: true
  runtimeDateTime: Дата
  points: 1.0
```

## 14. Подробные правила mocks

### Fake-объекты

Каждый `ЗагрузитьОбъект()` создаёт новый снимок. Изменение загруженного объекта
не записывает его обратно. Наборы ссылок не переходят между тестами.
Неизвестный ID при загрузке даёт ERROR; пустой объект вместо ошибки не подставляется.
Тип в `mocks.objects` должен иметь вид `<Объект>.Ссылка`, а его значение —
отображение строковых ID в объекты. Поля снимка проверяются по YAML-контракту.

### Регистры

Генерируются `НаборЗаписей`, `Фильтр.Установить`, `ДобавитьЗапись`, `Записать`.
События содержат `owner`, `method`, `args`; их порядок и полный состав значимы.
`captureCalls` фиксирует подставные API, а не все произвольные вызовы студента.
`observeCallArguments` действует на аргументы всех событий, не удаляет события
и не фильтрует их по владельцу. Без него проверяются все аргументы.

Регистры сведений: поддержаны непериодические и периодичность `Момент`.
Регистры накопления: поддержан вид `Остатки`, период записи `ДатаВремя`,
вид записи `Приход`/`Расход` и фильтр по типизированному регистратору.
Поддержанная запись: `Записать(Замещать: Булево = Истина)`;
перегрузка с `ПараметрыЗаписи` не реализована. `Обороты` не поддержаны.

Журнал подтверждает формирование записей и вызовы. Он не подтверждает хранение
движений, очистку по регистратору, активность, пересчёт остатков и транзакции.

### Запросы

Каждый элемент `mocks.queries` требует `text`, `fields`, `rows` и одно из
`parameterType` или `parameterTypes`:

| Поле | Назначение |
|---|---|
| `text` | Текст внутри `Запрос{...}`, без внешней оболочки |
| `fields` | Имена полей строки результата и их типы |
| `rows` | Подставные строки; `[]` означает пустой результат |
| `parameterType` | Тип единственного выражения `%{...}` (прежний формат) |
| `parameterTypes` | Список типов по порядку `%{...}` или `%Имя`; `[]` для запроса без параметров |

Пробелы и комментарии вне строк не влияют на сопоставление; строковые литералы
и выражения значимы. Для читаемости `text` можно записать через YAML `|-`.
Текст нужно брать из метода, а не пересказывать запрос.

Поддержаны запросы без параметров, `%Имя` и `%{...}` без вложенных фигурных
скобок. Число типов в `parameterTypes` должно совпадать с числом параметров;
для запроса без них укажите `parameterTypes: []`. Для этого формата
событие `Создать` содержит `Параметр1`, `Параметр2`, ...; прежний
`parameterType` сохраняет имя `Параметр`. У запроса без параметров `args: {}`.
Например:

```yaml
mocks:
  queries:
  - text: 'ВЫБРАТЬ %{Начало} КАК Начало, %{Склад} КАК Склад'
    fields: {Количество: Число}
    rows: [{Количество: 5}]
    parameterTypes: [ДатаВремя, Склад.Ссылка]
```

Реальный пример `parameterTypes: []` и `%Стадия` находится в
[задании ДемоСРМ](../assignments/demo-srm-stages/assignment.yaml).

Каждому литералу нужен один совпадающий контракт. Неиспользованный,
отсутствующий и неоднозначный контракты дают UNSUPPORTED. Имена событий
`query0`, `query1`, ... соответствуют
индексу контракта в `mocks.queries`.

Фабрика вычисляет каждое исходное выражение в Script runtime.
`Выполнить()` возвращает заданные строки; SQL/XBQL не исполняется.
Последующие преобразования коллекций выполняет сам Script runtime.
Не ожидать автоматического расчёта остатков из массива движений.

## 15. Входные типы runtime

| Тип | Как задать вход |
|---|---|
| `Строка` | YAML-строка |
| `Число` | Конечное YAML-число, не строка и не булево значение |
| `Булево` | `true` или `false` |
| `Время` | `"HH:MM"`, `"HH:MM:SS"` или `"HH:MM:SS.SSS"`; диапазон до `23:59:59.999` |
| `ДатаВремя` | `"YYYY-MM-DDTHH:MM:SS"` |
| Перечисление | `Новый` или `СтатусЗаказа.Новый` |
| Ссылка | `{Идентификатор: "product-1"}` |
| Nullable | `null` либо значение основного типа |
| Массив | Список значений соответствующего типа |
| `ЧитаемыйМассив<T>` | YAML-список; runtime передаёт типизированный `Массив<T>`, сохраняя читаемую сигнатуру |
| `Обходимое<T>` | YAML-список; runtime создаёт `Массив<T>`, включая типизированный пустой список |
| Простая структура того же модуля | Отображение полей объявленной XBSL-структуры; поддержаны обычные `пер` типов `Строка`, `Число`, `Булево` |
| Строка ТЧ | Отображение имён реквизитов в значения |
| `Объект`/`Данные` | Поля сгенерированного YAML-контракта |
| `ПараметрыЗаписи` | `{}` — пустой поддержанный контракт |
| Union | Явный вариант `{type: ..., value: ...}`, если вход неоднозначен |

Локальные структуры копируются из исходного модуля только по необходимости.
Аннотации, умолчания, методы структуры, другие типы полей и перенос через
границы модулей пока дают `UNSUPPORTED`. Проверенный пример —
[сумма стоимости товаров](../assignments/practical-total-cost/assignment.yaml);
контракт и результаты описаны в [отчёте №27](tasks/027-practical-total-cost.md).
`ЧитаемыйМассив<T>` с поддержанным элементом также сериализуется как результат
в обычный JSON-массив. Проверенный пример —
[представления товаров в наличии](../assignments/practical-stock-presentations/assignment.yaml);
точный формат строк и границы — в [отчёте №28](tasks/028-practical-stock-presentations.md).

Фрагмент входного варианта union:

```yaml
type: Отгрузка.Ссылка
value: {Идентификатор: shipment-1}
```

Тег должен совпасть с одним из вариантов типа параметра.
В `expected` находится обычное сериализованное значение: тег union выбирает
**входной** тип, а не добавляет выходную оболочку автоматически.

Структуры передаются именованными аргументами, поэтому порядок ключей не важен.
Неизвестные поля отклоняются. Пропущенные получают умолчания типа/метаданных;
для важных критериев лучше задавать значения явно.
В `Ссылка` поддержан только строковый `Идентификатор`.

`args` содержит данные, а не вычисляемые XBSL-выражения.
Входы `Дата`, `Момент`, соответствия пока не преобразуются из задания, даже если
эти типы встречаются в API или допустимы как возвращаемые значения.
`Ууид` распознаётся в метаданных, но пока не создаётся как вход runtime:
проверка `СоздатьИлиОбновить` из четвёртого xdump даёт `UNSUPPORTED`.
`Соответствие` не означает, что любой YAML-объект можно передать любому параметру.

## 16. Все формы expected

| Вызов | Значение expected |
|---|---|
| Без context, метод с результатом | Сам результат |
| С context, метод без результата | Наблюдаемое состояние |
| С context, метод с результатом | `{return: результат, context: состояние}` |
| Без результата, с context и captureCalls | `{context: состояние, calls: события}` |
| С результатом, с context и captureCalls | `{context: {return: результат, context: состояние}, calls: события}` |
| Без результата, с context и captureException | `{result: состояние, exception: null_или_описание}` |
| Без результата, с context, оба флага | `{result: {context: состояние, calls: события}, exception: null_или_описание}` |

`context` внутри `expected` — состояние после вызова, ограниченное `observe`,
если оно задано. Без `observe` нужно ожидать весь объект, включая `Ссылка` и
умолчания. Для устойчивости обычно лучше задать проекцию.

Фрагмент результата объектного метода с возвращаемым значением:

```yaml
expected:
  return: 123
  context:
    Итог: 123
```

С журналом вызовов он принимает форму:

```yaml
expected:
  context:
    return: 123
    context: {Итог: 123}
  calls: []
```

Это схемы оболочек, а не готовые тесты конкретного метода.
Вложенный `context` во втором примере соответствует текущей реализации.

`captureException: true` поддержан только для объектного метода без результата.
Без этого флага необработанное исключение даёт ERROR. С ним исключение становится
частью результата, который сравнивается:

```yaml
expected:
  result:
    Товары: []
  exception:
    type: Std::IllegalStateException
    message: Описание ошибки
```

Это тоже схема. `type` — подтверждённое имя типа runtime, не обязательно имя
класса в XBSL. Сообщение сравнивается точно, без регулярных выражений и подстрок.
При отсутствии исключения требуется `exception: null`.

## 17. Точное сравнение и умолчания

Runtime сравнивает полное ожидаемое и фактическое JSON-совместимое значение
средствами SBSL. Порядок ключей отображений не важен. Состав ключей, значения
и порядок элементов массивов важны.

Нет встроенного приблизительного сравнения чисел, допуска по времени,
регулярных выражений, подстрок, «содержит хотя бы» и рекурсивной проекции полей.
Строкой `"2"` нельзя подменять число `2`. Не округлять ожидания без требования
и соответствующего поведения метода.

`observe` выбирает поля верхнего уровня. В наблюдаемой строке ТЧ нужно ожидать
все сериализованные поля, в том числе умолчания пропущенных входных реквизитов.
Например, при входе `{Количество: 5}` строка может содержать также
`Номенклатура: null`, `Цена: 0`, `Сумма: 0`. Их нельзя произвольно убрать из expected.
Конкретные умолчания брать из YAML-контракта и подтверждённого поведения runtime.

## 18. Как выбирать сценарии и баллы

До генерации составить матрицу «требование → вход → ожидаемый эффект → id → баллы».
Она должна показать, что проверено автоматически, а что движок пока не поддерживает.

Обычно нужны следующие независимые сценарии:

1. Обычный случай с явными значениями.
2. Пустой набор, пустая строка или null — только если контракт их допускает.
3. Несколько разных строк: перестановка, неверная ссылка и повтор первой строки
   должны стать заметны.
4. Дробные значения без случайных чисел и неподтверждённого округления.
5. Непустой начальный context для выявления ошибочной очистки/дописывания.
6. Два fake-ID и отдельный вызов каждого.
7. Условия меньше, равно и больше порога бизнес-правила.
8. Ожидаемый отказ с captureException, если этого требует задание.

Не требовать проверки отрицательных чисел, уникальности, пересчёта, очистки
и других правил, которых нет в учебном задании.
Не превращать особенности неправильного студенческого решения в эталон.

Одна проверка получает весь вес или 0. Частичных баллов внутри проверки нет.
Для раздельной оценки независимых эффектов создать отдельные сценарии с узким
observe. Это будут новые независимые вызовы, а не продолжение одного объекта.
Баллы за множество мелких свойств не должны необоснованно перевешивать главное
поведение задания. Общую сумму сверить с заданным бюджетом.

### Оценочные тесты и контроль самого движка

В оценочном наборе каждый expected описывает правильное поведение.
Правильная реализация должна проходить все доступные критерии.

Отдельно для контроля движка можно намеренно изменить ожидаемые склад, товар,
количество, цену, сумму и порядок: такие проверки должны дать FAIL.
Не включать заведомо неверные ожидания в обычное задание студента.
Неизвестный fake-ID и неподдержанный контракт также проверять отдельно как
инфраструктурные случаи. В YAML нет `expectedStatus`: нужные статусы проверяются
внешним тестовым кодом или по отчёту вручную.

## 19. Статусы и оценка

| Статус | Значение | Баллы |
|---|---|---|
| PASS | Критерий выполнен | Полный вес |
| FAIL | Структура или значение не совпали | 0, вес входит в maxScore |
| ERROR | Ошибка конфигурации, исполнения или проверки | Вес исключён из maxScore |
| TIMEOUT | Превышен лимит | Вес исключён из maxScore |
| UNSUPPORTED | Возможность/окружение не поддержаны | Вес исключён из maxScore |
| SKIPPED | Задан skip | Вес исключён из maxScore |

`score` — набранные баллы; `maxScore` — доступный максимум;
`unavailablePoints` — вес ERROR, TIMEOUT, UNSUPPORTED и SKIPPED.
Итог `failed` имеет приоритет при FAIL. Иначе неполный набор даёт
`incomplete`, полностью успешный — `passed`.
ERROR сам по себе не доказывает ошибку студента: нужно прочитать сообщение и,
если возможно, повторить проверку после исправления среды или теста.
Не выдавать incomplete за подтверждённое выполнение всего задания.

Сценарии продолжаются после ошибки отдельной проверки. Ошибка загрузки всего
задания — например, повтор id или неправильный YAML — может остановить запуск
до выполнения сценариев.

## 20. Ограничения, обязательные для ИИ

- Подключаются достижимые методы того же модуля, статические вызовы внешних
  модулей и объявленных библиотек с учётом видимости. Индексатор строит дерево
  выражений поддерживаемого подмножества XBSL, но не является полным
  компилятором языка; неизвестные динамические вызовы остаются недоступными.
- Генерируются необходимые YAML-контракты документов, справочников, перечислений
  и поддержанных моков. Это не вся платформа.
- Поддержаны конструкторы `новый Объект.Товары(...)`, квалифицированные варианты
  и поддержанные generic-контейнеры. Разрешённые квалифицированные токены типов
  сокращаются для SBSL; прочая бизнес-логика не переписывается.
- Неизвестные/неоднозначные типы, конфликты кратких имён и циклы могут дать
  UNSUPPORTED. Поддержаны локальные объявления, `как` и алиасы импорта для
  разрешаемых проектных типов; прочие формы и динамические типы не поддержаны.
- Параметры записи — пустые структуры; флаги и другая семантика не моделируются.
- В обычном runtime fake-ссылки не сохраняют объект, регистры не хранят движения
  между тестами, а подставные запросы не выполняют XBQL.
- Отдельный opt-in `shipment-storage` хранит документы и движения в одноразовой
  PostgreSQL для ограниченного сценария отгрузки. Общие XBQL, виртуальные таблицы,
  платформенные транзакции и объектный API не реализованы.
- В обычном runtime ручной вызов ПослеЗаписи не означает реальную запись документа.
- В исходном Dvizhok.xdump у ПоступлениеТоваров нет ПослеЗаписи:
  не создавать тест несуществующего обработчика прихода.
- Интерфейс, сервер приложения и права реального пользователя в этом runtime
  не проверяются. Для них нужны отдельные UI/интеграционные инструменты.
- Наличие API в полной платформе не доказывает поддержку API этим адаптером.

## 21. Проверка сгенерированных файлов

### 21.1. Загрузить настоящим загрузчиком

Из корня репозитория:

```bash
python3 - <<'PY'
from element_test.assignment import load_assignment
assignment = load_assignment('assignments/my-task')
print('Проверок:', len(assignment['checks']))
print('Баллов:', sum(check['points'] for check in assignment['checks']))
PY
```

Это проверяет загрузку, повтор ключей/id, веса и часть типов. Это не полная
валидация всех полей, бизнес-ожиданий и runtime-совместимости.

### 21.2. Выполнить на эталоне

```bash
bin/element-test test \
  --project Dvizhok.xdump \
  --assignment assignments/my-task \
  --output result/my-task
```

Поддержаны каталог проекта, ZIP, TAR, TAR.GZ и XDUMP. Отчёт нельзя создавать внутри
исходного каталога проекта. Runtime требует Docker и настроенный executor
для режима совместимости. Образ нужно установить заранее: runner использует
`--pull never`. Команды подготовки окружения — в README.

`result.json` содержит детальные исходы, `report.html` — их представление.
Сверить expected и actual, а не только общий score.
Коды CLI: 0 — passed; 1 — failed; 2 — incomplete или ошибка входа/окружения.

### 21.3. Проверить чувствительность и покрытие

На отдельной копии ожиданий или доверенного fixture вне оригинального архива
сделать контролируемую ошибку: поменять значение, удалить поле, переставить строки.
Убедиться, что критерий перестаёт проходить. Не запускать студенческий код на хосте.
Не возвращать испорченные ожидания в оценочное задание.

Сверить все требования с матрицей критериев. Неподдержанные пункты описать отдельно,
а не выдавать их отсутствие за успешно выполненную автоматическую проверку.

## 22. Частые ошибки генератора

| Ошибка | Правильный подход |
|---|---|
| type: document или query | Поддержанный type; запрос — runtime с mock |
| name вместо field у реквизита | type: field, element, field |
| Имя ТЧ без владельца | element: Заказ.Товары |
| Сравнение массива Реквизиты целиком | Отдельный field на требуемое имя |
| args: [] для одного пустого массива | args: [[]] |
| args как отображение имён параметров | Список в порядке сигнатуры |
| UUID вместо fake-ID | {Идентификатор: "shipment-1"} |
| Оболочка context у чистого метода | Сам возвращаемый результат |
| Часть полей строки ТЧ в expected | Все сериализованные поля |
| observe: [Товары.Количество] | observe: [Товары] и полные строки |
| Дата вычислена на хосте | runtimeDateTime и маркер снимка |
| Пересчёт суммы при требовании переноса | Ожидать готовую сумму |
| captureCalls без ожидаемого calls | Полная оболочка журнала |
| Непроверенное имя XBSL-исключения в expected | Подтверждённое имя типа runtime |
| Реальные остатки ожидаются от mocks.queries | Задать rows, явно обозначить непроверенный XBQL |
| expectedStatus: ERROR | Инфраструктурный контроль отдельно |
| Неподдержанная проверка замаскирована skip | Явно описать ограничение и влияние на оценку |
