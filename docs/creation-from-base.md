# Создание на основании: прямой standalone контракт №37

Четыре `ПриСозданииНаОсновании` и два helper вызываются как явные targets
неизменённого Dvizhok.xdump. YAML `СозданиеНаОсновании` не запускает события:
исполняется только указанный исходный метод и его замыкание. Python разрешает
декларации и fixtures, Script выполняет загрузки, циклы, суммирование и перенос,
SBSL сравнивает независимо заданный expected. Expected отсутствует в IR/driver.

`storage.initial` задаёт реальные объекты с полным namespace/owner и native UUID.
Тип `Движок::Движок::Продажи::Заказ.Ссылка` разрешается по идентичности проекта.
Загрузка читает detached экземпляр из той же сессии; memory и PostgreSQL
используют общий адаптер. Native nullable/union сохраняются. Наблюдаемые
union-ссылки представлены `{type: Финансы::СчетНаОплату.Ссылка, value: {...}}`:
адаптация транспортных native JSON-тегов использует декларации сгенерированных
типов. Снимки sequence и проб до transport-разбора сохраняются как JSON-строки,
поэтому повторная native десериализация не стирает ветвь union. Верхний storage
передаёт исходные сохранённые JSON-значения, без потери type-тегов. Одинаковые UUID разных owners не теряют тип. Это техническое представление
наблюдений; входной `{type, value}` выбирает ветвь union до исполнения.

Объектный target требует `context`. Его полный снимок сохраняет реквизиты и
таблицы. Для void-helper обязательно `snapshotArgs: true`: `actual.result.args`
показывает изменённый второй аргумент, а первый — исходные строки.
Для возвращающего helper снимок `{result, args}` содержит весь новый объект.
Storage оборачивает наблюдение в `{result, storage}`. Аудит PostgreSQL заменяет
верхний storage фактической выборкой БД, сортированной по type/id. Служебное
`sql:commit` публикации начального состояния не является вызовом Записать
исходного документа. Отсутствие сохранения проверяется полным состоянием БД.

Новый `Отгрузка.Объект` в объявленном адаптере получает native defaults:
нулевой UUID Ссылка, Дата `0001-01-01T00:00:00`, пустой Номер, nullable Склад и
отдельный пустой массив Товары. Два создания могут иметь одинаковый нулевой UUID,
но являются независимыми экземплярами и массивами. Случайный ID, автонумерация,
ограничения всех YAML-реквизитов и платформенный жизненный цикл не имитируются.
ПриСозданииНаОсновании не переносит реквизиты, отсутствующие в исходном теле;
у Отгрузки нет реквизита Основание. Табличные строки дописываются без очистки.

## Последовательность и проверка живых экземпляров

`sequence` содержит 1..40 исходных вызовов одного модуля. Каждый `actions`
сериализуется непосредственно после вызова и остаётся прежним снимком.
Вместе с `snapshotArgs: true` аргумент следующего вызова может ссылаться на
предыдущий экземпляр: `{actionArg: [0, 1]}` либо `{actionResult: 0}`. Индексы
нулевые; разрешены только прошлые действия и точно совместимые типы. Так
повторный ПеренестиТабличнуюЧасть дописывает строки в тот же Документ.

`probeMutations` — явный технический инструмент проверки aliasing:

```yaml
snapshotArgs: true
probeMutations:
- action: 0
  target: result
  path: Товары.0.Количество
  value: 93
- action: 0
  target: argument
  argument: 0
  path: 0.Сумма
  value: 94
```

`target` принимает result, argument или context. Path проходит только
объявленные поля и индексы изменяемого Массив; значение проверяется по конечному
типу. Произвольный код, неизвестные поля/targets, будущие actions, void-result,
несовместимые значения и сочетание с перехватом исключений отклоняются.
Индексы за пределами фактического массива дают обычную ошибку исполнения.
Мутации выполняются в Script после вызовов. Наблюдение имеет форму
`{result: <снимок до проб>, probes: [[<живое наблюдение каждого вызова>], ...]}`.
Каждая проба фиксируется сразу после мутации. Ранее сохранённые actions,
другой созданный объект, входные строки и storage сравниваются независимо.
Проверка свежей повторной загрузки после мутации выполняется исходным кодом
переносимых проектов, а не сравнением двух Python-словарей.

При прямом объектном корне исходный статический модуль того же owner
размещается вместе с его сгенерированными типами (`coLocatedModules` в IR).
Это устраняет искусственный Script import-cycle Объект → helper → Объект.
Исходные тела, параметры, аннотации и диапазоны сохраняются; никакие собственные
ЗагрузитьОбъект/методы/локальные callable не заменяются по строковому имени.

## Отказы и границы

`observeFailure: true` сохраняет контекст, аргументы, исключение и storage при
ошибке исходного вызова. Статус остаётся ERROR с execution_error и недоступными
баллами. Он не делает отсутствующее основание успешным бизнес-сценарием.
Native отказ обращения к Неопределено сохраняет фактические type/message.
UNSUPPORTED не перехватывается как бизнес-исключение. SQL-аудит при ошибке
сохраняется отдельно как storageEvidence. Следующий критерий имеет новую сессию.
`captureException` сохраняет прежний отдельный контракт ожидаемых исключений.

Неверный fixture/тип/owner отвергается до запуска; неподдержанные API и ошибки
компиляции не засчитываются как FAIL. Бизнес-мутация засчитывается только после
успешного исполнения и независимого SBSL-сравнения. Браузерный UI, исполнения
YAML-привязок, native создание на основании и платформенная компиляция остаются
вне standalone контракта.
