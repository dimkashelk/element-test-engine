# Управляемое время и события таймера: runtime №48

Реализовано как расширение существующего `type: runtime`. `timers` включает
очередь событий в Script; обычный `sequence` теперь принимает действия времени.
Исходные callbacks исполняются в том же Script runtime и с тем же экземпляром
контекста, что и обычные методы. Реальные секунды для продвижения часов не ждутся.

```yaml
type: runtime
target: {module: MyForm, namespace: UI, method: Start}
args: []
context: {}
observe: [Counter]
clock:
  mode: fixed
  date: '2028-02-29'
  time: '23:59:59'
  timezone: UTC
executorLocale: en-US
timers:
  onClose: cancel
  maxEvents: 1000
sequence:
  - {method: Start, args: []}
  - {advanceTime: 500}
  - {timerEvent: next}
  - {advanceTime: 2000}
  - {closeTimers: true}
```

Это пример описания механизма, без бизнес-ожиданий. Автор задаёт независимый
`expected`; сравнение и начисление баллов выполняются прежним SBSL-движком
через `test`/`run`/`batch`. Часы, таймеры и состояния изолированы на критерий,
включая параллельные работы `batch`. Прежние проверки без `timers` сохраняют
свои форматы результатов и семантику неподвижного clock snapshot.

## Входы и действия

`timers` требует `onClose: cancel`. `maxEvents` — целое число 1..10000,
по умолчанию 1000, общее для всей сессии. Неизвестные поля запрещены.
Обязательны `clock.mode: fixed`, зона `UTC` или `Europe/Moscow` и явно заданная
локаль `en-US` или `ru-RU`. Исходный режим совместимости и профиль исполнителя
хранятся раздельно; механизм проверен на исходнике 9.0 и на query-профиле current.
[Схема options v1](timer-options-v1.schema.json) описывает поля `timers`;
зависимости часов, локали и порядок шагов дополнительно проверяет общий planner.

В `sequence` остаётся предел 40 действий. Каждый шаг содержит ровно одно
действие времени либо прежние `method`/`args`:

| Шаг | Правило |
|---|---|
| `advanceTime: N` | Целое число миллисекунд 0..31536000000. Выполнить все события со сроком ≤ текущий момент + N; затем поставить часы на заданную границу |
| `timerEvent: next` | Выполнить одно ближайшее событие и поставить часы на его срок. Пустая очередь не меняет время |
| `closeTimers: true` | Отменить активные регистрации без вызова callback. Только последний шаг |
| `method: M, args: [...]` | Исходный метод того же целевого модуля, с прежней типизацией аргументов |

Без `sequence` целевой метод вызывается один раз. Регистрации наблюдаются
перед автоматическим закрытием, а итоговое техническое свидетельство — после.
Ссылки `actionArg`/`actionResult` могут адресовать только шаг вызова метода.
`probeMutations`, `querySource` и `formRequirement` с `timers` пока не поддержаны;
произвольное приложение и динамическое дерево интерфейса относятся к №49.

## Регистрация callback и порядок событий

Поддержаны исходные вызовы:

```xbsl
ПодключитьОбработчикТаймера(&Tick, 1с)
ПодключитьОбработчикТаймера(&этот.Finish, 0с, Истина)
ОтключитьОбработчикТаймера(&Tick)
```

Допускается явный получатель `этот` для этих операций. Callback — собственный
метод целевого модуля с сигнатурой `()->ничто`. Его идентичность содержит
поставщика, проект/версию, namespace, owner, декларацию и файл; план сохраняет
исходный диапазон и хэш. Ссылка захватывается в достижимое замыкание методов.
Проектные методы и локальные callable, затеняющие системное имя операции,
исполняются как исходный код и не становятся регистрациями таймера.

Регистрация адаптирует проверенные диапазоны платформенного вызова и ссылки
на callback. Выражения интервала/однократности вычисляет Script. Dispatcher
вызывает исходный метод; Python не вычисляет его бизнес-результат. Динамические
callback-переменные, лямбды, ссылки на чужие методы/экземпляры и регистрации
из внешнего модуля получают точную причину `unsupported_syntax`.

* По умолчанию таймер периодический; третий аргумент `Истина` делает его однократным.
* Период положительный. Нулевой интервал разрешён однократному таймеру;
  отрицательный интервал и нулевой период вызывают `Std::IllegalArgumentException`.
* Первый срок — текущий модельный момент плюс интервал. Сроки измеряются
  в миллисекундах относительно начала сессии.
* Сначала выбирается минимальный срок, затем порядок регистрации. Callback
  исполняются последовательно, включая равные сроки.
* Повторное подключение той же исходной идентичности заменяет регистрацию,
  отсчитывает новый интервал от текущего момента и получает новый порядок.
* Периодическая регистрация получает следующий срок от прежнего срока,
  до вызова callback. Однократная снимается до вызова callback. Отключение
  либо переподключение внутри callback поэтому влияет на следующую итерацию.
* Отключение отсутствующего обработчика ничего не меняет. Отмена другого
  callback с равным сроком предотвращает его вызов.

Вызовы `Дата.Сейчас()`, `Время.Сейчас()`, `ДатаВремя.Сейчас()` и `Момент.Сейчас()`
без аргументов читают согласованные управляемые часы. Проектные/локальные
получатели сохраняются. Момент переводится из локального снимка по явно заданной
зоне; неявные границы срезов День/Секунда/Момент читают текущие часы при создании
запроса. Явно захваченная граница запроса сохраняет прежнюю семантику.
Даты переходят через полночь и високосный день; точность — миллисекунды.
Формат интерполяции зависит от заданной локали исполнителя.
Описание native длительности: [справка языка 9.0](https://1cmycloud.com/console/help/lang/9.0/docs/stdlib/Std/Time/Duration_ru/).
Порядок событий и политика переподключения выше — контракт модели движка,
не утверждение о поведении native браузерного event loop.

## Наблюдения, завершение и недоступность

Каждый вызов при включённом `timers` возвращает
`{result: <прежний результат>, timers: <снимок очереди>, clock: <ДатаВремя>}`.
Действия времени добавляют `events`: массив наблюдений
`{callback, elapsedMs, state, clock}` после каждого успешно завершённого callback.
`state` соответствует обычному `observe`/контексту; для статического метода без
контекста он равен null. Снимки сериализуются в момент наблюдения и не меняются
после следующих действий.

Снимок очереди содержит `elapsedMs`, `active`, `executed`, `closed`,
`cancelledOnClose`. Каждая активная регистрация содержит `callback`,
`intervalMs`, `dueMs`, `order`, `once`. `runtime-evidence.json` отдельно хранит
итоговые `clock` и закрытую очередь `timers`; план подготовки не заявляет EXECUTED.
`executed` считает доставленные события перед входом в callback; при его ошибке
это не свидетельство успешного завершения. Лимит применяется к этому счётчику.

Автоматическое завершение отменяет регистрации; `вконце` обеспечивает отмену
также при ошибке callback. Контейнер и его временные файлы затем удаляются.
Callback при закрытии не запускается. Лимит событий и предел 1000 активных
регистраций дают `UNSUPPORTED/unsupported_contract`, с описанием и закрытой
очередью, без бизнес-баллов. Ошибка описания — `invalid_test`; неизвестный
исходный callback/сигнатура — `unsupported_syntax`. Исключение из callback
даёт обычный runtime ERROR; `captureException` перехватывает прежние явные
вызовы методов, а не события очереди. Timeout/лимиты вывода и памяти сохранены.
