## Текущий набор

Проверены все три xdump в корне репозитория. Режим взят из каждого
`Проект.yaml` внутри `application.zip`, а не из имени архива. Извлечение
выполнялось во временный каталог без изменения дампов. Количество файлов ниже —
исходники проекта после исключения `.asm`; методы — результат отдельной
индексации, не число выполненных тестов.

| Xdump | Проект и роль | Режим | Файлы / XBSL-модули / найденные методы | `inspect` и `validate` |
|---|---|---:|---:|---|
| `Dvizhok.xdump` | `Движок`, приложение | 9.0 | 75 / 29 / 44 | Код 0, диагностик нет |
| `Demo-SRM-dev-2026-09-28-21-38.xdump` | `ДемоСРМ`, приложение | 9.0 | 158 / 48 / 172 | Код 2: `Мероприятия/Локализация/En/ЛокализованныеСтроки.yaml` не имеет `Имя` и `ВидЭлемента` |
| `autocheck-2026-09-24-16-14.xdump` | `check`, приложение; `БазаЗнаний`, библиотека | 9.0 у обоих | `check`: 141 / 46 / 195; `БазаЗнаний`: 282 / 112 / 507 | Исходный xdump: код 2, найдено два `Проект.yaml`. Каждый извлечённый проект по отдельности: код 2 на `Ресурсы.yaml` |

В `check/Проект.yaml` указана зависимость от библиотеки `e1c::БазаЗнаний`
версии `1.1.1`; в библиотеке совпадают поставщик и версия, а `ВидПроекта` —
`Библиотека`. Поэтому для проверки приложения нужны оба проекта из одного
xdump: `check` как проверяемый проект и `БазаЗнаний` как зависимость. Отдельный
анализ библиотеки полезен для диагностики, но не заменяет совместную проверку.
Дамп практических примеров режима 10.0 отсутствует в текущем наборе; доработки
для 10.0 в этот список не входят.

## Подтверждённые препятствия

1. Загрузчик ищет ровно один `Проект.yaml`; составной xdump останавливается до
   построения модели. После извлечения `check` и библиотеки в разные временные
   каталоги обе команды можно запустить, но они останавливаются на служебных
   YAML: 2 `Ресурсы.yaml` в `check`, 6 в библиотеке. В `ДемоСРМ` таких файлов
   3 `Ресурсы.yaml` и 4 `ЛокализованныеСтроки.yaml`.
2. Исследовательский прогон на **временных копиях** после исключения только
   служебных YAML дошёл до другой ошибки: `Элементы[*].Имя` требуется у
   `ДемоСРМ/Основное/ПанельНавигации.yaml`,
   `check/ПользовательскиеПриложения/СписокКомпонентов.yaml` и
   `БазаЗнаний/Основное/КомандыБазыЗнаний.yaml`. Для этих видов `Элементы`
   описывает интерфейсные команды. Прогон временных копий не означает, что
   исходные xdump успешно прошли `inspect`.
3. `check/Проверка/ПакетПроверки/КритерийПроверкиФормаОбъекта.yaml`, строка
   112, содержит недопустимое для двойных кавычек YAML экранирование `\'`.
   Это дефект входных исходников. После устранения более ранних блокировок
   движок должен точно сообщать файл и строку; исправлять содержимое xdump
   автоматически нельзя.
4. Независимая индексация XBSL нашла одну ошибку в библиотеке:
   `Пространства/Пространства.xbsl`, строка 70 — многострочная сигнатура с
   возвращаемым типом на следующих строках. В `Движок`, `ДемоСРМ` и `check`
   ошибок индексации не найдено. Пока индекс неполон, отсутствие метода в
   библиотеке нельзя считать доказанным `FAIL`.
5. Метаданные 9.0 содержат виды, которых пока нет в `ELEMENT_TYPES`, включая
   `ОбщийМодуль`, `Структура`, `Отчет`, `HttpСервис`, `КлючДоступа` и контракты
   библиотеки. Текущий `unsupported_element` — предупреждение о возможностях
   движка, а не дефект проекта. Расширять семантику стоит по конкретным
   заданиям и ожидаемым результатам.

Для новых проектов нет заданий с критериями и ожидаемыми результатами.
`test`/`run`/`batch` на них не выполнялись; оценки `PASS`/`FAIL` и баллы
отсутствуют. Режим 9.0 уже есть в `config/runtimes.json`, но это не подтверждает
исполнение новых методов без отдельных сценариев.

## Приоритеты доработок для этих проектов

| Приоритет | Доработка | Проверяемый результат |
|---|---|---|
| P0 | Разбирать `Ресурсы.yaml` и `ЛокализованныеСтроки.yaml` как служебные данные; проверять `Элементы` по `ВидЭлемента` и назначению поля. Сохранять ограничения размера и точную диагностику некорректного YAML. | `ДемоСРМ`, отдельно извлечённые `check` и `БазаЗнаний` проходят загрузку до содержательных диагностик; интерфейсные команды не требуют `Имя`. Строка 112 в `check` остаётся ошибкой входа. |
| P0 | Поддержать составной xdump с явным выбором приложения и разрешением объявленных библиотек по поставщику, имени и версии. Сверять метаданные зависимости и не выбирать произвольный проект. | `check` анализируется вместе с `e1c::БазаЗнаний` 1.1.1; библиотека может анализироваться отдельно. Неоднозначная, отсутствующая или несовпадающая зависимость получает точную диагностику. |
| P0 | Разделить идентичность проверяемого проекта и подключённых библиотек в модели, кэше `batch` и отчёте; учитывать содержимое библиотеки при `sourceHash` или отдельном хэше зависимостей. | Изменение только библиотеки инвалидирует результат `check`; библиотека не выдаётся за отдельную студенческую работу, а в отчёте видны выбранное приложение и зависимости. |
| P1 | Исправить индексирование многострочной сигнатуры в `БазаЗнаний/Пространства/Пространства.xbsl` и защитить проверки отсутствия метода при неполном индексе. | Сигнатура на строках 70–72 индексируется с исходными границами; регрессионный тест ловит ложный `FAIL`. |
| P1 | Составить задания из конкретных требований для `ДемоСРМ` и `check` с учётом вызовов в библиотеку; выбрать репрезентативные методы и проверяемые эффекты. | Для каждого критерия есть источник требования и подтверждённые `PASS`, контролируемый `FAIL`, а для недоступного контракта — `UNSUPPORTED`. |
| P2 | Добавлять поддержку новых видов метаданных и платформенных API по выбранным заданиям; измерить время и память анализа составного проекта после устранения P0. | Каждый добавленный контракт имеет положительный, отрицательный и недоступный случаи; замеры воспроизводимы и не меняют баллы. |

Порядок P0 следует из фактических кодов возврата: загрузка сейчас
останавливается до структурных критериев и runtime. При внедрении следует
проверить все три исходных xdump и сохранить результат контрольного `Движок`.
