# Полная проверка эталонных дампов и работ студентов

Статус: **план и матрица будущих тестов**, 3 октября 2026 года.
Основание: предоставленные пользователем четыре эталонных xdump и уточнения
к общему плану проверки. Этот документ не утверждает выполнение новых тестов.

После №38 добавлен [ночной корпус всех 303 UI-деклараций](../tests/corpus/all-dump-forms/README.md):
снимки деклараций/сигнатур, 326 критериев структуры и 312 сценариев значений.
Пять выбранных форм прошли локально; полный набор подготовлен для nightly.
Полная функциональная оценка динамических списков, деревьев и native API
по-прежнему требует расширения адаптеров.

## Зафиксированные требования пользователя

1. Формы проверяются универсально: на входе описание, на выходе оценка
   соответствия формы студента этому описанию. Dvizhok — первый корпус,
   а не специальная реализация механизма.
2. Все контракты запросов должны быть реализованы и проверены. Нынешние
   ограничения JOIN/ЗАПОЛНИТЬ и других форм — очередь доработок, не конечная
   граница готовности query runtime.
3. Расширить хранение, регистры и транзакции.
4. Добавить полную проверку необходимых видов метаданных.
5. Проверить права, библиотеки, сетевые интеграции, обмены и фоновые задания.
6. Автор тестов самостоятельно придумывает полный набор по предоставленным
   эталонам. Студенты присылают собственные реализации; исходники студента
   не определяют правильный ответ или обязательные требования.

Локально запускать только тесты изменённого участка и реально затронутых
контрактов. Общая регрессия запускается существующим ночным CI на проверяемом
коммите. Полнота подготовленного набора и частота его запуска — разные вещи.

## Корпус и происхождение требований

Текущий read-only индекс содержит следующие объявления методов и UI-форм.
Статические методы и перегрузки включены; старые таблицы сентября содержат
меньшие числа. Инвентаризация не равна покрытию исполнением.

| Эталон / проект | Объявления методов | UI-декларации |
|---|---:|---:|
| Dvizhok / Движок | 44 | 16 |
| Demo-SRM / ДемоСРМ | 186 | 28 |
| autocheck / check | 231 | 24 |
| autocheck / e1c::БазаЗнаний | 541 | 58 |
| Prakticheskie-primery / Примеры_new | 1162 | 177 |
| Всего | 2164 | 303 |

Для каждого сценария сначала читать постановку примера, комментарии,
метаданные и поведение предоставленного правильного решения. Затем автор
фиксирует отдельное требование, inputs, ожидаемый результат/эффекты и баллы.
При отсутствии отдельной постановки эталон задаёт правило, из которого автор
составляет письменное описание и независимые сценарии. Эталон не должен
вызываться во время оценки работы студента для получения его expected.

Сохранять sourceHash эталона и происхождение каждого требования. Expected
вычисляется заранее из требования, вручную или независимым oracle; совпадение
с эталоном проверяется исполнением. Выявленное противоречие фиксируется отдельно,
не исправляется молчаливой заменой expected на actual. Имена, UUID метаданных,
текст метода, внутренние helper и порядок YAML не становятся требованиями,
если не являются частью интерфейса/описания задания.

Преподаватель может передать собственное описание: оно имеет приоритет над
выведенными из эталона правилами. Проверки должны принимать альтернативный
правильный алгоритм, одинаковые owner-имена в разных подсистемах и разрешённые
описанием различия структуры. Шкала баллов связывается с требованиями;
внутренние вспомогательные тесты не дублируют баллы за один бизнес-результат.

## Матрица тестов, которую составляет автор

| Область | Обязательные сценарии | Что обнаруживают отрицательные варианты |
|---|---|---|
| Формы по описанию | Требуемые поля/типы/подписи/таблицы/команды; состояния и переходы; явно заданная компоновка; две разные правильные реализации | Нет обязательного поля, неверная привязка/видимость/доступность/эффект, нарушение явно заданного порядка |
| Чистые методы | Обычный, пустой, минимальный, граничный и составной вход; все ветви; типы результатов | Неверная формула, условие, округление, возврат, обработка пустого входа |
| Коллекции и строки | 0/1/несколько элементов, повторы, разный порядок, Unicode/пробелы, дроби и допустимые отрицательные значения | Пропуск/дублирование/перестановка, неверное поле, изменение входа |
| Даты и время | Граница дня/месяца/года, високосный год, включительность диапазона, текущее время по независимому oracle | Смещение границы/часового пояса, ошибочный день недели, stale дата |
| Объектный lifecycle | Создание, обновление, повторное действие, основание другого owner, свежая загрузка и независимость копий | Накопление вместо замены, неверное основание/поле, лишняя запись |
| Хранение и регистры | Пустое/заполненное состояние, полные и частичные фильтры, замещение/добавление, все поддерживаемые периодичности, фактический SQL-аудит | Потеря соседних записей, неверный фильтр/движение/период, stale снимок |
| Транзакции | Commit/rollback, именованные/вложенные ресурсы, ранний выход/исключение, две конкурентные сессии | Частичная фиксация, потерянное изменение, неверная блокировка/изоляция |
| Типы и зависимости | Namespace/alias/полная квалификация, одинаковые имена/UUID, nullable/union, структуры и callbacks | Подмена owner/библиотеки, неверная ветвь union, потеря зависимости |
| Метаданные | Каждый вид и его обязательные поля/связи/ограничения; положительные и отрицательные декларации | Отсутствующее поле/ресурс, несовместимый тип, нарушенная связь |
| Права и RLS | Разные роли и пользователи, разрешённая/запрещённая строка/операция, изменение ключа доступа | Чужие данные, чрезмерные/недостаточные права, утечка между пользователями |
| HTTP/OData/SOAP | Реальный запрос к управляемому тестовому сервису, payload, статусы, авторизация, ошибки/повтор | Неверный endpoint/метод/тело, ложный успех, утечка credentials |
| Обмены и фоновые задания | Повторная доставка, идентичность узла, запуск/повтор/отказ и итоговые данные | Дубликаты, пропуски, неверный узел/расписание/rollback |
| Проверка студентов | Правильная, альтернативная правильная и мутированная работа; публичные test/run/batch | Специальная ветка под эталон, ложный PASS, утечка контекста/кэша |

Для каждой достижимой ветви эталона автор подбирает вход; для циклов —
0/1/несколько итераций и существенные границы. Добавлять независимые проверки
связанных эффектов и повторных вызовов. Текстовые методы описания примеров,
обработчики, helper и методы библиотеки учитываются в карте по своей роли;
вызов зависимости не заменяет отдельную проверку её собственного контракта.
Недостижимая ветвь требует доказательства и отметки, а не выдуманного PASS.

Наблюдение сравнивает все существенные поля, порядок там, где он определён,
сохранность остальных данных и отсутствие лишних эффектов. Для случайного
UUID/текущего времени использовать отдельные правила/oracle, не подставлять
ответ студента как ожидание. Для каждой группы требований нужны исполнимые
мутации и проверка альтернативного правильного решения. Грамматический отказ
или ошибка компиляции не доказывают обнаружение неверной бизнес-формулы.

## Полное исполнение контрактов запросов

Составить отдельный версионированный каталог query-контрактов: все формы и API
запросов, встречающиеся во всех четырёх дампах и их зависимостях, плюс полный
документированный контракт выбранного режима совместимости 9.0. Для форм,
которых нет в эталонном корпусе, автор создаёт переносимые fixtures.
Зафиксировать источники семантики, типы, синтаксис и случаи сочетания операций;
платформенный XBQL и standalone Script различать при выборе реализации.

Следующие группы — обязательная матрица; точный синтаксис и все дополнения
уточняются инвентаризацией/документацией, не догадкой о наличии API:

| Группа | Положительные и граничные сценарии | Исполнимая мутация |
|---|---|---|
| Источники и aliases | Все допустимые metadata-источники, namespace/импорты, одинаковые короткие имена | Другой owner с тем же UUID |
| Параметры | `%Имя`, `%{выражение}`, порядок/однократность вычисления, повторное Выполнить после изменения данных | Повторное вычисление либо неправильный captured параметр |
| Проекции и выражения | Поля/aliases, вычисляемые значения, допустимые литералы и типовые преобразования | Другой столбец или неверная формула |
| Предикаты | Все операторы/логические сочетания, скобки, границы, списки и иерархия по каталогу языка | Удалённый отбор, строгое вместо включительного сравнения |
| NULL и nullable | Пустые/заполненные значения, функции замены/проверки, все допустимые типы | Смешение NULL с пустой строкой/нулём |
| JOIN | Все документированные виды и сочетания, 0/1/несколько совпадений, unmatched строки | Другой ключ, потерянная unmatched строка, неверная кратность |
| Группировки и агрегаты | Несколько групп, пустой набор, повторы, NULL и дроби | Неполный ключ группы, пропущенный/дублированный вклад |
| Уникальность и объединения | Все документированные формы, повторы и разные типы колонок | Ошибочная дедупликация либо потеря повторов |
| Сортировка и лимит | Несколько ключей/направлений, определённые ties, границы числа строк | Лимит до фильтра/сортировки, неверное направление |
| Виртуальные таблицы | Все документированные срезы/остатки/обороты, измерения, периоды и параметры | Неверный период/измерение/знак движения |
| ЗАПОЛНИТЬ и структуры | Имена/порядок полей, пропущенные defaults, nullable, квалифицированные owners | Другой тип либо перепутанное заполнение |
| Составные запросы | Документированные вложения, объединения/пакеты и их сочетания с другими группами | Потерянный вложенный отбор или результат |
| Результат и ресурсы | Типы строк, пусто/одна/несколько, обход, одиночный результат, закрытие/повтор по контракту | Неверная cardinality или stale результат |
| Состояние/транзакция/права | Запрос после записи, commit/rollback, изоляция и разрешённые данные | Чтение старого/чужого либо откатившегося состояния |

Query-критерий исполняет исходный запрос по фактическим подготовленным данным.
`mocks.queries.rows`, готовый результат и один trace не закрывают его контракт.
Ключевые сочетания тоже обязательны: JOIN + фильтр + сортировка + лимит,
срез + nullable-отбор + ЗАПОЛНИТЬ, запись/rollback + повтор запроса.
Если язык не гарантирует порядок равных ключей/несортированных строк,
проверять допустимый результат без навязывания случайного порядка эталона.

Memory и PostgreSQL дают одинаковую бизнес-семантику. PostgreSQL проверяется
по фактическому состоянию и независимому аудиту; неподдержанная операция
остается видимой задачей доработки. В конечной приёмке query-каталога не должно
быть обязательного контракта, закрытого через UNSUPPORTED или подставные rows.
Текущий ограниченный адаптер остаётся исторической базой для расширения;
новые ветки query runtime строятся по AST/типам, без специальных имён проектов.

## Условие завершения общего плана

В воспроизводимой карте есть все файлы, формы, декларации методов, существенные
ветви, виды метаданных и query-контракты. Для каждого проверяемого требования —
описание, criterionId, независимые входы/ожидания и реальное свидетельство
SBSL/SQL/UI по соответствующему контракту. Все обязательные query-контракты
исполняются. Исторические и свежие свидетельства различаются; недоступность
не считается покрытием. Регрессию всего набора подтверждает ночной CI.

Корректные и альтернативные корректные работы проходят, нарушения требований
обнаруживаются на мутированных работах. Публичные test/run/batch согласованы;
данные, права, константы и результаты не перетекают между студентами.
Недоступные внешние среды или недостижимые участки описываются отдельным
обоснованным остатком, который не скрывается в общем счётчике PASS.
