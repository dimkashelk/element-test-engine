# Ночная регрессия в GitHub Actions

Workflow: `.github/workflows/nightly-tests.yml`. Каждый день в **02:17 МСК**
(23:17 UTC предыдущего дня) запускается `unittest discover` с включёнными Docker
и PostgreSQL тестами. Используются Ubuntu 24.04, Python 3.12, Java 17 и образы
с digest из `config/`. Регрессия выполняется на четырёх независимых runner параллельно;
внутри каждого runner тесты идут последовательно.

Для Docker runtime на CI установлен `ELEMENT_TEST_RUNTIME_TIMEOUT=15s`:
лимит включает запуск JVM и компиляцию исходника на runner. Явный `timeout`
проверки имеет приоритет, в том числе в отрицательных тестах зависания.
Локальный лимит по умолчанию остаётся 5 секунд; максимальный wall timeout —
30 секунд. CPU ulimit соответствует wall timeout (с округлением вверх до
целых секунд); у SQL executor оба лимита — 30 секунд. Прежний фиксированный
CPU ulimit 8 секунд завершал JVM с кодом 137 до истечения wall timeout на Linux amd64.
Остальные ограничения ресурсов контейнера сохраняются. Обычные проверки ФИО
используют лимит окружения; явный короткий timeout отрицательных тестов сохранён.

Расписание проверяет последний коммит основной ветки. Файл workflow должен
находиться в основной ветке; локальные незакоммиченные/неотправленные изменения
в проверку не входят. В GitHub Actions доступен ручной запуск с выбором ветки.
По [правилам GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
запуск по расписанию может задержаться или быть пропущен при высокой нагрузке.
Отсутствующий запуск виден в истории Actions; отдельное утреннее оповещение
и внешний монитор отсутствующего запуска в этой версии не настроены.

## Что требуется подключить один раз

1. Войти в GitHub (`gh auth login`) и создать репозиторий.
   В текущей истории Git уже есть три исходных xdump; локальный дистрибутив
   executor и `Dvizhok.xdump` исключены из Git и доставляются через Release.
   Workflow поддерживает публичные и приватные репозитории. Текущий
   `dimkashelk/element-test-engine` переведён в публичный режим 3 октября 2026 года.
2. Отправить исходники и этот workflow в основную ветку. Перед отправкой
   согласовать состав текущих изменений проекта: CI проверяет отправленный коммит.
3. Подготовить пакет окружения локально (Python 3.12+):

   ```bash
   python3 tools/ci/assets.py pack result/ci-assets/element-ci-assets.tar.gz
   ```

   Пакет включает только `script_u_10.0.2_1/` (вместе с licenses) и
   `Dvizhok.xdump`. Прочие входные дампы уже находятся в Git. Права runtime
   нормализуются: контейнер под пользователем 65534 должен читать JAR-файлы.
   Существующий пакет не перезаписывается.
4. Загрузить пакет в Release `ci-assets-v1` **этого же репозитория**.
   После создания/подключения репозитория и отправки исходников:

   ```bash
   gh release create ci-assets-v1 result/ci-assets/element-ci-assets.tar.gz \
     --title 'CI assets v1' --notes 'Script executor 10.0.2-1 and regression fixture' \
     --prerelease
   gh variable set CI_ASSETS_SHA256 \
     --body "$(cat result/ci-assets/element-ci-assets.tar.gz.sha256)"
   ```

   `CI_ASSETS_SHA256` — repository variable, не secret. Тег по умолчанию —
   `ci-assets-v1`; другой тег задаётся переменной `CI_ASSETS_TAG`. Пакет
   проверяется по SHA-256 перед распаковкой. Для скачивания workflow использует
   встроенный `GITHUB_TOKEN` только с `contents: read`; отдельный токен не нужен.
   Пароль одноразовой БД генерируется на каждый запуск и маскируется в логах.
5. Для публичного репозитория стандартные GitHub-hosted runners бесплатны;
   для приватного нужно проверить доступный лимит/бюджет Actions.
   [Правила учёта минут](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
   Замер запуска `37111427816`: 287 тестов за 145 минут 16 секунд,
   задание целиком — 146 минут 9 секунд. Для приватного репозитория такой
   ежедневный запуск составил бы примерно 4410 минут квоты за 30 дней.
6. Запустить `Nightly regression` вручную и проверить реальное выполнение на Linux:

   ```bash
   gh workflow run nightly-tests.yml
   gh run list --workflow nightly-tests.yml --limit 5
   ```

## Где смотреть утром

На странице запуска Actions находится сводка: SHA проверенного коммита,
статус, число прошедших/упавших/пропущенных тестов, длительность и десять самых
медленных тестов. Задание `Complete regression summary` объединяет результаты всех
четырёх runner. Артефакты `nightly-<run_id>-<attempt>-shard-<0..3>` хранят каталог
`result/` каждого runner с логом `nightly/tests.log`, JSON-результатом, Markdown-сводкой
и отчётами тестов 14 дней. Артефакт `nightly-<run_id>-<attempt>-summary` содержит
объединённые JSON и Markdown. Автоматическая отправка сообщений в почту/мессенджер не настроена.

Любой пропуск теста, пустая suite, ошибка импорта, ошибка теста или неожиданно
успешный expected-failure делает прогон неуспешным. Ожидаемые падения учитываются
отдельно. Отрицательные сценарии внутри тестов сохраняют обычные ожидания:
корректно проверенный `FAIL` студенческой работы не означает ошибку регрессии.

JSON сохраняется после каждого завершённого теста. Если процесс прерван,
сводка помечает результат как `incomplete`; если окружение не подготовлено —
`setup_error`/`not_started`. Таймаут тестового шага каждой части — 150 минут,
всего задания runner — 180 минут, с запасом для подготовки окружения и сохранения
отчётов. Объединяющее задание ограничено 15 минутами. Индивидуальные лимиты runtime
и SQL executor сохранены.

### Распределение между runner

`tools/ci/run_nightly.py --shard-index 0 --shard-count 4` выбирает одну из четырёх
частей. Целые тестовые модули распределяются от самых долгих к самым коротким на
наименее загруженную машину. Это сохраняет последовательность тестов и общие
class/module fixtures. Каждая машина получает собственные Docker-контейнеры,
одноразовую БД, пароль и каталог отчётов. `fail-fast: false` сохраняет выполнение
остальных частей при падении одной из них.

Вес модулей зафиксирован в `config/nightly-module-timings.json`: измерения запуска
`37253831055` от 5 октября 2026 года и предыдущего полного запуска `37171915643`
для оставшихся тестов. Последовательный запуск оценивается примерно в 313 минут,
четыре части — примерно по 78 минут каждая, плюс подготовка и загрузка артефактов.
Это оценка по истории, фактический параллельный прогон ещё требуется проверить.
Новые модули распределяются автоматически с начальной оценкой времени; тесты
не исключаются из suite из-за отсутствующего веса.

Посмотреть план без запуска тестов:

```bash
python tools/ci/run_nightly.py --list-shards --shard-count 4
```

У каждой части сохраняются полный fingerprint suite и список назначенных тестов.
Сборщик проверяет ровно четыре отчёта, SHA коммита, общий fingerprint, отсутствие
повторов и точное совпадение завершённых тестов с планом. Потерянный отчёт,
прерванная часть, ошибка подготовки, неполное покрытие форм или чужой результат
делают итог `incomplete` и завершают сборщик с ненулевым кодом. Падения, ошибки
и пропуски сохраняют неуспешный итог. Для локального объединения скачанных
артефактов (каждый в отдельной подпапке) используется:

```bash
python tools/ci/run_nightly.py --aggregate result/shards --shard-count 4
```

Длительность в общей сводке — максимальное время выполнения части; суммарное
время всех runner сохраняется отдельно в `totalRunnerSeconds`. Запуск без
`--shard-count` по-прежнему выполняет полную suite последовательно.
При аварийной потере runner отчёты
могут не загрузиться; источником статуса остаётся страница запуска GitHub.

Полную регрессию не запускают на каждый push. Днём продолжают выполнять
тесты изменённого участка; перед выпуском вручную проверяют выпускаемый коммит.


## Формы всех предоставленных дампов

`tests/test_all_dump_forms.py` создаёт **303 отдельных ночных теста** по
замороженному manifest: ДемоСРМ — 28, Движок — 16, Примеры_new — 177,
check — 24, отдельная библиотека БазаЗнаний — 58. Проверяются снимки деклараций
и сигнатуры, 326 критериев структуры №38 и 312 сценариев значений привязок.
Ожидаемые значения/fixtures фиксируются до исполнения; baseline в nightly
не пересоздаётся. Отсутствующий/изменённый архив или состав форм даёт ошибку.

[Контракт корпуса](../tests/corpus/all-dump-forms/README.md) отдельно описывает
регрессию деклараций и функциональные сценарии. Неподдержанное поведение
1799 других выражений, включая динамические списки, деревья и native команды,
остаётся `NOT_CHECKED`, без утверждения runtime PASS. Утренняя сводка показывает
завершённые формы и эти границы; артефакты сохраняются для каждой формы в
`result/all-dump-forms/nightly/`. Расписание 02:17 МСК и прежние лимиты сохраняются.

Локальная приёмка расширения: пять выбранных форм и целевые тесты авторинга/CI.
Полная локальная регрессия не запускалась.
