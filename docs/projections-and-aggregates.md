арифметика (+, −, ×, /, %) и конкатенация, совместимые ВЫРАЗИТЬ, простой и поисковый ВЫБОР,
РАЗЛИЧНЫЕ, КОЛИЧЕСТВО/СУММА/МИНИМУМ/МАКСИМУМ/СРЕДНЕЕ,

параметрами, сортировкой, ПЕРВЫЕ и именованным ЗАПОЛНИТЬ.
Python строит и проверяет план; значения вычисляет сгенерированный Script.

## Семантика адаптера

- Порядок обработки: источники/JOIN → ГДЕ → группы → ИМЕЮЩИЕ →
  проекции/РАЗЛИЧНЫЕ → сортировка → ПЕРВЫЕ. Глобальный агрегат на пустой
  выборке даёт одну строку; группировка по ключам — ни одной.
- КОЛИЧЕСТВО(*) считает строки, КОЛИЧЕСТВО(выражение) пропускает SQL NULL.
  Остальные агрегаты на пустом множестве возвращают SQL NULL.
  РАЗЛИЧНЫЕ внутри агрегатов удаляет повторы до вычисления.
- SQL NULL хранится отдельным признаком от nullable значения реквизита
  Неопределено. Группы и DISTINCT сравнивают типизированные значения вместе
  с этим признаком; совпадение их JSON-представлений `null` не сливает группы.
  КОЛИЧЕСТВО nullable реквизита с Неопределено отличается от КОЛИЧЕСТВО(NULL).
- ВЫБОР вычисляет только выбранную ветвь, отсутствие ИНАЧЕ даёт SQL NULL.
  Агрегаты в ГДЕ/ПО/ключах группы, вложенные агрегаты и негруппированные поля
  отвергаются до запуска. Несовместимые ветви также недоступны.
- Десятичные литералы сохраняют исходные цифры. Округление и арифметика
  выполняются нативным типом Число Script. Квалификатор Число задаёт длину
  целой/дробной части (до 32), округляет и проверяет переполнение; переполнение
  является ERROR исполнения. Строковый квалификатор ограничивает длину.
  ВЫРАЗИТЬ не превращает несовместимые типы друг в друга.
- Ссылки и перечисления сохраняют точного владельца; одинаковый UUID разных
  типов не допускает подмены. Карта с ключами-перечислениями остаётся нативной
  внутри исходного метода; только JSON-результат/trace получают строковые ключи.
- Поддержанные сигнатуры методов: НачинаетсяС/ЗаканчиваетсяНа, Подстрока
  с одним или двумя индексами, ВВерхнийРегистр/ВНижнийРегистр, Длина,
  Округлить, Дата для ДатаВремя, ДобавитьДни для Дата. Подстрока использует
  нативные индексы `[начало, конец)`. Дополнительно сохраняется ЗаменитьNull.
  Остальные методы дают UNSUPPORTED, а не выдуманное значение.
- Параметры фиксируются при создании запроса; повторное Выполнить читает
  текущее staging. Старый результат остаётся снимком, rollback восстанавливает
  хранение. Identity-only ссылка не требует генерации всей схемы своего объекта;
  фактическая загрузка/запись связывает эту схему отдельно.

UNION/вложенные и составные запросы, дополнительные виртуальные таблицы,
иерархия/разыменование владельцев, внешний XBQL/API binding, математические
и прочие функции за пределами таблицы сигнатур, права и смешанные операции
остаются явной очередью №42–45. Для выбранных записей точные причины сохранены
в карте; остаток не обозначается PASS.

## Приёмка

50 различных целевых методов тестов успешны: 15 новых и 35 затронутых прежних.
32 основных и 8 граничных переносимых сценариев исполняются в двух проектах
с разными namespace, объектами, полями и точками входа. Проверены пять пустых
выборок, coalesce пустой суммы, переполнение, CASE с неисполняемой ошибочной
ветвью, порядок DISTINCT/ПЕРВЫЕ, номинальные типы и точность.

Реальные методы вызываются напрямую из неизменённых архивов:
`Мероприятия::Задачи.КоличествоОткрытыхЗадачСотрудника` (активные/пустые задачи)
и `Администрирование::ОписаниеРаботыФормаОбъекта.ПолучитьДоступныйНомер`
(максимум 17 с дубликатами). Пустой MAX отдельно проверен в переносимом проекте:
реальный метод приводит его к non-null Число и для пустой базы имеет ошибку
исходного алгоритма. Его expected не подменялся.

Авторские данные/ответы находятся в `tests/projection_fixtures.py` и assignments.
Они задаются независимо от вывода исходников. Полный SQL-аудит учитывает все
реквизиты реальных объектов: пропущенные в первой версии fixture поля были
явно заданы автором, а не скопированы из фактического результата. Все пять
исходных `.xbql` review templates встроены в отдельный переносимый проект;
каталог связывает fixtureHash с sourceHash/range обёртки и отдельным SBSL-критерием.

Семь исполнимых мутаций (арифметика, CASE, COUNT, SUM, HAVING, JOIN, DISTINCT)
дают SBSL FAIL. Арифметически эквивалентная реализация проходит. Проверены
некорректный fixture, timeout, неподдержанная операция и отказ backend с
последующим успешным запуском. Шесть PostgreSQL-сценариев покрывают реальные
корни и JOIN/агрегаты/повторные снимки/откат двух переносимых проектов;
независимый SQL-аудит и cleanup успешны.

Публичные test/run: Demo-SRM по 2/2 PASS, autocheck по 1/1 PASS.
Контрольный пакет: FAIL → UNSUPPORTED → PASS, unavailablePoints = 1.
Два batch с отдельными кэшами: 3/0/3 балла, cacheHit:false.
48 grading/batch/event/manifest артефактов прошли JSON Schema.
[Измерения](query-stage-041-measurements.json) сохраняют SHA-256 журналов,
первичные сбои и отдельные успешные повторы. Четыре архива неизменны;
прежние assignment expected, лимиты и расписание CI сохранены.

Полный discovery, 303 формы, 44 прежних корня, четыре validate и полная
регрессия локально не запускались. Ночное исполнение новых тестов не заявляется.
