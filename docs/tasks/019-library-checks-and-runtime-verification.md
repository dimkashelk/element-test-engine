## Точный выбор библиотеки в проверке

Необязательное поле `library` содержит строковые `provider`, `name`, `version`.
Структурный критерий выбирает вложенную модель именно этой зависимости.
Обычный runtime использует её каталог XBSL, элементы и типы. Каталог
выбирается из списка зависимостей, разрешённых при анализе приложения;
одинаковое краткое имя другого проекта не может подменить библиотеку.
Несовпадающий селектор даёт `invalid_test`, без ложного `FAIL` студента.

Проверка реального `check` находит уникальный метод
`e1c::БазаЗнаний` 1.1.1 `ПраваДоступа::ПраваБиблиотеки.ЭтоАдминистраторБиблиотеки`.
Полный `run_test` с таким критерием дал 1/1 `PASS` на исходном составном xdump;
задание и отчёт сохранены в `result/check-library-verified`.
Отдельный fixture с одноимёнными `Main.Ответ` в приложении и библиотеке
подтверждает выбор исходного тела библиотеки (`42` вместо `1`), исполнение
в Docker, контролируемый `FAIL` и последующий `PASS`.

Контракт охватывает прямые методы выбранной библиотеки. Автоматический переход
по вызовам в другие библиотеки и интеграционный SQL runtime для библиотечных
методов не заявлены; последний явно возвращает `UNSUPPORTED`.
