# Задание №57: независимые запросы, отчёты и панель

Статус: **сформировано, не реализовано**. P1. Зависимости: №55, №47, №51;
№53–54 для сценариев, использующих соответствующее сохранение.
Общие правила: [план приёмки](../dvizhok-final-verification-plan.md).

## Охват и случаи

| Источник | Обязательные проверки |
|---|---|
| Количество поступлений денег | 0/1/несколько документов; свежий результат после записи; посторонние документы не учитываются |
| Остатки перед отгрузкой | Две номенклатуры, два склада, повторы потребности, пустой результат; отбор запроса оценивается отдельно от бизнес-правила дефицита |
| Остатки перед расходом денег | Несколько движений/оснований, приход и расход, 0/граница/дефицит; повторное чтение |
| Последняя цена на приветствии | Нет истории/одна/несколько дат, другая номенклатура, граничный момент, nullable-вход по контракту |
| Отдельный XBQL отчёта цен | Есть цена/нет цены, несколько товаров, JOIN и NULL, число против строки «Нет цены», сохранение кратности |

Все пять исходных вхождений выбираются по точным owner, диапазону и sourceHash.
Исполняется оригинальный query по контролируемому хранению. Нельзя подставлять правильные
готовые строки. Отдельно прямо оценить `ФормаПриветствие.ПолучитьКоличествоПоступленияДС`
и `ПолучитьЦенаНоменклатуры`: их ветви пустого и непустого результата не закрываются
исполнением самостоятельного query entry. Остальные содержащие запрос методы относятся к №56.

Для всех шести отчётов проверить данные источника, значения каждой формулы, заявленные
колонки/роли, иерархию и поддержанную сортировку раздельно. Наборы: пустой, одиночный,
повторные строки, NULL, дроби, два типа регистратора; повторное чтение после записи.
Отчёт остатков сопоставлять с вручную заданными движениями, отчёт поставщиков — с независимо
заданной историей, денежные отчёты — с явными ожидаемыми суммами и регистраторами.
Не вычислять expected тем же query или parser формул, который проверяется.

Для панели проверить все шесть виджетов, ссылки, Ид и расположение, начальный снимок,
изменение данных до обновления и свежий снимок на границе 30000 мс, несколько периодов,
общую сессию и завершение таймеров. До обновления предыдущий снимок не должен превращаться
в свежий только из-за записи; ожидаемая политика определяется контрактом панели.

## Приёмка и артефакты

Создать `assignments/dvizhok-final-queries`, `assignments/dvizhok-final-reports`
и `assignments/dvizhok-final-panel`, связав критерии с требованиями №55.
Все 5 query-вхождений, 2 серверных метода, 6 отчётов и панель получают исполнение и
независимую оценку, с memory/PostgreSQL там, где используется хранение.
Для строк без заявленной сортировки использовать сравнение с сохранением кратности;
при сортировке оценить конкретный порядок. Проверить параметры, ресурсы результата и повторное чтение.

Сохранить планы происхождения запросов/формул, фактические строки и колонки, данные макета,
SQL-аудит, события обновления, grading и выявленные бизнес-дефекты. Запрос, макет и native
рендеринг имеют разные статусы. Отсутствующая обязательная колонка — нарушение требования,
если оно определено в №55, даже когда запрос возвращает правильную цену.
Native pivot/DOM/встроенная платформа остаются явной внешней границей, а не PASS.
