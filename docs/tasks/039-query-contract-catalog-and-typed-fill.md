## 1. Версионированный каталог query-контрактов

Подготовить `docs/query-contract-catalog.json` и читаемую Markdown-карту,
воспроизводимые командой отдельного read-only инструмента. Каталог объединяет:

1. Реальные литералы, query API и соответствующие зависимости всех пяти
   проектов четырёх дампов; зафиксированные неразобранные/динамические случаи.
2. Полный документированный каталог выбранного режима совместимости 9.0.
   Возможности из соседних версий и других продуктов не объявлять
   подтверждённой семантикой Элемента/standalone без отдельного основания.
3. Переносимые fixtures для документированных форм, которых нет в дампах.
   Их отсутствие в эталоне не отменяет обязательный контракт общего плана.

Запись содержит стабильный contractId, семейство и сочетания операций,
полную идентичность проекта/библиотеки/владельца, sourceHash, файл, исходные
диапазоны, текст запроса, целевой метод с сигнатурой, зависимости, источники
семантики и версию. Различать `discovered`, `parsed`, `planned`, `executed`,
`independentlyAssessed`, неподдержанную причину и следующий конкретный этап.
Для документированных форм без исходного файла указывать fixture, без
фиктивного source range. Критерий/журнал связывать с конкретным вхождением;
одинаковые тексты в разных местах не сливаются.

Каталог охватывает источники/aliases, параметры, проекции/преобразования,
предикаты/NULL, соединения, группировки/агрегаты, уникальность/объединения,
сортировку/лимит, виртуальные таблицы, ЗАПОЛНИТЬ, составные запросы,
результат/ресурсы, состояние/транзакции/права и существенные сочетания.
Наличие записи или trace не означает выполнения контракта. Старые журналы
№31–33 имеют историческое происхождение; свежая приёмка №39 помечается отдельно.

Разбор литералов учитывает строки, комментарии, вложенные скобки и captured
параметры; поиск API использует исходную идентичность и видимость. Не разрешать
случайный одноимённый проектный `Запрос` как системный. Неразобранный участок
остаётся видимым в каталоге с диапазоном и причиной, а не исчезает из карты.

## 2. Обязательные реальные корни ДемоСРМ

Оба метода в неизменённом `Общие/КурсыВалют/КурсыВалют.xbsl` должны получить
отдельный прямой критерий в memory и PostgreSQL, без `mocks.queries`/готовых rows:

| target.namespace | target.module | Метод | Независимое наблюдение |
|---|---|---|---|
| Общие::КурсыВалют | КурсыВалют | ПолучитьКурсВалюты | КурсВалюты? со всеми полями или отсутствие строки |
| Общие::КурсыВалют | КурсыВалют | ПересчитатьПоКурсу | Исходная формула/округление, ветки отсутствия курса и нулевой кратности |

Проверенное объявление `КурсВалюты` — YAML `Структура` в namespace
`Общие::КурсыВалют`. Поля в порядке объявления: Валюта: Валюты.Ссылка?,
Код: Строка, Период: Дата?, Курс: Число, Кратность: Число.
Реальный запрос проецирует Валюта/Период/Курс/Кратность и содержит
`ЗАПОЛНИТЬ КурсВалюты` перед ИЗ. Код не проецируется: его значение должно
следовать подтверждённому конструктору/default, не готовому ответу driver.
Идентичность регистра в storage: `Общие::КурсыВалют::КурсыВалют`.

Регистр — День, измерение Валюта: Валюты.Ссылка?, ресурсы Курс/Кратность: Число.
ПолучитьКурсВалюты использует СрезПоследних(%ДатаКурса), отбор валюты и
ЕдинственныйИлиНеопределено. ПересчитатьПоКурсу при найденной строке и
ненулевой кратности вычисляет `(Сумма * Курс / Кратность).Округлить(2)`,
иначе возвращает 0. Чтение исходника не подтверждает исполнение этой цепочки.

Прежний отказ генератора `КурсВалюты` сохранён в отложенном кандидате как
исторический. До реализации заново проверить оба корня текущим planner и
сохранить фактическую причину: не объявлять старый отказ свежим свидетельством.
`ПолучитьКурсыВалют` с соединением и ЗаменитьNull попадает в каталог и очередь,
но не становится обязательным положительным корнем группы заполнения №39.

## 3. Семантика именованного заполнения и YAML-структур

Перед renderer проверить официальные источники и доверенные native-пробы
Script `-c 9.0`. Исторические ссылки/границы описаны в
[отложенном кандидате](deferred-storage-backed-query-fill.md).
Разделять платформенный XBQL, standalone исполнитель и явный адаптер.
Отсутствие native Запрос не подтверждает его семантику; Script-пробы могут
подтвердить конструктор/умолчания/типизацию, а query-порядок проверяется отдельно.

Охват №39: существующая YAML-структура, автоматический конструктор,
именованное соответствие проекций полям; обычный источник №31 и дневной
СрезПоследних №33. Не создавать неизвестный тип по имени из запроса.
Позиционный fallback/пользовательский конструктор требуют самостоятельного
подтверждённого контракта; в этой группе их явно отклонять.

Подтвердить и реализовать:

- Строка, Число, Булево, Дата, Ууид и проектные ссылки, nullable-варианты;
  перечисления в пределах доказанного генератора, без произвольных cast.
- Widening T → T?, T? → T?; невозможность T? → T по одному непустому fixture
  или отбору ГДЕ. Несовместимые владельцы не объединяются по UUID/форме полей.
- Независимость от порядка проекций и полей; пропущенные допустимые поля с
  подтверждённым неявным/явным скалярным ЗначениеПоУмолчанию.
- Сохранение Обязательное/ТолькоЧтение и других объявленных модификаторов.
  Неподдержанное свойство не удаляется молча для получения компилируемого типа.
- Fresh-экземпляр результата и вложенных ссылок, объявленная изменяемость;
  прежние запросы без ЗАПОЛНИТЬ сохраняют readonly-строки №31–33.
- Пустой/одиночный/множественный результат и прежний контракт
  ЕдинственныйИлиНеопределено; native округление на дробных границах.

Реализация общая: ExecutionPlan → renderer → Script Docker → SBSL.
Python разрешает типы, AST, диапазоны и инфраструктуру; исходные параметры,
выбор строк, заполнение, формула и округление выполняются в Script.
Expected и вычисленные ответы не входят в query IR/driver. Начальная история —
отдельные входные fixtures storage, не готовые строки результата запроса.

ProjectTypes лениво генерирует YAML-структуру с полной номинальной
идентичностью. Сигнатура, исходный `новый`, аргумент/возврат helper, массив и
результат ЗАПОЛНИТЬ используют один тип. Общая сериализация/подготовка значений
работает со структурой; специальный тип/сериализатор курса запрещён.
Краткая/полная квалификация, import alias, видимость, одноимённые owners
и лексическое затенение разрешаются по декларациям.

IR фиксирует целевой owner, диапазоны ЗАПОЛНИТЬ/имени типа, типы колонок/полей,
сопоставление конструктора, defaults и модификаторы. Неизвестная/повторная
колонка, отсутствующее обязательное поле, неразрешимый/недоступный тип,
несовместимость и неподдержанный конструктор имеют точную причину/диапазон.
Неподдержанный недостижимый тип не блокирует поддержанный корень.

## 4. Состояние, переносимость и независимые критерии

Captured параметры сохраняют прежний порядок/однократность вычисления при
создании запроса; перестановка проекций не меняет этот порядок. Выполнить
заново читает текущее staging. Заполнение происходит после подтверждённых
фильтра/сортировки/ПЕРВЫЕ. Старый результат не меняется после следующей записи,
rollback, изменения нового результата или замещения истории. Чтение не
создаёт SQL-публикацию и не вызывает commit.

Создать `assignments/storage-query-fill-real` и SQL-вариант, два переносимых
проекта с другими именами/namespace и соответствующие задания. Один использует
обычный Справочник/Документ, второй — дневной СрезПоследних. Включить полную
квалификацию/alias, одинаковые краткие owners, одинаковые UUID разных владельцев,
перестановку колонок, defaults, mandatory/readonly и источник/тип в разных
подсистемах. Один номинальный тип проверяется через исходный helper/массив/новый.

Автор самостоятельно фиксирует описание, fixture, expected и баллы до запуска
работ; эталон не вызывается для вычисления ответа. Альтернативная корректная
реализация проходит по поведению; snapshot исходного метода/дерева YAML не
является критерием правильного алгоритма студента.

| Группа | Обязательные независимые случаи |
|---|---|
| История | Пусто; две валюты; несколько дат; до/на/после границы; отсутствующая валюта; nullable поля |
| Формула | Кратность не 1; нулевая кратность; ноль/дробная сумма; значения для независимого округления |
| Тип/поля | Все спроецированные поля, пропущенный Код, явный default, порядок проекций, owner-коллизии |
| Результат | Пусто/одна/несколько строк; полные поля; передача helper и массив; отдельная оценка двух корней |
| Состояние | Запись → заполнение → изменение результата → повтор запроса → rollback; старый снимок сохраняется |
| Backend | Одинаковая бизнес-семантика memory/PostgreSQL; полный независимый SQL-аудит истории/UUID/периодов |

Минимальные исполнимые мутации с SBSL FAIL: другой ресурс; перепутанные
Курс/Кратность при совместимых типах; неверная валюта/граница; потеря деления;
изменённое округление; неверная ветка отсутствия курса/нулевой кратности;
подмена default переносимого типа. Отказ компиляции не доказывает обнаружение
бизнес-ошибки. Ошибки типов/недоступность проверяются отдельными случаями.

Сохранить invalid_test, unavailablePoints, sticky инфраструктурный ERROR,
TIMEOUT и очистку после catch. Последовательность FAIL → UNSUPPORTED → PASS
не теряет статусы/баллы; ошибка fixture, API или backend не блокирует следующую
поддержанную проверку. Старые mocks остаются отдельным явно выбранным режимом;
при отказе storage автоматического fallback к ним нет.

## 5. Приёмка, артефакты и выполнение

1. Каталог: все обнаруженные запросы четырёх архивов/библиотеки и полный
   документированный перечень; источник/версия, критерий или конкретная очередь.
2. Native: доверенные пробы конструктора/defaults/readonly/widening и границы
   адаптера, сохранённые версии, исходники, stdout/stderr и первичные отказы.
3. Runtime: оба неизменённых корня ДемоСРМ напрямую, memory и PostgreSQL;
   один номинальный тип и два переносимых проекта; независимые мутации и аудит.
4. Публичные `test`/`run`: одинаковые статусы, наблюдения, баллы/причины.
   Два batch в свежих каталогах: правильная → мутированная → соседняя правильная,
   одинаковые UUID, без runtime cacheHit/утечки состояния. Проверить JSON Schema
   grading/batch/manifest/events. Scope каждого batch явно записан в отчёте.
5. Только целевые новые и реально затронутые прежние тесты query AST,
   ProjectTypes/values, planner/renderer, срезов/набора, транзакции и отчётов.
   SQL проверяет состояние/публикацию; все чистые случаи в SQL не дублировать.
   Полный discovery, 303 формы, 44 старых корня и четыре validate **не запускать**.
6. Сохранить SHA-256 архивов, очистку ресурсов, первичные сбои и отдельные
   повторы. Не менять expected/старые задания/лимиты ради зелёного результата.

Новые тесты обнаруживаются существующим nightly; расписание не менять.
Каталог и nightly должны показывать непроверенные обязательные контракты,
не превращая найденный запрос или YAML snapshot в runtime PASS.

Обновить teacher guide, runtime/query matrix, README, roadmap, next-task и

## Границы №39 и следующая очередь

№39 закрывает каталог и первую группу именованного заполнения существующей
YAML-структуры. **Он не объявляет исполнение всех query-контрактов.** Остаток
каталога получает отдельные нумерованные задания: соединения/NULL (включая
ПолучитьКурсыВалют), вычисляемые проекции/агрегаты, объединения/вложения,
остальные виртуальные таблицы, предикаты/ресурсы и сочетания. Зависимости
хранения/типов, нужные этим группам, выполняются вместе с соответствующей группой.

Позиционное заполнение, неизвестные/порождённые типы, пользовательские
конструкторы/методы, вложенные коллекции/рекурсивные структуры и новые аннотации
нуждаются в отдельном подтверждённом контракте. Динамические списки/деревья,
native/browser UI, права/сетевые API/фоновые задания, LMS и деплой сохраняют
свою очередь. Все обязательные query-контракты общего плана остаются целью;
UNSUPPORTED описывает текущий долг, не итоговую готовность системы.

Реализованы ленивый номинальный тип YAML-структуры и именованное заполнение
в общем query AST/renderer для обычного metadata-источника и дневного среза.
Defaults/mandatory/readonly переносятся в native конструктор; nullable widening,
ссылки и enum сохраняют тип. Helper, массив, новый и teacher args используют
ту же идентичность. Независимые проекции ссылок не разделяют изменяемый экземпляр.

Оба неизменённых прямых корня ДемоСРМ выполнены в memory/PostgreSQL.
Публичные test/run: по 16 PASS, одинаковые checks и 16/16 баллов.
Два переносимых проекта проверяют defaults, коллизии owners/UUID, helper/args,
состояние, capture, повторное чтение и rollback. Девять бизнес-мутаций получили
SBSL FAIL после успешного Script исполнения. Контроль: FAIL → UNSUPPORTED → PASS,
недоступный балл сохранён. Два свежих batch проверили только четыре переносимых
memory-критерия на трёх работах: баллы 4 → 1 → 4, runtime cacheHit:false.
Все 52 проверки схем grading/manifest/batch/events успешны.

Выборочный основной прогон: 27/27 тестов (14 новых и 13 затронутых прежних),
525.771 с. После исправления привязки evidence каталога добавлены две проверки:
отдельный прогон 7/7, 19.294 с; финальные повторы изменённых проверок
3/3 (27.301 с) и 1/1 (3.298 с); суммарно 29 различных тестов.
11 native-проб подтвердили конструктор и ограничения адаптера; ожидаемые
компиляционные/runtime отказы записаны отдельно. Первичные отказы SQL-наблюдения
и дневного fixture исправлены в тестовом harness; бизнес-expected и лимиты
не подгонялись. Полный discovery/303 формы/44 прежних корня/четыре validate
не запускались, CI и исходные архивы не изменены.
