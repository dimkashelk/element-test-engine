# Многострочная сигнатура и задания по новым xdump

## Индексатор

`parse_module` продолжает заголовок метода после `):`, если тип результата
перенесён на следующую строку. Граница тела начинается после полной строки типа;
вложенные generic-скобки и продолжение после `<`, `,`, `|`, `.` учитываются.
Ошибка сигнатуры по-прежнему делает `indexComplete: false`, и структурная
проверка отсутствующего метода возвращает `UNSUPPORTED`, а не ложный `FAIL`.

Регрессия на исходном `БазаЗнаний/Пространства/Пространства.xbsl:70–72`:
`ПространстваСоСтраницами` входит в индекс с типом
`Соответствие<Пространства.Ссылка, Массив<СтраницыПространств.Ссылка|ЧерновикиСтраницПространств.Ссылка>>`;
`indexComplete` у модуля — `true`. Тест также проверяет первую строку тела и
отдельный неполный индекс с исходами `PASS`, `UNSUPPORTED`.

## Задания на основе исходников

По выбору пользователя исходные проекты приняты за эталон поведения. Это
контрольные задания для данного эталона; отдельные учебные требования и бюджет
баллов не предоставлены. Ожидания выведены из указанных строк исходников.

| Задание | Источник | Критерии | Баллы |
|---|---|---:|---:|
| [ДемоСРМ](../../assignments/demo-srm/assignment.yaml) | `Мероприятия/Задачи.yaml`, `СтатусМероприятия.yaml`, `Задачи.Объект.xbsl:11–13` | 5 структурных, 2 runtime | 9 |
| [check OData](../../assignments/check-odata/assignment.yaml) | `Проверка/ИнтерактивноеДобавлениеКритериев.yaml`, `.xbsl:255–270` | 3 структурных, 7 runtime | 12 |

В `ДемоСРМ` проверяются документ задачи, поля `Владелец` и `Статус`, статус
`Запланировано` и сигнатура обработчика. Runtime-сценарии требуют присвоить
переданную ссылку на сделку как новому, так и ранее заполненному владельцу.
Они различают пропуск присвоения и сохранение старого владельца.

В `check` проверяются интерфейсный компонент и две сигнатуры. Для ссылки
OData проверяются пробелы и завершающие `/`; для ответа — 200, 0, 401, 403 и
404. Исходное условие возвращает `false` для четырёх исключённых кодов и
`true` для 200. Контролируемое изменение `returnType` в тесте даёт `FAIL`.

`check/Проект.yaml` объявляет `e1c::БазаЗнаний` 1.1.1. Тест проверяет точную
идентичность подключённой библиотеки в составной модели. Выбранные методы
OData не вызывают библиотеку; прямых импортов её пространств и обращений к
её объектам в XBSL приложения не найдено. Библиотечные методы сейчас лежат в
отдельной модели, поэтому критерии `method` и runtime для них в задание
`check` не включены: нужен отдельный контракт обращения к библиотеке.

## Проверка

- `python3 -m unittest discover -s tests -p 'test_algorithm_corpus.py' -v` —
  8 тестов прошли, включая реальную сигнатуру и неполный индекс.
- `python3 -m unittest discover -s tests -p 'test_reference_assignments.py' -v` —
  2 теста прошли: оба задания загружены, структурные критерии на эталоне дают
  `PASS`, контролируемые неверные типы дают `FAIL`, все runtime-сценарии
  создают Script-модули без ошибки адаптации.
- На исходном `ДемоСРМ` команда `test` дала 5 `PASS` и 2 `UNSUPPORTED`
  (`backend_unavailable`): Docker daemon в текущей среде недоступен. Отчёт:
  `result/demo-srm-reference/`.
- Исходный `check` не загружается из-за `\\'` в YAML на строке 112. Только во
  временной распакованной копии два экранирования заменены на обычные `'`;
  составная модель загружена с библиотекой, а `test` дал 3 `PASS` и 7
  `UNSUPPORTED` по той же причине. Отчёт: `result/check-odata-reference/`.
  Исходный xdump не изменён.

Runtime-ожидания основаны на чтении эталона и пока не подтверждены выполнением
его бизнес-логики в Docker. После запуска Docker следует повторить оба задания,
сверить `expected`/`actual` и отдельно проверить контролируемый runtime `FAIL`
на копии ожиданий. Отчёт по временно исправленному `check` не является
результатом запуска исходного xdump.
