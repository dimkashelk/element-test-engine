# Задание №54: тегированное хранение ссылочных union объекта

Статус: **сформировано, не реализовано**. P0. Зависимости: №50–51; от №53 не зависит.
Основание: [очередь](../dvizhok-final-verification-plan.md), текущая проба сохранения поступления денег.

## Проблема и требуемый результат

`ПоступлениеДенежныхСредств.Основание` имеет тип `Заказ.Ссылка|СчетНаОплату.Ссылка|?`.
`metadata_lifecycle.object_validation` отклоняет запись с несколькими ссылочными вариантами.
Нужен общий путь сохранения и повторной загрузки поля с сохранением конкретного номинального
типа ссылки. Одинаковый UUID двух разных типов не должен делать ссылки взаимозаменяемыми.

## Работа

1. Определить внутренний формат ссылки: полный владелец типа и идентификатор,
   nullable отдельно от пустой ссылки. Тип разрешать по метаданным/импортам, не по форме JSON,
   порядку членов union или имени бизнес-поля. Неоднозначный вход требует явного тега.
2. Применить один codec к реквизитам и полям ТЧ сохраняемых справочников/документов,
   снимкам `До`, текущему объекту, повторной загрузке, snapshot и SQL-аудиту. Учесть nullable
   union; прежние одиночные ссылки и скалярные union сохраняют публичный контракт.
3. Обеспечить переходы вариант A → B → NULL → A, сравнение и проверку типа, разрешение
   ссылок и загрузку соответствующего владельца. Ссылки одного типа с одним ID равны по
   идентичности; ссылки разных типов с тем же ID различимы. Снимки независимы от живого объекта.
4. Согласовать codec с уже существующими тегами union-регистратора и query/report-адаптерами:
   поле основания проходит запрос, наблюдение и формулу без потери типа. Не объединять
   разные owner при индексировании и сохранении.
5. Сохранить атомарность отказа обработчика: прежний вариант, идентификатор и связанные
   движения восстанавливаются вместе. SQL хранит различимую типовую идентичность;
   независимый аудит проверяет её, а не повторяет ответ runtime.
6. Указать формат в контракте/IR и версионировать изменение публичного наблюдения, если
   оно необходимо. Не переписывать старые expected массово ради нового внутреннего формата.
   Проверить профили Строка/Ууид и границы 9.0 исходника / 9.3-current executor.

## Обязательные технические сценарии

| Случай | Проверяемое свойство |
|---|---|
| A и B имеют одинаковый UUID | После round trip сохраняется разный номинальный тип |
| A → B → NULL → A | Свежая загрузка и независимый `До` различают все переходы |
| Несколько строк ТЧ с A/B/NULL | Порядок, повторы, тип каждой строки и отсутствие алиасинга |
| Ссылка с нулевым UUID и NULL | Различимы; обязательность проверяется по объявленному правилу |
| Одинаковые короткие имена в двух namespace | Разрешение по полному owner, без случайного выбора |
| Неизвестный тег, чужой тип, неверный ID | Ошибка задания; неоднозначность не угадывается |
| Объектная запись с ошибкой в `ПослеЗаписи` | Прежний тег и связанные регистры восстановлены |
| Чтение поля запросом/формулой и загрузка ссылки | Верный владелец и свежие данные |

Memory/PostgreSQL должны давать эквивалентные нормализованные наблюдения и независимый
аудит. Обязателен переносимый fixture с другими владельцами и типами, без имени Основание.

## Приёмка и артефакты

- Декларативная запись `ПоступлениеДенежныхСредствФормаОбъекта` с `storage.lifecycle: true`
  проходит план и генерацию без отказа по ссылочному union; исходник и режим проекта сохранены.
- Все технические случаи исполнены в обоих backend. Существующие одиночные ссылки,
  скалярные union и регистраторы проходят затронутую регрессию.
- Публичные `test/run/batch` сохраняют SBSL PASS/FAIL/UNSUPPORTED, корректные причины
  недоступности и веса. Намеренно неверный тег/expected не приводит к ложному PASS.
- Создать контракт codec, технические тесты и измерения №54; показать свежие планы точного
  финального исходника отдельно от исполнения fixtures. Бизнес-сценарии денег — №56.

Произвольные объектные union, миграция внешней production-базы, native доступ и удаление
ссылочных объектов не входят в этот контракт. Работа идёт с изолированным тестовым хранением.
