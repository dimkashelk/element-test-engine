## Цель и измеримый охват

Поддержать ограниченные эффекты формы в общем pipeline
`ExecutionPlan → renderer → Script Docker → SBSL`: запись текущего объекта
и типизированный запрос открытия другой формы. Исполнить и независимо
оценить три дополнительных прямых корня исходного архива:

| Namespace / модуль | Прямой корень | Наблюдаемый результат |
|---|---|---|
| CRM / СделкаФормаОбъекта | АрхивироватьОбработчик | Переключённый флаг, сохранённый объект и текст команды |
| Продажи / ЗаказФормаОбъекта | АрхивироватьОбработчик | Переключённый флаг, сохранённый объект и текст команды |
| Продажи / ЗаказФормаОбъекта | ОтгрузитьОбработчик | Полный запрос открытия с перенесёнными строками и итогами |

Итог — **38/44 независимо оценённых методов**, сохранены прежние 35 корней.
Архив содержит 75 файлов (46 YAML, 29 XBSL); SHA-256:
`c69ddf9247d0508207e3ab80c4ae87c782e8d876503487ee6fcc01105bccec97`.
Каждому корню нужен отдельный критерий и реальная оценка SBSL. Вызов helper,
подготовленный план и отсутствие диагностик не считаются прямой оценкой.

Python разрешает декларации, готовит fixtures и собирает наблюдения.
Исходные условия, присваивания, циклы, итоги, перенос строк и последовательность
вызовов исполняются в Script. Запрещены специальные ветки по именам проекта,
форм, реквизитов, методов и критериям, вычисление бизнес-результата в Python,
готовый ответ из mocks или изменение исходного архива.

## Проверенная исходная точка

В карте №35 все три корня имеют контрольные критерии UNSUPPORTED:
`Сделка_unsupported_АрхивироватьОбработчик`,
`Заказ_unsupported_АрхивироватьОбработчик`,
`Заказ_unsupported_ОтгрузитьОбработчик`.
`form_context.bind_form_call` останавливает их на эффектах Записать/Открыть
вне контракта №34. Это граница адаптера, не ошибка студенческой логики.

Оба исходных АрхивироватьОбработчик переключают Объект.Архивный,
вызывают **неявный `Записать()` формы**, затем исходный
ОбновитьПредставлениеАрхивирования. У Сделка нет объектного XBSL-модуля;
у Заказ объектный модуль содержит ПриСозданииНаОсновании. Этот обработчик
не должен запускаться вследствие обычной записи.

ОтгрузитьОбработчик вызывает исходный РассчитатьИтоги(Параметр), затем
`Товары::Отгрузка.СоздатьЧасть(Параметр)` и
`Товары::ОтгрузкаФормаОбъекта.Открыть(...)`. СоздатьЧасть создаёт новый
Отгрузка.Объект и вызывает исходный ПеренестиТабличнуюЧасть. Последний
создаёт новые строки, копирует Номенклатура/Количество/Цена/Сумма и добавляет
их в документ. Записи отгрузки в этой цепочке нет.

Открыть получает только пять именованных свойств формы: СозданныйНаЧасти,
ТоварыТабличнаяЧасть, КоличествоВыбранныхСтрок, КоличествоТоваров,
СуммаВыбранныхТоваров. Сам НовыйДокумент не передаётся как Объект формы.
Нельзя незаметно связать целевую форму с этим документом или запустить
ПередЗаписью/ПослеЗаписи отгрузки. YAML-выражение Источник таблицы не входит
в нынешнее исполнение; standalone-наблюдение не доказывает браузерный UI.

## Технический контракт перед реализацией

Создать `docs/form-effects.md` с семантикой и границами. Сверить официальную
документацию и доступные native-пробы для Записать формы, Открыть, параметров
создания формы, завершения записи и жизненного цикла. Если UI API отсутствует
в standalone Script либо документация недоступна, зафиксировать это и объявить
ограниченный адаптер явно; не выдавать его за native платформенную реализацию.

Эффекты включаются явным контрактом преподавателя. Уточнить в техническом
документе формат opt-in, разрешённые операции/формы, типы и наблюдения.
Прежние задания без opt-in сохраняют три ожидаемых UNSUPPORTED; новые критерии
проверяют поддержанные эффекты. Не расширять область доступных API молча.
Expected и готовые итоги не входят в execution IR, renderer и driver.

Разрешение системного вызова опирается на AST, YAML, namespace/import,
тип получателя и области видимости. Собственный метод Записать/Открыть,
локальный получатель, параметр или import alias не подменяется глобальной
заменой текста. Неизвестные свойства, повторные аргументы, несовместимые типы,
неоднозначный owner и неподдержанные перегрузки получают точную причину
подготовки с исходным файлом/диапазоном. Отказ одного критерия не блокирует
следующий поддержанный критерий.

## Запись объекта формы

Неявный Записать() связывается с объектом именно текущего экземпляра формы
и переиспользует declaration-driven storage №29–33. Нужны memory и PostgreSQL,
полный owner/namespace + native UUID, реальные реквизиты/табличные части,
передача исходных ПередЗаписью/ПослеЗаписи при их наличии и наблюдаемый trace.
Простой spy «Записать вызван» не заменяет сохранённое состояние.

Сначала определить идентичность, новизну и связь `context.Объект` с
`storage.initial`. Для существующего объекта подготовить согласованную ссылку
и исходный снимок. Для нового — явно описать создание ID и смену isNew после
успешной записи; Номер/expected не определяют новизну. Проверить новый объект
с непустым номером и существующий с пустым. Автонумерация, уникальность и
валидация всех YAML-ограничений не считаются реализованными автоматически.

Проверить границу фиксации операции и внешний `storage.transaction` отдельно.
В исходных обработчиках нет транзакционного ресурса; нельзя приписать им
исходную транзакцию. Семантика успешной записи и последующей ошибки должна
быть явно определена. Переиспользовать прежний контракт commit/rollback,
не создавать второй backend специально для форм.

При отказе исходного обработчика записи и техническом SQL-сбое проверить
независимо storage, in-memory Объект и свойства формы. Изменение флага до
неуспешной записи не означает его фиксацию в БД; откат БД не доказывает откат
клиентского экземпляра. Зафиксировать, что сохраняется и что восстанавливается.
Не выполнять следующий helper как будто запись завершилась успешно.
SQL-аудит читает реальную БД доверенной инфраструктурой, а не журнал вызовов
или возвращённый студентом снимок; инфраструктурный сбой не становится PASS.

## Запрос открытия формы

Разрешить owner целевой КомпонентИнтерфейса и именованные параметры по YAML
Свойства, включая закрытые типы массивов и nullable-ссылок. В момент вызова
сохранить независимый снимок: полный owner, порядок запросов, имена/значения
переданных свойств. Отсутствующий аргумент и явно переданное значение различаются;
умолчания применяются только при создании целевого контекста.

Это наблюдение запроса открытия, не настоящий клиентский UI. Один критерий
должен отдельно передать реальные параметры запроса в новый целевой контекст
и исполнить исходный ОтгрузкаФормаОбъекта.ПослеСоздания по явно объявленному
контракту lifecycle. Проверить ЗаголовокФормы и ТекстИтоговЧасти. Не вызывать
этот обработчик автоматически без технического контракта. Не вычислять
YAML-привязки таблицы и не считать документ записанным вследствие Открыть.

Сохранять источник и диапазон вызова, owner/type каждого параметра,
source dependencies, фактические запросы и trace. Повторное открытие создаёт
новый снимок; последующая мутация массива не переписывает прежний журнал.
Журнал не должен разделять изменяемые значения между формами/критериями.
Неподдержанные способы открытия и API пассивных команд остаются явными отказами.

## Независимые приёмочные сценарии

Для каждого АрхивироватьОбработчик обязательны оба начальных флага,
новый/существующий объект, пустой/непустой номер и sequence двух переключений.
Проверить тексты «Вернуть из архива» / «Архивировать», запись под точной ссылкой,
сохранность всех нецелевых реквизитов/таблиц и соседних объектов, порядок
Записать → helper. Sequence наблюдает состояние каждой операции и выполняет
повторное чтение из storage. Обязательны memory и PostgreSQL, отказ записи,
rollback внешней оболочки и поддержанный успешный сценарий после отказа.

Для ОтгрузитьОбработчик нужны пустой массив, одна строка, несколько строк,
повторные товары/строки, нулевые и дробные количество/цена/сумма,
nullable-номенклатура и native UUID. Параметр может быть выбранным подмножеством
Объект.Товары через явный fixture; обработчик не должен брать всю таблицу.
Сумма не обязана равняться Количество × Цена: независимый fixture должен
обнаруживать неверный пересчёт вместо переноса исходного поля.

SBSL сравнивает полный запрос открытия, количество и порядок строк,
все четыре поля каждой новой строки, флаг СозданныйНаЧасти=Истина и три итога.
Нужны snapshotArgs/contextPath и сохранность исходного заказа. Trace подтверждает
вызовы РассчитатьИтоги → СоздатьЧасть → ПеренестиТабличнуюЧасть → Открыть;
storage подтверждает отсутствие записи отгрузки и движений регистров.
Проверить два открытия в sequence с разными данными и отсутствие aliasing
между исходными строками, новым документом и снимками открытия.

Создать переносимые проекты как минимум с двумя другими наборами имён:
объекты, формы, поля, таблицы, методы, namespace и import alias. В разных
подсистемах использовать одинаковые краткие owners; в работах — одинаковые UUID.
Проверить проектные одноимённые методы и лексическое затенение. Общий planner
должен выбирать один и тот же механизм по декларациям, а не по Dvizhok.

## Мутации и публичные команды

Мутации временных копий должны независимо обнаруживаться как FAIL через SBSL:
неверное переключение флага; пропуск записи; запись другого объекта;
неверный текст helper; потеря нецелевого реквизита; пропуск/перестановка строк;
порча каждого переносимого поля; изменение входной таблицы; неверные итоги;
неверный флаг/owner/параметр Открыть; отсутствие или лишний запрос открытия.
Мутации РассчитатьИтоги и обоих helper Отгрузки обнаруживаются через исходный
ОтгрузитьОбработчик. Их вызов не даёт прямой оценки этих helper в карте.

Все три новых корня выполнить через публичные test и run на исходном xdump;
сравнить статусы, наблюдения и баллы. Два настоящих batch в свежие output
включают две правильные работы и одну мутированную: UUID совпадают,
storage/контексты различаются, соседние результаты изолированы. Проверить
новые критерии memory/SQL, fresh state, sequences и отсутствие runtime cacheHit.

Сохранить исходные задания №34/35 и их контрольные границы. Новые поддержанные
критерии эффекта находятся в отдельном задании с явным opt-in. Отказы формата
преподавателя, неподдержанный API, ошибка исполнения и FAIL бизнес-результата
не смешиваются; баллы и unavailablePoints следуют прежнему SBSL-контракту.

## Финальная проверка

Реализован общий opt-in formEffects: синхронная запись текущего объекта через
прежнее storage, типизированные запросы открытия по YAML и явно объявленный
lifecycle целевого контекста. Бизнес-логика остаётся исходным XBSL; Python
не рассчитывает перенос/итоги. SQL-снимки каждой фиксации строятся SELECT
по фактической БД и независимо читаются административным аудитором.
[Технический контракт](../form-effects.md) фиксирует ограничения standalone.

Публичные test/run дали каждый **46/46 PASS**, совпали наблюдения/баллы,
выполнены три новых прямых корня в memory/PostgreSQL.
[Карта](../dvizhok-coverage-after-036.md) подтверждает **38/44** с сохранением
прежних 35 методов. Свежие прежние задания: 74 PASS + 3 ожидаемых UNSUPPORTED
для №34, 70 PASS для №35, 22 PASS для прежних бизнес-критериев.

Полная последовательная регрессия: **266/266 без пропусков**, включая
все прежние 246 тестов. 24 временных мутаций дали независимый FAIL;
два переносимых проекта проверили имена/namespace/alias, собственные методы,
затенение и snapshots. Два свежих batch дали каждый 2 passed / 1 failed и
нулевой cacheHit. SQL-сбой остался ERROR; проверены отказ до/после записи для
новых/существующих объектов, успешный следующий критерий, поздняя ошибка и
внешний rollback в обоих backend.

Первичная приёмка содержала ошибки fixtures (native имя исключения,
недостижимый код и YAML anchors), а проверка исходных методов выявила
компоновку lifecycle без alias. Первичные журналы сохранены; исправленные

Четыре validate прошли; grading/batch/manifest/events соответствуют JSON Schema.
