# Этапы 4–5: типы в теле метода и структурные проверки

Runtime анализирует типы в локальных объявлениях `пер`/`знч`, приведениях
`как` и конструкторах достижимых методов. Разбор учитывает вложенные generic,
union, комментарии и интерполяцию. Квалифицированные проектные типы приводятся
к имени SBSL только после проверки точного владельца. Конфликт одинаковых
кратких имён и циклическая зависимость типов завершаются недоступной проверкой,
а не выбором произвольного типа. Исходный XBSL не меняется; контракт создаётся
только для использованных типов.

Структурные `module` и `method` принимают точный `namespace` и `exists: false`.
Отсутствие метода в неполном индексе даёт `UNSUPPORTED`. Для `field` допустимы
только `Реквизиты`, `Измерения`, `Ресурсы`, `Константы`; совпадение имени в
нескольких коллекциях требует явного `collection`. При несовпадении свойства
возвращаются его имя, ожидаемое и фактическое значения. Статусы и баллы
по-прежнему рассчитывает SBSL.

Проверки: `tests/test_body_types.py`, `tests/test_generated_types.py` и
`tests/test_engine.py` покрывают локальные типы, вложенные generic и union,
конфликты владельцев, цикл, `exists: false`, неполный индекс, коллекции и
точную причину несовпадения. Локальный тип также скомпилирован и выполнен
Script executor. Тесты реального проекта читают `Dvizhok.xdump` напрямую;
полный набор: 88 тестов, 11 штатных пропусков, без ошибок.
