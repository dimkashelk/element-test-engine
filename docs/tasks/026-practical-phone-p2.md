# P2: исполняемое задание из `Примеры_new`

## Независимое требование

Для покупателя номер телефона корректен, только если **вся** строка состоит
из `+7` и следующих за ним десяти цифр. Вход — строка, результат — `Булево`.
Формат `+7хххххххххх` сообщается пользователю в
`РаботаСИсключениями/Покупатели.xbsl:27`; комментарий к методу на строках
52–60 требует проверять соответствие формату. Проверяемый метод —
`Покупатели.НомерТелефонаКорректен`. Интерфейс и состояние приложения не нужны.
Ожидания заданы этим правилом, а не скопированы из регулярного выражения эталона.

[Задание](../../assignments/practical-phone/assignment.yaml) проверяет справочник,
поле `Телефон: Строка`, сигнатуру метода и четыре входа: корректный номер,
неверный префикс, недостаточную длину и посторонний текст после номера.
Структурные критерии дают 3 балла, runtime — 5, всего 8. Справочник уже
поддерживается моделью; для метода общего модуля хватает имеющегося индекса.
Новых видов метаданных и платформенных моков для этого требования не нужно.

## Подтверждённые исходы

| Вход | Результат |
|---|---|
| Исходный `Prakticheskie-primery-2026-09-30-15-20.xdump` | 7 `PASS`, 8/8, `unavailablePoints = 0` в `test` и `run` |
| Временная копия, где метод всегда возвращает `Истина` | 4 `PASS`, 3 `FAIL`, 5/8, `unavailablePoints = 0` |
| [Проверка границы](../../assignments/practical-phone/fixtures/unsupported.yaml): `СоздатьИлиОбновить` с входным `Ууид` | `UNSUPPORTED`, `unsupported_contract`, 1 недоступный балл |

Контрольное изменение выполнено только во временной распаковке проекта; три
отрицательных номера стали ошибочно допустимыми. Это проверяет ошибку в исходном
методе, а не подмену `expected` в задании. Отдельный вызов
`СоздатьИлиОбновить` пока останавливается при подготовке значения типа `Ууид`:
генератор runtime не умеет этот тип, хотя анализ метаданных его распознаёт.
До записи покупателя этот сценарий не доходит, поэтому поведение хранения здесь
не заявлено как проверенное. Проверка границы лежит в `fixtures/` и не входит
в оценку основного задания.

Пакетный запуск с эталоном и изменённой копией дал соответственно `passed` 8/8
и `failed` 5/8, без `incomplete` и `inputError`. Код выхода `batch` равен 1,
поскольку в пакете намеренно есть ошибочная работа. Отчёты локальных прогонов:
`result/practical-phone-p2`, `result/practical-phone-negative`,
`result/practical-phone-unsupported`, `result/practical-phone-run` и
`result/practical-phone-batch`.

Четыре исходных xdump сохранили SHA-256 из
[отчёта по корпусу](../xdump-corpus-2026-09-30.md) и проходят `validate`:
`Движок` — 0 диагностик, `ДемоСРМ` — 29 предупреждений,
`check` — 83 предупреждения, `Примеры_new` — 213 `unsupported_element`
и один ожидаемый `dynamic_call` (всего 214 предупреждений).

Проверки: `python3 -m unittest discover -s tests -v` — 147 тестов прошли,
13 opt-in пропущены; отдельный
`ELEMENT_TEST_DOCKER_TESTS=1 python3 -m unittest discover -s tests -p 'test_practical_phone.py' -v`
— 2 теста прошли. Исходный XBSL исполнялся Script executor режима 9.0 в Docker;
баллы и сравнение определял SBSL-движок.

## Дальнейшая граница

Этот P2 подтверждает один сценарий четвёртого архива. Для новых учебных
требований из него следует отдельно выбирать наблюдаемый эффект. Runtime
`Ууид` и запись произвольного покупателя расширять только вместе с заданием,
которому они нужны. Предупреждения по остальным видам метаданных не превращаются
в ошибки студента.
