# Движения, остаток и состояние ссылки в одной проверке

По уточнению пользователя параметры записи в текущую работу не входят.
Сценарий [`poc-shipment-sequence`](../../assignments/poc-shipment-sequence/assignment.yaml)
использует уже ограниченный SQL-адаптер отгрузки и оригинальные обработчики
`Отгрузка.ПередЗаписью`/`ПослеЗаписи` из `Dvizhok.xdump`. Выполнение идёт
в Script executor и изолированной PostgreSQL; баллы считает SBSL.

Начальный приход — 5 единиц товара `a`. В одной проверке:

1. Отгрузка `shipment-a` на 3 записывается и создаёт расход.
2. `load-fresh` дважды загружает документ. Очистка табличной части первого
   снимка в памяти не меняет второй снимок и сохранённые строки.
3. Отгрузка `shipment-b` на 3 отклоняется, потому что после первого расхода
   доступно 2. Повторная загрузка ссылки `shipment-b` возвращает `null`.
4. Отгрузка `shipment-c` ровно на 2 записывается. Независимый аудит БД видит
   только документы `a` и `c`, приход 5 и два расхода 3 и 2.

Это проверяет чтение сохранённых движений последующим исходным запросом
остатков, откат отказа и свежесть снимков в пределах **одной** проверки.
Ожидания выведены из исходного обработчика; отдельное учебное требование не
предоставлено. Контракт относится к SQL-адаптеру: чистые `mocks.objects`
по-прежнему возвращают свежие снимки и не хранят изменения, а общая семантика
платформенного API не заявлена.

Публичный CLI с `--integration`: `PASS`, 4/4, `unavailablePoints = 0`, отчёт
`result/poc-shipment-sequence`. Контрольный пакет в
`result/poc-shipment-sequence-negative` дал `FAIL` для неверного ожидаемого
количества движения, `UNSUPPORTED/unsupported_contract` для неизвестного
действия и последующий `PASS`: 4/8 доступных баллов, 4 недоступных.
