# Завершённое задание №12: массовый запуск студенческих работ

Основание: этап 8 [плана](../roadmap.md) и завершённый
[контракт оценки](011-grading-contract.md). Один запуск `test` уже создаёт
`result.json`, `grading.json` v1.0 и `report.html`; работа отдельного студента
изолирована. Следующий этап должен принимать партию архивов и продолжать её
обработку при ошибке одного входа. Приложения студентов и LMS недоступны.

## Цель и интерфейс

Добавить CLI:

```bash
bin/element-test batch --manifest <batch.json> --output <каталог> \
  [--workers 1..4] [--integration]
```

По умолчанию один worker; `--integration`
явно включает существующий PostgreSQL-режим и не подменяет его mocks. Manifest
находится у преподавателя отдельно от студенческих проектов. Пример:

```json
{
  "schemaVersion": "1.0",
  "assignment": "assignments/demo",
  "assignmentId": "demo",
  "submissions": [
    {"studentId": "student-001", "project": "incoming/001.tar"},
    {"studentId": "student-002", "project": "incoming/002.xdump"}
  ]
}
```

Пути во входном manifest разрешаются относительно самого manifest; `project`
принимает каталог, tar или xdump через существующий безопасный загрузчик.
Проверить версию manifest, обязательные поля, уникальность `studentId` в партии,
тип/существование входов, отсутствие выходного каталога внутри любого проекта и
повторные/коллидирующие пути **до** запуска workers. В `batch-result.json`,
`grading.json`, HTML и событиях не публиковать входные пути и секреты.
Внутренние каталоги результатов именовать безопасным порядковым номером или
хэшем, а не напрямую `studentId`. Для каждой работы сохранять независимые
`result.json`, `grading.json`, `report.html`; `assignmentId` берётся из manifest,
`runId` уникален для каждой работы (например, ID партии и порядковый номер),
чтобы не смешивать результаты разных студентов.

## Выполнение и изоляция

1. Вынести запуск одной работы из CLI в повторно используемую функцию/процесс,
   сохранив поведение `test`/`run`, SBSL-оценивание, статусы и коды CLI. Не
   переносить подсчёт баллов в Python.
2. Реализовать ограниченный пул отдельных процессов. Для каждой работы — свой
   временный каталог, собственное исполнение проверок и отдельные Docker-ресурсы
   на runtime-проверку. Один повреждённый архив, `ERROR`, `TIMEOUT` или
   `UNSUPPORTED` не останавливает очередь; ошибка manifest останавливает до
   запуска. При SIGINT и исключениях завершать workers и очищать ресурсы.
3. Писать `events.jsonl` по мере завершения работ: начало партии, начало работы,
   завершение проверки (когда результат доступен), завершение работы и партии.
   Событие содержит безопасные идентификаторы, статус и баллы, без сырых логов,
   ожидаемых/фактических значений, путей и данных подключения. Запись должна
   быть атомарной по строкам и пригодной для чтения во время выполнения.
4. Создать `batch-result.json` с версией схемы, идентификатором партии, итоговыми
   счётчиками `passed`/`failed`/`incomplete`/`inputError` и ссылками **относительно
   output** на пакеты каждой работы. Дать JSON Schema для manifest, индекса и
   событий. Отдельный `inputError` не превращать в `FAIL` студента и не
   подставлять фиктивный `grading.json`.

## Кэш

Постоянный локальный кэш должен использовать ключ из нормализованного
`sourceHash`, содержимого всех файлов задания, версии движка/контракта,
режима и конфигурации runtime (включая образ). Не доверять имени архива или
времени файла. Писать запись атомарно, проверять её схему/ключ при чтении и
исключить гонку двух workers за один ключ.

Повторно использовать только завершённые детерминированные результаты, у
которых все проверки имеют `PASS` или `FAIL` и `unavailablePoints == 0`.
Не кэшировать `ERROR`, `TIMEOUT`, `UNSUPPORTED`, `SKIPPED`, ошибки входа,
результаты с `runtimeDateTime`, текущим временем или непредсказуемым внешним
состоянием. Если детерминированность runtime-критерия не доказана, выполнить его
заново. При cache hit создать новый пакет с идентификаторами текущей работы,
не переносить `studentId`/`runId` прежнего запуска. Кэш не должен изменять
баллы или обходить SBSL при cache miss.

## Проверки и артефакты

- Партия из структурных работ: одинаковые результаты при `--workers 1` и `2`,
  уникальные пакеты и корректный индекс; входные архивы побайтно неизменны.
- Повреждённый архив между двумя корректными даёт только свой `inputError`;
  последняя работа всё равно завершается. Дубликаты ID и ошибочный manifest
  отвергаются до первого запуска.
- Повтор партии даёт cache hit только допустимым работам. Изменение исходника,
  одного файла задания, версии/конфига runtime или режима аннулирует запись.
  Неполный результат после отсутствующего Docker не возвращается из кэша.
- Отрицательное ожидание остаётся `FAIL` из SBSL; `ERROR`/`TIMEOUT` и
  `UNSUPPORTED` остаются недоступными баллами. Все `grading.json` соответствуют
  [схеме v1](../grading-v1.schema.json), индекс и события — своим схемам.
- При доступном Docker запустить runtime и SQL-регрессию с двумя workers,
  проверить отсутствие оставшихся контейнеров/сетей и сравнить результаты с
  одиночной CLI. Сохранить JSON/HTML/JSONL/журнал и измерения времени/памяти в
  `result/poc-batch-runner`.
- Обновить README, roadmap и это задание по фактическим результатам. Не
  подключать LMS и внешнюю сеть.

## Результат

- `bin/element-test batch` запускает 1–4 отдельных процесса. Ошибка manifest
  останавливает запуск до создания output; повреждённый архив получает
  `inputError`, а следующие работы завершаются. Пакеты хранятся в каталогах
  с порядковыми номерами, `runId` уникален; входные файлы не изменяются.
- [Manifest](../batch-manifest-v1.schema.json),
  [индекс](../batch-result-v1.schema.json) и
  [события](../batch-events-v1.schema.json) имеют схемы v1. JSONL пишется
  построчно по мере завершения работ. Локальная проверка 73 manifest,
  индексов, событий и пакетов оценки против полей схем прошла.
- Ключ кэша включает `sourceHash`, содержимое всех файлов задания, исходники
  движка и SBSL, контракт, конфигурацию runtime/SQL, режим и образ.
  Запись атомарная с межпроцессной блокировкой; старые идентификаторы не
  сохраняются в кэше. Кэшируются только полностью завершённые структурные
  результаты PASS/FAIL. Runtime и SQL каждый раз выполняются заново.
- Структурный прогон с двумя workers: 2/2 работы по 6/6 критериев; повтор
  использовал кэш для обеих работ. Отрицательная проверка остаётся FAIL из
  SBSL; UNSUPPORTED сохраняет недоступные баллы и в кэш не попадает.
  Повреждённый архив между двумя корректными работами не остановил очередь.
- Локальная регрессия: 78 тестов, 11 пропусков. Docker runtime с двумя
  workers: 2/2 работы по 3/3 критериям; SQL с двумя workers:
  2/2 по 2/2. Баллы/статусы каждого критерия совпали с одиночным CLI.
  Контейнеров/сетей `element-test-*` и `element-integration-*` после
  запусков нет. Время runtime-партии 18,48 с против 8,83 с для одной работы;
  SQL-партии 19,63 с против 10,34 с. Максимум RSS по `/usr/bin/time -l`:
  245/233 MiB для runtime, 243/233 MiB для SQL.
  Артефакты и журналы: `result/poc-batch-runner`.

Docker-зависимые 11 тестов полной регрессии в локальном sandbox пропущены;
отдельные runtime и SQL прогоны выполнены с доступом к daemon. Полный набор
`ELEMENT_TEST_DOCKER_TESTS=1` в этом цикле не запускался.
