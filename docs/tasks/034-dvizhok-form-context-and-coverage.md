# Задание №34: контекст форм и карта полного покрытия Dvizhok

Статус: **реализовано в указанном охвате**, 2 октября 2026 года.
Приоритет пользователя: двигаться к полной проверке `Dvizhok.xdump`.
Основание: [результат №33](033-storage-backed-information-register-slices.md#отчёт-о-реализации),
[универсальный runtime](../universal-runtime.md) и
[свежая карта дампа](../dvizhok-coverage-baseline.md).
Результат №33 зафиксирован коммитом `d5faefd`.

Предложение о ЗАПОЛНИТЬ для ДемоСРМ
[отложено](deferred-storage-backed-query-fill.md). В Dvizhok нет запроса
с этим предложением; его реализация не закрывает главный пробел данного дампа.

## Цель и измеримый охват

Выполнять исходную логику форм объектов в Script executor через ограниченный,
генерируемый из YAML контекст формы. Добавить сквозную карту файлов, методов,
сценариев и причин недоступности, чтобы полная проверка дампа измерялась
фактическим исполнением и независимой оценкой.

Свежий разбор неизменённого `Dvizhok.xdump` дал 75 файлов — 46 YAML и
29 XBSL, 40 объектов и 44 метода, без диагностик текущего анализатора.
Восьми модулям форм принадлежат **29 из 44 методов**. В существующих публичных
заданиях обнаружены 8 уникальных прямых runtime-target; это число объявленных
корней, а не доказательство покрытия всех зависимостей и веток.
Подробные факты и SHA-256 — в
[JSON-карте](../dvizhok-coverage-baseline.json).

Обязательный runtime-охват №34 — **20 методов семи форм объектов**, включая
уже проверяемый РассчитатьИтоги. Для остальных методов сохранить явный
статус и следующий необходимый контракт. №34 является этапом к полной
проверке; нельзя назвать дамп полностью проверенным после этих 20 методов.

Один planner → renderer → executor → SBSL обслуживает `test`, `run`, `batch`.
Python разрешает метаданные, типы, имена и диапазоны, генерирует контекст
и инфраструктуру. Исходные циклы, условия, вызовы helper и изменения состояния
выполняет Script; сравнение и баллы определяет SBSL. Имена Заказ, Сделка,
компонентов и методов не выбирают реализацию адаптера.

## Подтверждённый исходный барьер

До №34 для `Продажи::ЗаказФормаОбъекта.ПослеСоздания` planner отклонял
context: `context допустим только как объект для модуля Объект`.
Без контекста команда редактирования останавливается на типе ОбычнаяКоманда.
Это подтверждено вызовом planner на исходном дампе; бизнес-код на host не
исполнялся. Снятие одного барьера не означает поддержки всего обработчика.

Типичный исходный обработчик:

```xbsl
метод ПредставлениеРедактированиеДанныхОбработчик(Команда: ОбычнаяКоманда)
    если РедактированиеДанных
        РедактированиеДанных = Ложь
        ПредставлениеРедактированиеДанных = "Разрешить редактирование реквизитов"
    иначе
        РедактированиеДанных = Истина
        ПредставлениеРедактированиеДанных = "Запретить редактирование реквизитов"
    ;
;
```

Реквизиты формы объявлены в YAML `Свойства`; тип Объект берётся из
`Наследует.Тип: ФормаОбъекта<...>`. Компоненты с именами и их типы объявлены
во вложенном дереве `Наследует.Содержимое`. Контекст нельзя составлять
произвольными полями, угаданными из текста одного обработчика.

## Обязательный результат

### 1. Карта покрытия всего дампа

Сохранить воспроизводимую инвентаризацию всех 75 файлов и 44 методов.
Полная идентичность метода включает проект, namespace, модуль, файл и имя.
Для каждого файла указывать роль, применимые проверки и диагностики.
Для каждого метода — прямые критерии задания, достижимые зависимости,
сценарии/ветки, execution plan, фактический статус и ссылку на журнал.

Разделять сведения:

- Файл прочитан и проиндексирован; ограниченная статическая проверка пройдена.
- Для метода существует критерий; подготовлен план; метод действительно вызван.
- Результат/побочный эффект независимо оценён SBSL; проверена конкретная ветка.
- Выполнение недоступно с причиной; для метода пока нет сценария/ожидания.

Пустой XBSL-модуль не получает runtime PASS за отсутствие методов.
Отсутствие диагностик validate не считать платформенной компиляцией.
Вызов helper как зависимости не заменяет проверку его значимых веток.
Нераспознанные свойства/выражения формы не должны исчезать из карты.
Карта должна обнаруживать новый файл/метод после изменения архива, а не
содержать захардкоженные списки как единственный источник данных.

YAML форм проверить отдельно: свойства, тип основания формы, уникальность
именованных компонентов, ссылки на собственные обработчики и их сигнатуры
в достижимом поддержанном охвате. Встроенные команды и выражения вроде
RowData/Объект учитывать как отдельные контракты; не объявлять их неверными
лишь потому, что они не являются собственными XBSL-методами. Полная оценка
всех декларативных выражений и браузерного поведения остаётся в карте
непроверенной до соответствующих следующих этапов.

### 2. Контракт состояния формы

Добавить в общий ExecutionPlan разрешённый контекст КомпонентИнтерфейса,
унаследованного от ФормаОбъекта<T>. Различать его с существующим контекстом
модуля Объект и с чистым методом внутри модуля формы. Текущий poc-order
без context должен остаться совместимым.

Контекст содержит типизированный Объект, собственные свойства формы и
доступные именованные компоненты. Умолчания свойств брать из YAML либо
подтверждённого умолчания типа. Доступ через `этот`, неявное имя свойства
и Компоненты.<имя>.<свойство> привязывать по декларации и лексической области.
Локальная переменная/параметр с тем же именем сохраняет своё значение.
Не заменять все совпадения идентификатора регулярным выражением.

Поддержать используемую здесь Надпись.Значение типа Строка. Компоненты
расположены в разных вложенных группах/страницах; перечисление должно
находить их по YAML-дереву, не требуя одной позиции в Содержимое.
Неизвестный компонент, свойство, повторное имя и неверный тип входа/observe
имеют явную диагностику. Fixture не может добавлять недекларированный
компонент, чтобы ошибочное имя в исходнике стало успешным.

ОбычнаяКоманда и КомандаСПараметром<Массив<T>> нужны как аргументы исходных
сигнатур. В данном этапе это объявленные типизированные пассивные значения:
обработчики не обращаются к их API. Достижимое использование неподдержанного
свойства/метода команды даёт UNSUPPORTED, а не молчаливую заглушку.

Объект.ЭтоНовый() должен читать явно заданное состояние жизненного цикла
объекта тестовой сессии. Установить его контракт до реализации. Не выводить
признак из пустого Номер, отсутствия business-поля или teacher expected.
Нужны новый объект с непустым Номер и существующий с пустым Номер, чтобы
отделить состояние от эвристики. Новизна относится к объекту, а не названию
формы; интерфейсный адаптер не должен менять её вне объявленной операции.

Проверяемый результат включает объявленные observe-пути свойств,
Объект и компоненты. Повторные вызовы в одной sequence сохраняют состояние
одного экземпляра формы; критерии и batch-работы изолированы. Вложенные
объекты/массивы/ссылки не разделяют изменяемые значения между сценариями.
Сериализация и SBSL-сравнение используют общий контракт значений.

До фиксации YAML-формата задания проверить официальные сигнатуры и
доверенные native-пробы Script `-c 9.0` для генерируемых типов, полей,
default-значений, ссылок, generic-аргументов и состояния экземпляра.
Платформенные формы и команды могут отсутствовать в standalone executor:
в таком случае явно описать адаптер и не выдавать его за native UI.
Правила генерации именованных компонентов требуют отдельной сверки
официальной документации актуальной версии, а не переноса старого API
Исполнителя 4.0/5.2 по сходству названий.

### 3. Исходные helper и отсутствие эффектов вне охвата

При ПослеСоздания исходный ОбновитьПредставлениеАрхивирования исполняется
в том же экземпляре формы. ИтогиОтмеченных вызывает исходный РассчитатьИтоги.
Импорты, видимость @Локально и имена зависимостей разрешаются общим графом.
Неподдержанный соседний метод не блокирует достижимый поддержанный корень.

Записать() из формы и Форма.Открыть(...) в №34 не исполняются и не
подменяются пустым успехом. АрхивироватьОбработчик и ОтгрузитьОбработчик
остаются UNSUPPORTED с точной причиной. Они проверяются отдельными
контрольными критериями, за которыми выполняется поддержанный PASS.
Это два будущих контракта эффектов; обновление надписи без фактической
поддержки Записать не доказывает правильность архивирования.

ExecutionPlan сохраняет идентичность формы, тип объекта, поля/компоненты,
default-значения, привязки системных операций, исходные диапазоны и ограничения.
Teacher expected и готовые надписи/итоги не входят в IR и не выбирают ветку.
Общий модуль с похожими именами или проектный метод ЭтоНовый не подменяется
системным контрактом формы.

### 5. Независимая оценка и регрессия

Контролируемые мутации копий исходника должны давать FAIL через SBSL:
перепутанная ветка нового объекта, ошибочный текст заголовка, неверное
переключение редактирования, изменение обоих текстов helper на одинаковые,
потеря строки/слагаемого в сумме, неверная надпись компонента и пропуск
условия СозданныйНаЧасти. Мутацию в зависимости РассчитатьИтоги должны
обнаруживать и helper-критерий, и критерий исходного вызывающего обработчика.
Ошибочные компоненты/типы проверять отдельно как отказ подготовки.

Подтвердить прежние FAIL/UNSUPPORTED/ERROR/TIMEOUT и unavailablePoints.
Сбой инфраструктуры не становится ожидаемой бизнес-ошибкой; следующий
критерий и отдельный запуск продолжают работать. Batch с одинаковыми
UUID и разными состояниями форм изолирован; повтор в свежий output даёт
те же баллы. Мутация одной работы не меняет результат соседней.

Публичные test/run/batch должны совпадать по критериям и состояниям.
JSON Schema grading, batch и событий проверяется прежним контрактом.
Прежние объектные context, mocks, storage, транзакции, запросы/срезы
и SQL-профили сохраняются; поддержка формы не изменяет их семантику.

4. **34.4 — приёмка:** все 20 корней реального архива, переносимость,
   мутации, публичные пути, карта с фактическими доказательствами и регрессия.

Сохранить в `result/dvizhok-form-context/` native-пробы, планы, наблюдения,
журналы, исходные отказы, результаты/баллы, полный per-file/per-method отчёт
и SHA-256. Поддержать воспроизводимое обновление карты по дампу и заданиям.
В README, teacher guide, runtime matrix, roadmap и next-task отразить новый
контракт; в этот файл добавить отчёт реализации с фактическими цифрами.

База регрессии — 220 различных тестов №33. После целевых тестов выполнить
полный корпус с Docker/SQL opt-in и временным паролем окружения; четыре
validate, хеши архивов и схемы публичных пакетов. Не удалять старые тесты
и не увеличивать лимиты ради успеха. Сохранять первичные сбои и результаты
изолированных повторов; широкие прогоны не запускать одновременно.
Проверить очистку тестовых контейнеров/сетей и неизменность Dvizhok.

№34 завершено только после реального вызова всех 20 корней, независимой
оценки результатов и успешных мутаций. План или список файлов сами по себе
не являются завершённым runtime-охватом.

платформенную компиляцию и браузерные проверки внешнего вида/событий.
Доступ к студенческим приложениям не является условием данного этапа.

Общий UI runtime, layout/rendering, настоящий браузер, автоматическое
выполнение всех YAML-выражений, константы/календарь и запись/открытие форм
не входят в №34. ЗАПОЛНИТЬ/JOIN для других архивов, LMS, HTTP и деплой
остаются отложенными относительно потребностей Dvizhok.

## Отчёт о реализации

Этап реализован в общем `ExecutionPlan → renderer → Script Docker → SBSL`.
Новый `element_test/form_context.py` разрешает форму и тип её объекта по
namespace/import и YAML, рекурсивно перечисляет именованные компоненты,
генерирует свойства и ограниченные типы команд. Renderer прикрепляет исходные
корни и helper к одному экземпляру формы. Имена объектов Dvizhok не выбирают
адаптер; переносимые ledgers/accounts проходят тот же pipeline.

Обязательный `lifecycle.isNew` задаёт новизну объекта независимо от Номер и
expected. Технический флаг исключён из входа и наблюдения; неопределённое
состояние не превращается в false. Смена самого объекта формы требует
отдельного контракта. AST-проверки учитывают область видимости; native
структура сохраняет затенение. Проектный ЭтоНовый не подменяется системным.

Поддержана `Надпись.Значение: Строка`, включая вложенные группы; остальные
компоненты и выражения сохранены в IR/карте с явными ограничениями.
`{contextPath: Объект.Товары}` передаёт реальный объявленный массив в параметр
с совпадающим типом. Поэтому проверка входной таблицы обнаруживает её порчу,
даже если итоговая надпись правильна. Sequence сохраняет состояние экземпляра
и отдельные снимки операций; критерии и batch создают свежие значения.

[Контракт](../form-context.md) фиксирует официальные сигнатуры Элемента 9.1,
отличие адаптера от native UI и результаты доверенных Script-проб. Locale форм
явно en-US: точка в дробных надписях соответствует авторскому требованию,
исходная интерполяция исполняется Script. Ссылки — native UUID с owner-типами.
Записать/Открыть остаются UNSUPPORTED с точными причинами; за каждым отказом
в приёмочном задании следует поддержанный успешный критерий.

### Проверка реализации

`assignments/dvizhok-form-context` содержит 77 критериев: 74 положительных
сценария и 3 контрольных границы. Актуальные публичные `test` и `run` дали
**74 PASS, 74/74, unavailablePoints=3** и вызвали все **20 корней семи форм**.
Все 77 статусов, наблюдаемых состояний и баллов совпали. Проверены
четыре сочетания новизны/номера, архивный helper, два переключения в sequence,
пустые/дробные/повторные строки, участники, итоги и сохранность входных таблиц,
оба состояния частичной отгрузки, нулевые и дробные значения.

`assignments/dvizhok-runtime-regression` объединяет 22 прежних бизнес-критерия
с отдельными идентификаторами и trace. Публичный `test` дал **22 PASS**:
свежие журналы подтверждают ещё семь прямых бизнес-корней исходного архива.

Девять мутаций временных копий дали **11 FAIL через SBSL**. Ошибку
РассчитатьИтоги обнаружили и прямой helper-критерий, и вызывающий обработчик;
отдельная мутация изменила таблицу при правильном тексте надписи.
Оба переносимых проекта дали по 2 PASS. Два batch-прогона в свежие output
дали каждый 2 успешные работы и 1 ошибочную, с одинаковыми баллами.
Финальный отдельный повтор этой проверки через настоящий
`bin/element-test batch` также прошёл (1/1).
UUID ссылок одинаков, состояния различны; мутация одной работы не повлияла
на соседнюю. Код и данные исходного архива не изменялись.

Полная регрессия — **233 разных теста (220 прежних + 13 новых), без пропусков**,
с Docker/SQL opt-in и временным паролем окружения. После неё актуальный корпус
форм повторно прошёл **13/13**; две дополнительные точечные проверки подтвердили
различие вызова/оценки в карте и независимость native-пробы от локали host.
Лимиты выполнения не увеличивались. Четыре исходных xdump прошли validate.
JSON Schema grading/batch/events проверена для 39 документов и событий.
SHA-256 всех четырёх архивов до/после совпал; Dvizhok остаётся
`c69ddf9247d0508207e3ab80c4ae87c782e8d876503487ee6fcc01105bccec97`.
После завершения тестовых контейнеров/сетей нет; существующий
`check-moodle-rest-1` и сеть `check_default` сохранены.

Первичные сбои сохранены: отказ подготовки типов/компонентов, несовпадение
локали числовой интерполяции, неверный импорт в batch-тесте и запуск полного
unittest из stdin, несовместимый с multiprocessing spawn. Также устранено
глобальное удаление пробелов из имени типа, нарушавшее прежнюю адаптацию тела
метода; отдельные 8 регрессионных проверок типов прошли. Итоговый полный прогон
запускался из файла с main guard и завершился OK. Журналы первичных попыток
и успешных повторов находятся в `result/dvizhok-form-context/`.

### Воспроизведение и свидетельства

Команды `test`, `run`, прежних бизнес-сценариев, целевых тестов и доверенных
native-проб приведены в
[README корпуса](../../tests/corpus/form-context/README.md).
Полную регрессию запускайте с обоими `ELEMENT_TEST_DOCKER_TESTS=1` и
`ELEMENT_TEST_INTEGRATION_TESTS=1`, а временный пароль задавайте через
`ELEMENT_TEST_INTEGRATION_PASSWORD`, без сохранения в исходниках.

Карта строится заново, списки файлов/методов не захардкожены:

```sh
python3 -m element_test.coverage --project Dvizhok.xdump --assignments assignments \
  --evidence result/dvizhok-form-context/test \
  --evidence result/dvizhok-form-context/run \
  --evidence result/dvizhok-form-context/legacy \
  --output result/dvizhok-form-context/coverage
```

`coverage.json` содержит идентичности, хеши файлов, YAML-декларации,
сигнатуры обработчиков, выражения, criteria, зависимости, планы и ссылки на
runtime-журналы. `coverage.md` даёт обзор всех файлов/методов.
`final-verification.json`, `schema-verification.json`, `public-equivalence.json`,
`archive-hashes-before.json`/`archive-hashes-after.json` и `cleanup.json`
фиксируют итоговые проверки. `full-regression.log`, `target-tests.log`,
`batch-cli-repeat.log` и `mutations.json` содержат свидетельства приёмки.
Вызванный метод с ERROR не получает статус независимой оценки; зависимость
не засчитывается как самостоятельно проверенная ветка. Пустой модуль
не получает runtime PASS. Native UI, платформенная компиляция и декларативные
выражения остаются NOT_CHECKED. Полная проверка дампа ещё не завершена.

Итоговая карта содержит **75 файлов (46 YAML + 29 XBSL), 44 метода**,
30 объявленных прямых targets, 27 подготовленных и **27 независимо оценённых
методов**. Оставшиеся 17 требуют поддержанного прямого сценария: у трёх есть
контрольный UNSUPPORTED, у 14 прямого критерия пока нет. Сценарии проверенных
методов подтверждают перечисленные ветки; полнота всех их API не заявляется.

В Git сохранены [измерения №34](../dvizhok-stage-034-measurements.json) и
[полная карта после №34](../dvizhok-coverage-after-034.md) с
[машиночитаемым снимком](../dvizhok-coverage-after-034.json).
Снимок относится к указанному SHA-256 архива и перечисленным журналам;
при изменениях его нужно пересоздать из новых результатов исполнения.
