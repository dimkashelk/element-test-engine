# Представления товаров в наличии из `Примеры_new`

Задание выполнено на исходном `Prakticheskie-primery-2026-09-30-15-20.xdump`.
Метод `МетодыРаботыСКоллекциями::РаботаСКоллекциями.ПолучитьПредставленияТоваровВНаличии`
исполнен Script executor **10.0.2-1** в Docker с режимом совместимости **9.0**.
Сравнение массивов, статусы и баллы определяет SBSL-движок.

## Требование и оценка

Независимое правило взято из `ПостановкаЗадачи` в
`МетодыРаботыСКоллекциями/Служебное/ОписаниеПримера_ПоследовательнаяОбработкаКоллекции.xbsl`:
преобразовать данные товаров в массив представлений, включающий только товары
в наличии и упорядоченный по убыванию цены. Для этого примера цена соответствует
полю `Стоимость`, наличие — положительному `Количество`.

[Задание](../../assignments/practical-stock-presentations/assignment.yaml) содержит
один критерий сигнатуры и девять runtime-критериев, всего **12 баллов**.
Матрица и авторские уточнения находятся в
[контракте задания](../../assignments/practical-stock-presentations/README.md).
Проверены исходный пример, пустой список, нулевое и отрицательное количество,
единственный товар, три разные стоимости, положительное дробное количество,
нулевая и отрицательная стоимость, одинаковые строки и специальное наименование.
Порядок различных товаров с равной стоимостью не задан и не оценивается.

Точное представление `В наличии: <имя> Стоимость: <число>` — явное уточнение
автора задания, согласованное с шаблоном оригинального метода. Сам текст
постановки не задаёт пунктуацию; оформленный пример содержит дополнительную
запятую после имени. Ожидаемые фильтрация и порядок определены независимо
от исполняемого метода, а формат описан отдельно.

Первый пробный запуск выявил ошибку ожидания для больших чисел:
executor возвращает `1,000` и `2,000` при интерполяции `${...}`. Это использование
`Представление()`, а не обычного преобразования `ВСтроку()`; различие описано
в [официальном руководстве по интерполяции](https://1cmycloud.com/console/help/executor/8.0/docs/topics/string-interpolation/).
Отдельный доверенный скрипт в Docker режима 9.0, без целевого метода,
подтвердил `[1000, 2000, 1.25]` → `["1,000", "2,000", "1.25"]`.
После этого исправлены только ожидаемые строки; исходный XBSL не изменялся.
Точное форматирование подтверждено в настроенном executor и образе из
`config/runtimes.json`, без обещания совпадения при смене локали.

## Runtime-контракт

`ProjectTypes.require` теперь допускает `ЧитаемыйМассив<T>` и рекурсивно
проверяет поддержанный тип элемента. Для аргумента нужен YAML-список;
генерируется `новый Массив<T>([...])` с явным типом, включая пустой список.
Сигнатуры методов сохраняют `ЧитаемыйМассив<T>`. Возвращаемый массив
сериализует штатный `СериализацияJson`, без специальной подмены результата.

В Docker отдельно подтверждены аргументы и результаты чисел/строк,
пустой массив, nullable-массив, вложенные массивы, кавычка, перевод строки
и литерал `${probe()}`. Неверный вход и неподходящий элемент списка отклоняются
как `invalid_test`. Неверное число generic-параметров и неподдержанный
элемент `Ууид` не получают придуманную семантику.

Структура `ДанныеТовара` копируется из того же исходного модуля по контракту
[задания №27](027-practical-total-cost.md). Тело целевого метода сохранено
полностью: фильтрацию, сортировку и преобразование выполняет стандартная
библиотека executor. Неиспользованный метод суммы не включается в скрипт.
Метаданные, UI, хранение и библиотечные зависимости этим изменением не расширены.

Прежняя недоступность `ЧитаемыйМассив<Строка>` из №27 устранена.
Его `fixtures/unsupported.yaml` заменён реальным недоступным контрактом
создания покупателя с входным `Ууид`; та же проверка используется отдельно
от оценки в №28. Подготовка возвращает `UNSUPPORTED / unsupported_contract`
до операции записи. Аннотации, умолчания и методы локальных структур,
перенос структуры между модулями и прочие неподдержанные элементы массивов
сохраняют прежние ограничения.

## Воспроизведение и регрессия

```bash
bin/element-test test --project Prakticheskie-primery-2026-09-30-15-20.xdump \
  --assignment assignments/practical-stock-presentations \
  --output result/practical-stock-presentations/test
bin/element-test run --project Prakticheskie-primery-2026-09-30-15-20.xdump \
  --assignment assignments/practical-stock-presentations \
  --output result/practical-stock-presentations/run
bin/element-test test --project Prakticheskie-primery-2026-09-30-15-20.xdump \
  --assignment assignments/practical-stock-presentations/fixtures/unsupported.yaml \
  --output result/practical-stock-presentations/unsupported
python3 -m unittest discover -s tests -v
ELEMENT_TEST_DOCKER_TESTS=1 python3 -m unittest discover -s tests \
  -p 'test_practical_stock_presentations.py' -v
```

Общая регрессия: **157 тестов, 16 штатных opt-in пропусков**, остальные прошли.
Целевой набор с Docker: **4/4 прошли**; два из этих тестов исполняют
оригинал, три изменённые копии и отдельные контракты контейнеров в Docker.
Регрессия прежних наборов с Docker: **17/17 прошли** — сумма (6), телефон (2),
прежние runtime-сценарии (9), включая массивы, объектный контекст, fake-ссылки,
моки регистров/запросов, отрицательные оценки и продолжение после отказа.
Журнал — `previous-docker-tests.log` в том же каталоге.

Артефакты в `result/practical-stock-presentations/`: `verification.json`,
`verification.log`, `unit-tests.log`, `docker-tests.log`, публичные JSON/HTML
и пакеты оценки в `test-final/`, `run/`, трёх `negative-*/`, `unsupported/`, `batch/`.
Там же находятся отдельные копии изменённых проектов и manifest партии.
Скрипт `verify.py` сохраняет сводку CLI и проверяет коды/баллы/хеши.
