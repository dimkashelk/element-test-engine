## Описание формы — основной вход проверки

Описание принадлежит преподавателю и хранится отдельно от работы студента.
Оно задаёт назначение формы, данные и типы полей, заголовки, обязательные
таблицы/колонки, источник данных, команды/результаты их действий, состояния
видимости/доступности, read-only правила, обязательные группировки и порядок.
Явно определять обязательное, необязательное и запрещённое, допустимость
дополнительных компонентов и критерии/баллы. Отсутствие требования к порядку
не создаёт скрытого требования совпасть с деревом эталона.

Поддержать подготовку описания на русском языке и его нормализацию в
версионированный YAML/JSON контракт требований. Спроектировать и реализовать
схему, валидацию и authoring-вход; сохранять исходный текст и связь каждого
критерия с пунктом описания. Нормализованный контракт готовится до проверки
студенческих работ, воспроизводим и повторно используется для всей группы.
Разбор описания не исполняет работу студента; оценивание не зависит от нового
ответа языковой модели на каждый присланный архив. Если необходимый параметр
не указан, обозначить его в контракте как недоопределённый; не додумывать
обязательные ограничения во время оценки конкретного студента.

Для предоставленных эталонов автор тестов самостоятельно пишет полные
описания и нормализованные контракты. Пользователь уже разрешил этот выбор:
дополнительного согласования каждого fixture/expected не требуется.
Если позже преподаватель передаст собственное описание, оно определяет
требования; эталон используется для проверки тестов на соответствие им.

Компоненты сопоставляются по объявленным требованиям: роли, типу данных,
привязке и другим указанным признакам. Точное имя/путь требуется только при
прямом указании в описании. Идентичность владельца данных сохраняется;
сходство имён разных owners не разрешает подмену. Неоднозначное сопоставление
показывается в отчёте, вместо выбора первого подходящего компонента.
Путь реальной формы используется в диагностике, не навязывается всем студентам
как копия эталонного YAML. Эквивалентные выражения и исходные обработчики
принимаются, если дают требуемое поведение на независимых тестах.

Результат по каждому пункту: выполнено/нарушено/проверка недоступна, ожидаемое
требование, фактические компоненты/значения, исходные пути и баллы SBSL.
Описание с неверными/противоречивыми типами — ошибка задания. Отсутствующее
обязательное поле, неправильная привязка или неверное состояние формы —
нарушение студенческой работы в поддержанном контракте.

### Пример независимого описания и сценариев

«Форма отгрузки содержит дату, номер, склад и таблицу товаров с колонками
номенклатура, количество, цена, сумма. При обычном создании отображаются
товары документа. При создании по выбранной части отображаются переданные
строки; видна надпись с итогами части. Переключение режима редактирования
меняет доступность даты и номера и представление соответствующей команды.
Просмотр и переключение источника не сохраняют документ».

| Критерий описания | Вход / действие | Независимое ожидание |
|---|---|---|
| Обязательные поля | Эталон и работа без склада | Эталон соответствует; отсутствие склада нарушает отдельный пункт |
| Типы и привязки | Разные дата/номер/склад, однотипные поля с маркерами | Каждое поле отображает предназначенный реквизит |
| Обычный источник | Строка документа: количество 2, цена 10, сумма 17; переданная строка с суммой 31 | Таблица показывает строку документа и сумму 17, без пересчёта в 20 |
| Источник части | Те же массивы, признак части Истина | Таблица показывает переданную строку и сумму 31 |
| Повторное переключение | Обычный → часть → обычный | Источник и все колонки снова соответствуют документу |
| Пустые/повторные строки | Пустой массив; две одинаковые строки | Ноль строк; два вхождения без удаления повтора |
| Видимость итогов | Оба значения признака части | Надпись видна только для части, её значение соответствует состоянию |
| Редактирование | Два вызова связанной команды | Доступность и представление переключаются и возвращаются |
| Эквивалентная реализация | Другие имена компонентов и равнозначное условие | То же описание даёт тот же успешный результат |
| Отсутствие записи | Просмотр/переключение и независимый аудит | Документ и основание в storage неизменны |

Числа примера фиксируются в критериях до исполнения. Остальные 15 описаний
и их полные матрицы составить из предоставленного эталона тем же способом.
Проверки компоновки выполняются по декларации, если она требуется описанием;
пиксельное отображение и реальные браузерные события относятся к отдельному
исполняемому UI-контракту. Неподдержанный пункт описания остаётся явно
недоступным и не приносит баллы автоматически.

## Общий контракт деклараций и критериев

Перед реализацией описать формат новых структурных и runtime-критериев
в `docs/declarative-bindings.md`, затем закрепить его в teacher guide.
После сопоставления требования с работой привязка разрешается по полной
идентичности её реальной формы и пути от корня YAML,
например `Наследует/Содержимое/.../Источник/Данные`. Индексы списков сохраняются;
одинаковый текст в разных местах имеет отдельную идентичность. Имена компонентов
используются для разрешения деклараций, а не для выбора специальной реализации.

План содержит исходный файл, YAML-путь, текст выражения, разрешённые символы,
типы входа/выхода и зависимости. Если доступны позиции YAML, сохранять их;
не придумывать XBSL-диапазон для строки YAML. Пути из старой карты местами
отсчитываются от Наследует, местами от полного документа: новый контракт
нормализует их от корня файла без потери старого свидетельства.

Предусмотреть runtime-критерий для формы **без XBSL-модуля и target метода**.
Нельзя создавать фиктивный исходный метод ради запуска YAML-выражения.
Для формы с исходными методами допускается явная последовательность:
подготовка контекста → объявленный исходный метод → снимок привязок →
следующий исходный метод/типизированное изменение fixture → новый снимок.
Каждый шаг и его порядок задаются в контракте описания; для данного корпуса
их составляет автор тестов. Lifecycle не запускается неявно.
Наблюдение может охватить несколько путей, но у каждого проверяемого пути
должны быть независимое ожидание и ссылка на критерий в карте.

Ошибки fixture получают `invalid_test`; неподдержанная конструкция/API —
UNSUPPORTED с точной причиной; runtime/инфраструктурный отказ — ERROR/TIMEOUT.
Некорректная декларация работы в поддержанном контракте должна давать FAIL
структурного критерия через SBSL, а не успех из-за пропуска её исполнения.
Поддержанная декларация с неверным значением даёт FAIL runtime-критерия.
Отказ одного критерия не блокирует следующий поддержанный критерий.

## 1. Структура, типы и связи интерфейса

Независимые SBSL-критерии строятся из описаний всех 16 эталонных форм.
Общий механизм умеет проверять следующие виды требований:

- базовый тип формы и owner Объект/Запись, собственные свойства, их типы/defaults;
- имена и типы компонентов в допустимой области, дубли и точные пути;
- ПолеВвода<T>, Флажок и Надпись: допустимость привязки Значение,
  булевый тип Видимость/Доступность/ТолькоЧтение и строковые представления;
- Таблица<ИсточникДанныхМассив<T>>, тип Данные, тип каждой колонки и RowData;
- собственные Обработчик/ПриНажатии: owner, видимость, параметры команды,
  тип строки/массива и void-результат; все 14 мест привязки;
- ссылки на встроенные команды формы/таблицы в соответствующем фрагменте,
  ссылки на три встроенные формы записи констант в ФормаПриветствие.

Разрешать проект/namespace/import alias по декларациям, nullable/union,
полную квалификацию и совпадающие краткие owners разных подсистем.
RowData имеет тип строки ближайшей таблицы; соседняя таблица не предоставляет
ему поля. Вне колонки/объявленного контекста строки RowData не возникает.
Поле проекта с системным именем и затенение разрешаются прежде встроенного
символа. Каталог известных системных свойств/команд ограничен базовым типом
и описан в контракте, а не глобальным списком строк, разрешённых везде.

Все 128 ссылок на команды получают проверку разрешения/типов либо явную
причину недоступности. Структурный PASS не означает исполнение ЗаписатьИЗакрыть,
Удалить, перемещения строк или браузерного события. Такие операции не запускать
в №38 только потому, что встретилась ссылка на команду. Сигнатуры действуют
в рамках объявленного адаптера; непроверенные правила native UI не утверждать.

## 2. Выражения значений и снимки в Script

Поддержать по AST исходного выражения необходимые архиву конструкции:
собственные свойства формы, пути Объект.<поле>/Запись.<поле>,
RowData.<поле> и условное выражение. Литералы и другие конструкции включать
только по явно описанному общему контракту. Не использовать Python eval,
бизнес-вычисления Python или regex-подстановку имени для готового результата.
Преобразование в Script сохраняет исходное выражение и типовую идентичность.

Наблюдать заголовок, представления команд, Значение, Доступность и Видимость,
Данные источника и значения всех колонок. Ожидания определяются из описания
до запуска; для данного корпуса их самостоятельно составляет автор тестов. Использовать разные маркеры в однотипных полях и соседних таблицах,
чтобы ошибочная привязка не могла случайно дать тот же ответ.

Обязательные состояния: пустые/непустые строки, нулевые/дробные числа,
оба булевых значения, даты, enum, nullable и все объявленные варианты union.
Одинаковый UUID у разных owners не смешивает ссылки. Непереданные поля
получают только объявленные defaults адаптера; неизвестные поля отклоняются.

Для ФормаЗаписиНабораКонстант добавить ограниченный **контекст чтения Запись**
по YAML владельца и fixtures констант №35. Отсутствие XBSL файла допустимо.
Снимок проверяет четыре поля компании, две настройки и семь дней, а также
неизменность подготовленных констант. Это не native lifecycle формы записи
и не реализация записи констант или их SQL-хранения.

Для семи форм с РедактированиеДанных проверить новое вычисление Доступность
после двух исходных переключений и связь представления команды с изменённым
свойством. У Сделки/Заказа проверить ПредставлениеАрхивирования после исходного
обновления в обоих состояниях Архивный. ФизическиеЛица оцениваются с обоими
флагами ТелефонАктивен/ПочтаАктивна, без выдуманного обработчика их изменения.
У ФормаПриветствие проверить заголовок до и после объявленного ПослеСоздания
с fixtures №35; не добавлять новый oracle, зависимый от actual.

Перевычисление явно выполняется в точках наблюдения. Нельзя выдавать его
за реактивную подписку native UI. Двусторонняя запись из поля ввода,
ограничения редактирования, браузерная очередь событий и layout не входят
в этот контракт. Прежние context/observe без нового opt-in сохраняют поведение.

## 3. Пять таблиц и условный источник Отгрузки

Проверить Участники/ПервичныйСпрос Сделки, Товары Заказа, Отгрузки и
ПоступлениеТоваров. Для каждой таблицы: пустой массив, одна/несколько строк,
повторы, исходный порядок, nullable-значения и независимые значения колонок.
Количество строк и сериализованный источник не заменяют оценку каждого
RowData.<поле>. Одинаковое краткое имя Товары не смешивает типы строк.

Исходное выражение Отгрузки:
`=СозданныйНаЧасти?ТоварыТабличнаяЧасть: Объект.Товары`.
При Ложь источник — Объект.Товары; при Истина — ТоварыТабличнаяЧасть.
Задать различающиеся массивы, затем переключить флаг в том же контексте:
Ложь → Истина → Ложь. Проверить выбранные строки/колонки, Видимость
НадписьИтогиЧасти и её Значение ТекстИтоговЧасти. Исходные массивы неизменны,
уже собранный снимок не меняется после мутации живого массива в Script.
Пробы независимости использовать по контракту №37, не сравнивать две
заранее сериализованные Python-копии как доказательство aliasing.

Связать один поддержанный сценарий №36 с новыми наблюдениями: исходный
ЗаказФормаОбъекта.ОтгрузитьОбработчик создаёт документ, передаёт typed свойства
в запрос открытия, явный lifecycle формирует контекст, а новая оценка YAML
показывает переданные строки в таблице целевой формы. Не переносить их неявно
в Объект.Товары и не сохранять документ. Сценарий независимо сравнивает
запрос открытия, оба массива, вычисленные привязки и storage. Прямые критерии
СоздатьЧасть/ПеренестиТабличнуюЧасть №37 остаются собственными критериями.

## Переносимость и обнаружение ошибок

Добавить минимум два небольших проекта в `tests/corpus/declarative-bindings`.
Одно описание должно принимать две разные правильные реализации и отклонять
нарушение каждого обязательного пункта. Отдельное другое описание меняет
требования и оценку той же формы: это доказывает зависимость оценки от входа.
В проектах использовать:
другие имена свойств/форм/компонентов/колонок, import alias, полная квалификация,
одинаковые краткие owners в разных namespace, формы без XBSL, обычная Форма,
форма объекта и форма записи констант. Исполнить условный источник с другими
именами. Ни Dvizhok, ни Товары, ни RowData-поле не выбирают бизнес-ответ в коде.

Исполнимые временные мутации должны независимо давать FAIL в SBSL:
неверное однотипное поле/owner, перепутанные значения колонок, другая таблица,
инвертированный флаг, перепутанные ветви условного источника, неизменный
результат после переключения, потерянная/переставленная/дублированная строка,
неверное представление или видимость, совместимый обработчик с неверным эффектом,
удаление обязательного пункта, запрещённый компонент и нарушение явно
заданной компоновки. Перестановка колонок без требования порядка в описании
и переименование не должны сами по себе снижать оценку.
Удалённый компонент/поле, неверный generic или несовместимая сигнатура дают
FAIL собственного структурного критерия. Ожидания под мутации не переписывать;
ошибка компиляции/UNSUPPORTED не считается обнаруженной бизнес-ошибкой.

Отдельно проверить неизвестную конструкцию, неверный teacher fixture и runtime
отказ, затем успешный критерий. Контексты, константы, RowData и снимки не
перетекают между критериями и работами. Ссылки на команды не создают эффектов.
