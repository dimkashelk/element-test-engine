# Задание №13, пункт 8: повторное использование анализа в batch

При промахе кэша worker прежде открывал проект и выполнял `analyze` для
`sourceHash`, затем `run_test` повторно открывал проект и выполнял `analyze`.
Для архивов это также означало повторную распаковку или конвертацию XDUMP.

Теперь worker держит безопасно открытый проект до конца проверки и передаёт
его корень вместе с уже построенной моделью в `run_test`. Ключ кэша по-прежнему
вычисляется из `sourceHash` модели, содержимого задания, движка, контрактов и
конфигурации. При cache hit анализ остаётся необходимым для проверки содержимого;
при cache miss анализ и открытие выполняются по одному разу. Одиночные команды
`test` и `run` сохраняют свой интерфейс и самостоятельно анализируют проект.

Проверка на `Dvizhok.xdump` с `assignments/demo`: одиночный запуск, cache miss
партии и следующий cache hit дали одинаковый `result.json`: `passed`, 6/6,
одинаковый `sourceHash`. SHA-256 исходного архива:
`c69ddf9247d0508207e3ab80c4ae87c782e8d876503487ee6fcc01105bccec97`;
архив не изменён. Отдельный тест запрещает повторный вызов `analyze` и
`open_project` внутри `run_test` при cache miss.

Три локальных запуска каждого пути на macOS, холодный кэш для партии; медианы:

| Путь | Время | Пик RSS процесса Python |
|---|---:|---:|
| Одиночный `run_test` | 1,192 с | 32,3 MiB |
| Прежний путь `batch` (двойной анализ) | 1,318 с | 32,3 MiB |
| Новый путь `batch` (один анализ) | 1,182 с | 32,0 MiB |

Прежний путь воспроизведён отдельным локальным скриптом: анализ для ключа,
затем обычный `run_test`. Замеры относятся к одному Python-процессу без
дополнительного worker; RSS JVM executor и Docker не включён. Небольшая выборка
показывает отсутствие заметного роста памяти, а не гарантированное ускорение
на любой машине или задании.

Полная локальная регрессия: 96 тестов, 11 штатных пропусков без opt-in Docker.
Docker/SQL-регрессия в этом изменении не запускалась.
