# Задание №30: общие контракты транзакций и бизнес-исключений XBSL

Статус: **выполнено в заявленном охвате**, 1 октября 2026 года.
Основание: [результат №29](029-universal-runtime.md#отчёт-о-реализации)
и [действующий контракт runtime](../universal-runtime.md).
Ниже сохранены требования этапа; фактические результаты — в отчёте о реализации.

## Цель

Расширить общий pipeline planner → renderer → executor → наблюдения → SBSL
так, чтобы исходный XBSL мог управлять транзакционным ресурсом, выполнять
несколько связанных записей и выбрасывать/перехватывать поддержанные
бизнес-исключения. Сохранить атомарность, реальные исходные вызовы,
независимый аудит и различение ошибки работы и недоступности среды.

Контракты выбираются по разрешённым типам/API и декларациям метаданных.
Нельзя добавлять ветки движка по имени Покупатели, СоздатьИлиОбновить,
namespace учебного проекта или ожидаемому ответу.
Python готовит план и инфраструктуру; бизнес-условия и порядок операций
исполняет Script executor. Сравнение и баллы остаются в SBSL.

## Исходное состояние и реальный сценарий

№29 поддерживает native UUID, общие CRUD/наборы регистров, свежие снимки,
оригинальные обработчики записи и транзакцию вокруг вызова driver.
`captureException` наблюдает ИсключениеНедопустимоеСостояние, сохраняя
прежнюю оболочку `{result, exception}`. Глубина цепочки методов не ограничена
движком; ресурсные ограничения Docker/executor сохраняются.

До этапа №30 были недоступны исходный `исп Транзакции.Начать()`, ИсключениеВалидации и
загрузка с блокировкой. Конструктор объекта через системный `Ид` также
требовал привязки к генерируемой ссылке: наличие входного UUID само по себе
не реализовывало этот контракт.

В неизменённом `Prakticheskie-primery-2026-09-30-15-20.xdump` метод
`РаботаСИсключениями::Покупатели.СоздатьИлиОбновить`:

1. Проверяет ФИО и телефон; при ошибке выбрасывает ИсключениеВалидации.
2. Получает ссылку по Ууид и объявляет `исп Транзакции.Начать()`.
3. Вызывает `ЗагрузитьОбъект(Истина)`; обновляет существующий объект
   либо создаёт `новый Покупатели.Объект(Ид = Ид, …)`.
4. Записывает объект и возвращает его ссылку.

Этот метод — пример приёмки общего алгоритма. Переносимые проекты с другими
именами, схемами и несколькими записями обязательны. Поддержка только
транзакционного вызова без оставшихся зависимостей не завершает сценарий.

## Обязательный результат

### 1. Проверенный контракт платформенных операций

До реализации зафиксировать официальные сигнатуры и семантику нужных API
для выбранного режима совместимости. Различать сведения документации,
результат доверенной native-пробы Script executor 9.0 и поведение нашего
адаптера. Отсутствующий native API реализуется явным общим адаптером;
его нельзя объявлять native-возможностью или полной эмуляцией платформы.

Уточнить для `исп`: время жизни ресурса, закрытие при обычном выходе,
`возврат`, исключении, выходе из блока и вызовах зависимостей. Отдельно
установить условия фиксации/отката: не считать закрытие автоматическим
commit без подтверждённого основания. Зафиксировать взаимодействие
с перехваченным внутри блока исключением и явными операциями завершения,
если они входят в выбранный контракт.

Платформенное приложение/деплой и доступ к приложениям студентов не нужны.
Если семантика не подтверждена или не воспроизводится адаптером, операция
остаётся `UNSUPPORTED` с объяснением. Этап не считается завершённым,
пока обязательный основной контракт не реализован и не проверен.

### 2. Привязка транзакционного ресурса в ExecutionPlan

Расширить существующие AST, разрешение имён, реестр возможностей и план.
Распознавать разрешённый API транзакции и лексическую область ресурса,
включая безымянное объявление `исп` из реального примера.
Одноимённая проектная декларация или локальная переменная не должна
случайно связываться с платформенным адаптером.

В IR сохранить исходную идентичность/диапазон, выбранный контракт,
область жизни, backend и ограничения. Преобразования выполняются по
AST/проверенным диапазонам. Исходные условия, формулы, порядок вызовов,
возвраты и обработчики сохраняются; метод целиком не заменяется шаблоном.

Сохранить единый путь `test`, `run`, `batch` и отсутствие `expected`
в плане исполнения. Не вводить ограничение глубины цепочки методов.

### 3. Общая транзакционная сессия

Расширить сессию №29 общим жизненным циклом транзакции из исходного кода.
Запись объекта, его строк и набора регистра из зависимого метода должна
участвовать в той же активной транзакции. Поддержать несколько объектов
разных видов/namespace, свежую загрузку и оригинальные обработчики записи.

Атомарность распространяется на все изменения выбранной транзакции.
Ошибка второго объекта или ПослеЗаписи не должна оставлять первый объект,
часть строк либо движения. Ранее завершённые независимые операции
сохраняются в соответствии с зафиксированным контрактом. Контроль активной
транзакции и откат выполняются в executor/backend, а не пересчётом
бизнес-результата в Python.

Определить взаимодействие исходной транзакции со старым
`storage.transaction: true`: исключить случайный двойной commit,
перезапись резервного снимка и потерю внешней транзакции.
Вложенные исходные транзакции: либо реализовать документированный контракт,
либо заранее отвергать достижимую неподдержанную конструкцию. Молчаливо
выбирать произвольную семантику savepoint/вложения нельзя.

Memory и PostgreSQL должны давать одинаковые наблюдаемые результаты
в общем поддержанном охвате. Для SQL сохранить независимый аудит и доказать
реальный rollback при отказе backend. При staged-хранении явно описать,
как границы исходной транзакции соотносятся с публикацией в БД; общий commit
driver не заменяет доказательство семантики транзакции исходного кода.

### 4. Бизнес-исключения и общий перехват

Добавить ИсключениеВалидации как явный платформенный контракт с проверенным
конструктором и сообщением. Сохранить ИсключениеНедопустимоеСостояние.
Поддержать выбрасывание, переход через исходные зависимости, типизированный
перехват, повторное выбрасывание и наблюдение в driver в выбранном охвате.

Тип адаптера не должен менять выбор исходного обработчика исключения.
Сохранить различие между видами исключений, базовым типом и операциями
над типом, если они используются достижимым кодом. Если точную семантику
представления/наследования нельзя обеспечить, соответствующее обращение
отклоняется; разные типы нельзя сводить к одному только ради компиляции.

Сохранить публичную форму `captureException` и логическое имя типа
бизнес-исключения. Техническое имя адаптера не становится именем
платформенного типа в expected. Сообщение и интерполяция аргументов берутся
из исходного кода. Отсутствие ожидаемой валидации или неверный тип/сообщение
обнаруживаются независимым критерием и дают `FAIL`.

Компиляция неподдержанного обращения — `UNSUPPORTED`; неверное задание —
ошибка задания; Docker/SQL, timeout и сбой публикации остаются
инфраструктурными исходами. Даже при `captureException: true` их нельзя
превращать в успешное наблюдение ожидаемого бизнес-исключения.

### 5. Сопутствующие общие контракты метаданных

Связать системный `Ид` конструктора объекта с native UUID и соответствующей
ссылкой по общей семантике Справочника/Документа. Сохранить старые строковые
fake-ID и не смешивать одноимённый обычный реквизит с системным параметром.
Одинаковые ID разных типов/namespace должны оставаться разными записями.

Реализовать `ЗагрузитьОбъект(Заблокировать = Истина)` в явно заявленном
охвате изолированной сессии: требование активной транзакции, время удержания
и освобождения, чтение существующего и отсутствующего объекта. Нельзя
просто удалить аргумент или игнорировать Истина. Определить, какие гарантии
адаптер действительно обеспечивает в memory и PostgreSQL; конкурентная
семантика за пределами проверенной сессии не заявляется.

Любые дополнительные неподдержанные операции метаданных сохраняют честную
недоступность. Если для реального примера обнаружится ещё одна зависимость,
описать и реализовать её общим контрактом либо явно пересмотреть охват;
не добавлять специальный обход для этого метода.

## Порядок реализации

1. **30.1 — семантика и пробы.** Проверить исходники, сигнатуры, жизненный
   цикл `исп`, исключения, системный Ид и загрузку с блокировкой. Сохранить
   доказательства и матрицу поддержанного/недоступного.
2. **30.2 — planner и типы.** Добавить разрешённые привязки, области ресурса,
   контракт бизнес-исключения и общую связь конструктора/ссылки.
   Проверить коллизии владельцев и отсутствие подмены проектных объявлений.
3. **30.3 — runtime/backend.** Реализовать жизненный цикл, атомарность,
   перехват и блокировку в заявленном охвате; согласовать старую транзакцию
   driver и исходные транзакции, сохранить прежние пакеты.
4. **30.4 — переносимость и регрессия.** Исполнить реальный метод и новые
   проекты в Docker, подтвердить аудит/откаты и CLI, обновить fixtures,
   руководство и отчёт по действительным результатам.

## Критерии приёмки

| Проверка | Требуемое доказательство |
|---|---|
| Реальный метод | Создание и обновление по UUID, существующая/отсутствующая ссылка, поля, сохранённый ID и ссылка подтверждены аудитом |
| Валидация | Пустое ФИО и некорректный телефон дают исходный тип/сообщение; запись не появляется; правильный ввод исполняется |
| Исходный перехват | Типизированные и общие catch выбирают нужную ветвь; rethrow сохраняет исключение; удалённый/неверный catch выявляется |
| Границы ресурса | Обычный выход, ранний возврат, исключение и перехват внутри блока дают исходы подтверждённого контракта |
| Несколько записей | Объект + другой объект/строки/регистр изменяются совместно; ошибка позднего шага не оставляет частичного состояния |
| Исходные зависимости | Проверяется только А; Б/В реально выполняются, ошибка внутри них меняет итог или состояние и даёт FAIL |
| Взаимодействие транзакций | Старый driver, исходный ресурс и обработчики не делают двойную фиксацию и не уничтожают нужный снимок |
| Блокировка | Активная/неактивная транзакция, существующий/отсутствующий объект и освобождение проверены в объявленном охвате |
| Независимость соседей | Откат не меняет прежние записи и другие типы с тем же UUID; ранее завершённые операции сохраняются по контракту |
| Backend-отказ | Внедрённый SQL-сбой даёт ERROR/недоступные баллы и независимый аудит отката; не маскируется ожидаемым исключением |
| Имена и схемы | Другие методы, namespace, алиасы, реквизиты, ТЧ и владельцы работают без правок алгоритма адаптера |
| Негативные варианты | Пропуск валидации, неправильный ID/поле, отсутствие второй записи, нарушение атомарности и перехвата обнаруживаются |
| Честная граница | Достижимая неподдержанная операция/вложение даёт UNSUPPORTED; недостижимый метод её не исполняет и не блокирует доступный корень |
| Совместимость | Прежние доступные результаты и баллы №29/старых заданий сохранены; test/run/batch согласованы |
| Изоляция и очистка | После отказа успешный сценарий проходит; две работы batch с одинаковыми ID не делят состояние; ресурсы удалены |

Для каждого нового общего контракта нужны независимые `PASS`,
контролируемый `FAIL` и обоснованный `UNSUPPORTED`. Переносимый корпус должен
содержать как минимум два проекта с разными именами/схемами и транзакционную
цепочку нескольких исходных методов. Ожидания формирует преподаватель;
результат студенческого метода не используется как эталон.

## Проверка и артефакты

Исходные архивы открываются на чтение. Исполнять submission XBSL только
в Docker; native-пробы на хосте содержат лишь отдельный доверенный код.
Сначала целевые проверки, затем общая регрессия и Docker/SQL-наборы.
Проверить четыре validate и SHA-256 исходных архивов, согласованность
`test`/`run`/`batch`, отсутствие утечки паролей и оставшихся ресурсов.

При реализации сохранить в `result/transactions-and-business-exceptions/`:
матрицу подтверждённой семантики, native-пробы, планы/трассы, независимые
аудиты до/после и при отказе, журналы тестов, CLI-сопоставление,
публичные JSON/HTML/grading-пакеты и отчёт о переносимости.
Fixtures и задания преподавателя включить в репозиторий.

Fixtures недоступности, которые после реализации стали исполняемыми,
заменить действительно неподдержанной границей и объяснить миграцию.
Форму ожидаемого storage-наблюдения обновить явно: одна возвращённая ссылка
не доказывает запись и правильную валидацию.
Обновить руководство, матрицу runtime, next-task и roadmap.
Завершённость подтверждается всеми четырьмя этапами и реальными исходами;
доверенная компиляция адаптера сама по себе не является приёмкой.

LMS, HTTP-доставка, UI, деплой приложений, общий XBQL, новые API чтения
регистров и полный конкурентный эмулятор платформы в этот этап не входят.

## Отчёт о реализации

Этапы 30.1–30.4 выполнены. Общий pipeline связывает операции по разрешённому
типу/API, декларациям YAML и исходным диапазонам AST. В коде адаптера нет
ветвей по Покупатели, СоздатьИлиОбновить, именам переносимых проектов или
expected. Исходные условия, формулы, зависимости и обработчики выполняет
Script executor; сравнение и баллы вычисляет SBSL.

### Контракты и изменения

- `source_contracts.py` добавляет ресурсные области, общую привязку
  бизнес-исключений и системного Ид. В IR сохраняются исходная идентичность,
  диапазоны, backend и ограничения. Одноимённые проектные владельцы/локальные
  имена не подменяются платформенными API; expected в плане отсутствует.
- `storage.py` реализует отдельные снимки исходной транзакции и driver,
  атомарность объектов/строк/регистров, реестр блокировок типа/ID и публикацию
  SQL на границах. Повторная публикация неизменённого состояния пропускается.
- ИсключениеВалидации имеет отдельную native идентичность пользовательского
  исключения с базой Исключение. Подтверждены typed/general catch, rethrow,
  union, `это` и `как`; тип отличается от НедопустимоеСостояние. Описание
  вычисляется исходником. Сбой SQL остаётся ERROR даже после исходного общего
  catch; доверенный независимый аудит подтверждает SQL rollback.
- Системный `Ид` конструктора разрешённого Справочника/Документа связывается с
  его UUID-ссылкой. Одноимённый обычный реквизит сохраняет свой смысл.
  Загрузка с блокировкой требует активную транзакцию, удерживает владение до
  её завершения и возвращает свежий объект либо Неопределено.
- Renderer сохраняет вызовы скалярных зависимостей обработчика, включая
  зависимость на вспомогательный метод входного модуля, без циклического
  импорта всего входного модуля. Трасса void-метода использует finally/leave,
  поэтому корректна для раннего возврата и метода, всегда выбрасывающего
  исключение; leave не объявляет результат успешным.

Официальные сведения платформы, native-пробы Script 9.0 и выбранные адаптеры
разделены в [матрице семантики](../../result/transactions-and-business-exceptions/semantics.md).
Native API транзакции и ИсключениеВалидации в проверенном Script отсутствуют.
Отдельная доверенная проба выявила пропуск внешнего catch/finally при
неподходящем внутреннем typed catch. Общий AST fallback catch/rethrow исправляет
распространение исключения; контрольный неправильный catch теперь откатывает
состояние и освобождает ресурс. Пробы и их журналы сохранены в native-probes.

### Границы и миграция

Это общий адаптер выбранных контрактов, а не полный эмулятор платформы.
Именованные ресурсы, явное завершение, вложенные исходные транзакции и ресурс
в лямбде остаются UNSUPPORTED. Блокировки гарантированы внутри изолированной
staging-сессии; FOR UPDATE, конкуренция сессий и savepoint не заявляются.
Reflection и дополнительные перегрузки адаптированных исключений недоступны.
Полный контракт и команды воспроизведения —
[transactions-and-business-exceptions.md](../transactions-and-business-exceptions.md).

Прежние fixtures недоступности записи покупателя заменены действительно
недоступным XBQL без заданного подставного запроса. В CRUD заданиях граница
блокировки заменена именованным ресурсом. Доступные проверки и баллы прежних
заданий сохранены. Обновлены руководство, матрица runtime, next-task и roadmap.
