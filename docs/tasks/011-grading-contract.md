# Завершённое задание №11: контракт оценки студенческих работ

Цель: связать текущие проверки с единым отчётом student/assignment/score/feedback
и воспроизводимым запуском одного студенческого архива. Основание:
`docs/roadmap.md`, ТЗ, завершённое `docs/tasks/010-shipment-storage.md`.

## Исходное состояние

- Python загружает архив/каталог/xdump, SBSL проверяет структуру и оценивает результаты.
- Оригинальные методы исполняются в Docker; mocks и opt-in SQL-адаптер раздельны.
- PostgreSQL подтверждает хранение отгрузок, движения, замещение и откат.
- SQL-адаптер ограничен фиксированной схемой и одним запросом остатков.
  Общий объектный API, полный XBQL и платформа не эмулируются.
- Доступа к приложениям студентов не будет; новые проверки проектируются
  исключительно по исходникам и явному поддержанному контракту.

## Порядок работы

1. Сверить требования LMS из ТЗ с существующим JSON и предложить версионированный
   транспортный контракт. Не подключать реальный LMS/внешний сервис на этом этапе.
2. Добавить необязательные studentId/assignmentId/runId, сведения о совместимости
   и режиме запуска, отделив их от оцениваемых фактов. Не включать пути/секреты.
3. Нормализовать feedback по критериям: ожидаемое/фактическое, сообщение,
   баллы, UNSUPPORTED/ERROR/TIMEOUT/SKIP. Сохранить оценивание в SBSL.
4. Согласовать passed/failed/incomplete, maxScore и unavailablePoints;
   недоступный runtime или подмножество API не должны автоматически давать ноль
   за бизнес-логику студента. Проверить отрицательные ожидания и продолжение.
5. Создать пример пакета результата и JSON Schema, проверить его на всех текущих
   заданиях. Сохранить обратную совместимость CLI либо явно версионировать формат.
6. Запустить текущую регрессию с Docker/интеграцией и сохранить JSON/HTML/журнал
   в `result/poc-grading-contract`; обновить README/roadmap по фактам.

## Критерии готовности

- Один архив и assignment дают проверяемый пакет для конкретного studentId.
- Результат содержит статусы/баллы/feedback и соответствует JSON Schema.
- Баллы вычисляет SBSL, ERROR/UNSUPPORTED не выдаются за бизнес-FAIL.
- Нет зависимости от приложения Элемента, LMS или внешней сети.
- Прежние задания и изоляция продолжают работать.

Workers, persistent cache, внешняя отправка в LMS, расширение XBQL/объектного API
и полная семантика платформы остаются отдельными задачами.

## Результат

- SBSL исключает `ERROR` и `TIMEOUT` из доступного максимума; только `FAIL`
  означает невыполнение критерия. Продолжение после ошибки и отрицательные
  ожидания проверены.
- CLI принимает необязательные идентификаторы и создаёт `grading.json` v1.0
  рядом с прежними `result.json` и `report.html`.
- [Контракт](../grading-contract.md), [JSON Schema](../grading-v1.schema.json)
  и [пример](../grading-v1.example.json) сохранены в `docs`.
- Пакеты всех девяти текущих заданий валидны по JSON Schema. Структурная
  демонстрация: 6/6 PASS. Локальная регрессия без Docker: 74 теста,
  11 пропусков (`result/poc-grading-contract/unit-tests.log`). Docker daemon
  недоступен, поэтому runtime-пакеты корректно имеют `incomplete`;
  полный Docker/SQL прогон в этой среде не подтверждён.
