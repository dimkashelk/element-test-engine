# Выражения вызова и функциональные значения

Индексатор теперь хранит для каждого вызова исходные позиции, полную цепочку
имени получателя и вид выражения: прямой вызов, вызов метода, вычисляемый
получатель или ссылка `&Метод`. Комментарии и текст строк игнорируются,
выражения `${...}` разбираются. `Factory().Run()` и `Items[0].Run()` больше не
превращаются в статический вызов `Run`.

Граф и runtime используют одни и те же узлы вызовов. Ссылки на методы добавляют
достижимую зависимость; алиас внешнего модуля переписывается только в копии
XBSL для Script executor. Локальное значение, инициализированное лямбдой или
ссылкой на метод, можно вызвать. Неизвестный функциональный параметр и
вычисляемый получатель потенциального проектного метода дают диагностический
`dynamic_call` и `UNSUPPORTED` при подготовке runtime. Имя объявленного метода
имеет приоритет перед одноимённой локальной переменной. Для параметров,
переменных, переменных цикла и `поймать` учитывается конец содержащего блока.

Проверка: `tests/test_expression_calls.py` содержит случаи прямых и вычисляемых
вызовов, лямбды и их параметров, ссылки на метод с алиасом, области видимости, приоритета имени
и неразрешённого функционального параметра. Ссылка `&Alias.Value` исполняется в
локальном Script executor и возвращает `4`. Полная регрессия: 122 теста,
12 штатных пропусков.

Это **не полный AST XBSL**. Индексатор строит дерево объявлений и блоков, а для
выражений — только узлы вызова с исходными позициями. Произвольные операторы,
литералы, лямбда-тела и присваивания ещё не представлены единым деревом.
Неизвестное значение функционального параметра нельзя разрешить статически;
оно помечается как динамическое и не объявляется проверенным по графу.
На архиве `autocheck-2026-09-24-16-14.xdump` выявлен 31 такой вызов, в том
числе цепочка `Критерий.ЗагрузитьОбъект().СоздатьКопию()`. Чтобы разрешить её,
понадобится вывод типа результата промежуточного вызова.

Последующая реализация вывода типов получателей и проверка архива описаны в
