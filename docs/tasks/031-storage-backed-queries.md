# Задание №31: общие запросы по фактическому состоянию хранения

Статус: **выполнено**, 1 октября 2026 года.
Основание: [результат №30](030-transactions-and-business-exceptions.md#отчёт-о-реализации),
[универсальный runtime](../universal-runtime.md) и
[контракт транзакций](../transactions-and-business-exceptions.md).
Ниже сохранены требования этапа; фактические результаты приведены в отчёте о реализации.

## Цель и приоритет

Расширить единый pipeline planner → renderer → executor/backend → наблюдения
→ SBSL ограниченным, явно описанным AST запросов к сохранённым Справочникам
и Документам. Исходная функция должна находить реально записанные объекты,
использовать их поля и ссылки и принимать решения по текущему состоянию
своей транзакционной сессии. Результат запроса нельзя заменять строками,
подготовленными из expected, или отдельным решением известного примера.

№29–30 уже обеспечивают запись, свежую загрузку, UUID, обработчики,
транзакционные границы и независимый SQL-аудит. Однако обычный запрос к этим
данным ещё недоступен: `mocks.queries` даёт явные подставные строки, а
`query_plan.py` разбирает только ограниченный запрос остатков legacy-профиля.
Чтение из собственного состояния замыкает полезный сценарий
«записать → найти → использовать найденное → изменить → отменить/зафиксировать».

Алгоритм выбирает контракт по AST, разрешённому источнику метаданных,
типам проекций/параметров и backend. Имена объектов, namespace, методов,
поля Артикул или текст одного примера не выбирают реализацию. Python
разбирает запрос и готовит инфраструктуру, но не исполняет исходные условия,
вычисления параметров или бизнес-формулы. Код исходных зависимостей исполняет
Script executor; сравнение и баллы остаются в SBSL.

## Реальный пример и граница охвата

В неизменённом `Prakticheskie-primery-2026-09-30-15-20.xdump` метод
`РаботаСИсключениями::Номенклатура.НайтиПоАртикулу` содержит запрос:
один Справочник, проекция Ссылка, ВЫБРАТЬ ПЕРВЫЕ 1,
равенство поля параметру `%Артикул`, выполнение и
`ЕдинственныйИлиНеопределено()?.Ссылка`.
Это проверенный по исходнику кандидат приёмки; его существование не является
доказательством семантики всех операций платформы или поддержки в Script.

Пример должен работать без изменения исходного метода и без `mocks.queries`.
Для него нужны найденный/отсутствующий объект, другой артикул, сохранённый
UUID и независимый аудит. Данные задаёт преподаватель через начальное
состояние либо поддержанную запись. Для точного ожидания ПЕРВЫЕ 1 без
сортировки набор должен иметь единственное совпадение.

Основной охват этапа — один обычный источник Справочника или Документа,
проекции сохранённых полей/Ссылка, параметры, фильтрация, явная сортировка
и ограничение числа строк. Общий XBQL, JOIN, подзапросы, агрегаты,
виртуальные таблицы регистров и чтение наборов регистров в этот этап не входят.
Именованные/вложенные транзакции, параметры записи, LMS, HTTP, UI, деплой
и конкуренция сессий сохраняют прежние границы.

## Обязательный результат

### 1. Подтверждённая семантика выбранного подмножества

Перед реализацией проверить официальную документацию для используемого
режима совместимости и отдельные доверенные native-пробы Script 9.0.
Разделить наличие native API, сведения платформы и контракт адаптера.
Фиксировать сигнатуры и поведение:

- Запрос с одним источником, необязательным алиасом, полями проекций и КАК.
- Равенство и конъюнкция условий; параметры `%Имя` и `%{выражение}`.
- ВЫБРАТЬ ПЕРВЫЕ с положительным целым литералом, явная сортировка по
  поддержанным скалярным полям в обоих направлениях.
- Выполнить, обход результата и ЕдинственныйИлиНеопределено; Пусто,
  если это подтверждённая операция того же результата.
- Значения Неопределено, nullable-поля, ссылка и native UUID: правила
  сравнения, проекции, сериализации и отсутствующего результата.
- Момент вычисления параметров и момент чтения состояния; поведение
  результата после изменения данных и закрытия ресурсной области.

Не переносить автоматически правила SQL NULL на XBSL/XBQL Неопределено.
Не объявлять сортировку без УПОРЯДОЧИТЬ ПО гарантированной; в тестах
отделять порядок от состава строк. Если семантика конструкции не подтверждена,
её отклонять с объяснением. Основной запрос реального примера обязателен;
этап нельзя завершить одной недоступностью этого запроса.

### 2. AST и привязка в ExecutionPlan

Расширить существующий разбор, а не завести второй pipeline для нового
задания. По токенам/проверенным диапазонам разобрать источник, алиас,
проекции, предикаты, параметры, сортировку и лимит. Строки, комментарии,
вложенные выражения параметров и интерполяция не должны ломать границы.
Не распознавать запрос сравнением с эталонной строкой или регулярным
выражением, перечисляющим имена учебных таблиц/полей.

Разрешать владельца и поля через namespace/import/алиасы и декларации YAML.
Коллизии кратких имён, неизвестное поле, неоднозначный источник и
несовместимый тип имеют явную причину отказа. Системная Ссылка отличается
от обычного одноимённого члена по существующему контракту метаданных.
Проектный владелец или локальный получатель не подменяется платформенным API.

В плане сохранить идентичность и диапазон исходного запроса, типизированный
AST, полные идентичности источника/полей, тип строки результата, диапазоны
параметров, выбранный backend/режим и ограничения. В плане нет expected
и вычисленных преподавательских ответов. `test`, `run`, `batch` используют
один planner. Недостижимый неподдержанный запрос не блокирует доступный корень;
достижимый не даёт частичного PASS.

### 3. Выполнение по фактическим данным

Параметры и исходные зависимости вычисляются в executor в подтверждённый
момент, с сохранением кратности и порядка вычислений. Один параметр,
использованный несколько раз, не должен случайно многократно вызывать
исходный метод с побочным эффектом. Объект запроса, выполняемый повторно,
должен соблюдать зафиксированные правила, а не использовать произвольный кэш.

Выборка использует реальные начальные и записанные данные сессии. Поля
и типы результата строятся из метаданных; проекция не подменяется всем
объектом. Ссылки сохраняют UUID и разрешённого владельца. Возвращённые строки
не должны менять хранилище без предусмотренной записи. Источники с одинаковыми
краткими именами или ID остаются разными.

Memory и PostgreSQL должны совпадать в общем поддержанном контракте.
Если выбран staged-адаптер, выполнение предикатов/проекций происходит в
executor по текущему staging-состоянию; Python не вычисляет выборку.
Это нужно явно назвать адаптером запроса, а не native XBQL или SQL SELECT.
Если выбран перевод в SQL, SQL строится из разрешённого AST/метаданных,
значения передаются параметрами и обеспечивается тот же транзакционный обзор.
Чтение только ранее опубликованной smoke.objects не заменяет чтение
неопубликованных изменений активной исходной транзакции.

Подставной `mocks.queries` сохраняется отдельным явным режимом. Нельзя
молчаливо переключаться между ним и чтением storage при ошибке исполнения
или неподдержанной конструкции. Если совместное использование режимов не
входит в охват, оно отвергается до исполнения с причиной invalid_test.

### 4. Транзакционный обзор и отказы

Проверить чтение после записи до исходного commit, после commit и после
rollback, включая зависимый метод и оригинальный обработчик записи.
Ранее завершённые операции и соседние типы/записи сохраняются. Старый
`storage.transaction: true` остаётся дополнительной оболочкой; запрос
не вызывает побочную публикацию или двойной commit.

Результат чтения и независимый аудит сохраняются раздельно: возврат правильной
ссылки не доказывает корректное состояние. Отказ SQL/публикации, timeout или
файловый сбой остаётся инфраструктурным исходом с недоступными баллами,
включая общий catch в исходнике. Успешный запуск после отказа и две работы
batch с одинаковыми UUID не делят состояние; ресурсы и секреты очищаются.

## Порядок реализации

1. **31.1 — семантика и корпус.** Проверить операции/типы, выбрать точный
   охват AST, сохранить native-пробы и матрицу. Подготовить два переносимых
   проекта с разными схемами и независимые ожидания.
2. **31.2 — разбор и IR.** Добавить типизированную привязку запросов в общий
   ExecutionPlan, разрешение владельцев/полей, параметры и диагностику.
3. **31.3 — executor/backend.** Реализовать выборку по данным, результат,
   транзакционный обзор и отказы в memory/PostgreSQL; сохранить режим моков
   и прежний профиль остатков.
4. **31.4 — приёмка и миграция.** Исполнить неизменённый реальный метод,
   переносимый корпус, контролируемые ошибки, CLI и регрессию. Обновить
   задания, руководство, ограничения и отчёт по действительным результатам.

Все четыре части обязательны. Компиляция адаптера или единственный запрос
из примера сами по себе не завершают этап.

## Критерии приёмки

| Проверка | Необходимое доказательство |
|---|---|
| Реальный xdump | Неизменённый НайтиПоАртикулу находит единственное совпадение либо возвращает Неопределено; ссылка и UUID соответствуют независимым данным |
| Переносимость | Не менее двух проектов: другие namespace, методы, алиасы, поля, Справочник/Документ и типы параметров; без правок алгоритма |
| Поля и параметры | Несколько проекций с КАК, условия по двум полям, строковый/числовой/ссылочный параметр; вход с кавычками и текстом выражения остаётся значением |
| Кратность вычисления | Параметр из исходной А → Б → В и параметр с побочным эффектом вычисляются по подтверждённой семантике; ошибка зависимости меняет результат |
| Пустота и количество | Пустой результат, единственная и несколько строк; поведение ЕдинственныйИлиНеопределено проверено по подтверждённому контракту |
| Порядок и лимит | Сортировка в обоих направлениях и ПЕРВЫЕ дают независимый ожидаемый результат; без сортировки не оценивается произвольный порядок |
| Актуальность состояния | Чтение до commit видит собственные записи; после rollback отменённых данных нет; ранее завершённые операции сохранены |
| Свежие строки | Изменение возвращённой строки без записи не меняет хранилище; повторный запрос соблюдает подтверждённые правила чтения |
| Коллизии | Одинаковые краткие владельцы/UUID в разных namespace не смешиваются; неоднозначные/затенённые/неизвестные обращения честно отклоняются |
| Memory/PostgreSQL | Возврат и сохранённое состояние совпадают; независимый SQL-аудит и backend-отказ подтверждены |
| Ошибки работы | Пропуск предиката, неверный параметр/поле, неправильный источник/сортировка/лимит и чтение устаревшего состояния дают FAIL через SBSL |
| Честная недоступность | JOIN/виртуальная таблица/иная неподдержанная достижимая форма даёт UNSUPPORTED; последующий успешный критерий исполняется |
| Совместимость | Старые явные mocks.queries, legacy остатки, №29–30 и прежние успешные баллы сохранены; test/run/batch совпадают |
| Изоляция | Две работы batch с одинаковыми ID не делят состояние; после отказов нет контейнеров, сетей, credentials и публичной утечки секретов |

Для каждого нового общего контракта нужны независимые PASS,
контролируемый FAIL и обоснованный UNSUPPORTED. Ожидания задаёт преподаватель;
вывод проверяемого метода или адаптера не используется как эталон.

## Проверка и артефакты

Submission XBSL исполняется только в Docker. Native-пробы на хосте содержат
только отдельный доверенный код. Архивы открываются на чтение.
После целевых тестов выполнить общую регрессию с Docker/SQL, четыре validate
и контроль SHA-256, согласовать test/run/batch и публичные grading-пакеты.
Не заявлять проверенным новый контракт по одной подготовке SBSL.

Корпус и задания преподавателя включить в репозиторий. В
`result/storage-backed-queries/` сохранить матрицу, native-пробы, планы/AST,
трассы параметров и исходных вызовов, независимые аудиты до/после/при отказе,
PASS/FAIL/UNSUPPORTED, журналы, CLI-сопоставление, JSON/HTML/grading и очистку.

Текущие fixtures недоступности трёх практических заданий используют именно
НайтиПоАртикулу. После его поддержки их необходимо заменить другой реально
неподдержанной границей и объяснить миграцию. Устранение старого UNSUPPORTED
не должно скрывать изменение максимума, недоступных баллов или ожиданий.
Обновить README, руководство, матрицу runtime, next-task и roadmap;
в конце задания дать отчёт с фактическими результатами и оставшимися границами.

## Отчёт о реализации

Этапы 31.1–31.4 реализованы 1 октября 2026 года. Общий planner сохраняет
типизированный `StorageQuery` AST и capability-привязки, renderer генерирует
staged-адаптер, executor выполняет параметры, предикаты, проекции и сортировку
по текущему состоянию сессии. Ветка по имени Номенклатура/Артикул отсутствует.
Неизменённый реальный НайтиПоАртикулу исполняется в Docker без mocks.
[Подтверждённая семантика и границы](../storage-backed-queries.md).

31.1: документация платформенного API 9.1 проверена через авторизованный браузер;
раздел 9.0 возвращает 404. Отдельные native-пробы Script `-c 9.0` подтвердили
отсутствие Запрос, native массив/UUID/readonly/passing semantics. Поэтому
реализован явно описанный staged-контракт, а не заявлен native XBQL.

31.2: разбор добавлен в существующий `query_plan.py`; источник и поля связаны
через общие ProjectTypes/namespace/import/alias. Планы содержат исходную
идентичность/диапазон, AST, полные владельцы, тип строки, все диапазоны
параметров и backend; expected отсутствует. Противоречивые типы, неизвестные
поля/источники, коллизии и затенение отклоняются. Недостижимый JOIN не блокирует
поддержанный корень. Публичные планы заменяют текст запроса/выражения хешами.

31.3: memory/PostgreSQL используют одну выборку в executor по актуальному
staging. Параметры фиксируются при создании; каждое Выполнить читает новое
состояние. Отдельные expression occurrences выполняются по одному разу;
повтор простой переменной использует captured slot. Ссылочный параметр
сохраняет независимый снимок UUID/владельца. Проекции readonly, возвращённые
значения отделены от storage. Исходные обработчики и транзакции используют
то же состояние; чтение не вызывает commit. Файловый sticky-маркер и служебный
признак отказа в выводе дополняют существующий SQL-маркер: общий catch не
скрывает инфраструктурный отказ, даже когда запись файла маркера недоступна.

31.4: включены Catalog/Document corpus и независимые teacher assignments,
real xdump, мутации source/projection/predicate/parameter/dependency/order/limit/
stale-read, неподдержанные конструкции и продолжение после отказа. Три
практических fixture перенесены с поиска по артикулу на реальный В ИЕРАРХИИ;
основные задания/баллы не менялись. README, руководство, runtime matrix,
next-task и roadmap обновлены.

- Целевой Docker/SQL набор — **13/13, без пропусков**, 224.971 секунды;
  `result/storage-backed-queries/target-tests.log`. Дополнительная проверка
