# Следующее задание: интеграционное окружение для хранения и XBQL

Цель: выбрать и подтвердить минимальным воспроизводимым экспериментом окружение
для реального хранения данных и выполнения запросов. Установить границу между
возможностями платформы Элемента и API, который потребуется реализовать адаптером.
Не считать прямое SQL-соединение эмуляцией объектного API платформы.

## Исходное состояние

Эксперимент №8 завершён: `assignments/poc-receipt` — 5/5 PASS в Docker.
Оригинальный обработчик переносит склад и четыре поля строки, сохраняет порядок
и дописывает строки. Шесть неверных ожиданий дают FAIL в SBSL; неизвестный
fake-ID — ERROR, неподдержанный контракт — UNSUPPORTED. Следующие проверки
после каждого отрицательного случая проходят.

Поддержаны YAML-контракты, объектный context, observe, fake-ссылки,
регистры сведений/накопления как наблюдаемые подставные API, подставные запросы,
union-входы, runtime-дата и типы конструкторов из достижимых методов.
Хранение документов и движений, пересчёт остатков и исполнение XBQL отсутствуют.
Полная Docker-регрессия прошла 48 тестов; после добавления проверки импорта
текущий набор содержит 49 тестов (40 PASS без Docker, 9 opt-in Docker-тестов).
Архив предыдущего задания: `docs/tasks/008-receipt.md`.

## Порядок работы

1. Провести разведку доступных локальных средств и безопасно прочитать
   оригинальные `Отгрузка.ПередЗаписью`, `Отгрузка.ПослеЗаписи`, YAML регистра
   товаров и используемый запрос из `Движок.tar`. Составить точный перечень API,
   необходимого для интеграционного сценария: загрузка/запись документов,
   типизированные ссылки, набор записей и фильтр регистратора, период/вид движения,
   запись с замещением и запрос остатков. Проверить документацию по версиям
   платформы; не выводить сигнатуры API по аналогии.
2. Создать `docs/integration-environment.md` с решением и основаниями выбора:
   - полноценное приложение Элемента: реальная семантика API и XBQL, требования
     к окружению, авторизации, изоляции данных и автоматизации;
   - PostgreSQL + адаптер: воспроизводимость локально, доступ из Script runtime,
     необходимый объектный API, отличие SQL от XBQL и стоимость его реализации.
   Проверить возможности установленного Script executor, не предполагая наличие
   драйвера БД или объектного API. Зафиксировать подтверждённые возможности,
   ограничения и оставшиеся вопросы. Выбрать один путь для прототипа по фактам.
3. Ввести явный opt-in интеграционный режим, отдельный от текущих mocks.
   Описать конфигурацию backend, жизненный цикл тестового набора данных,
   проверку доступности и поддержанные операции. Добавить preflight:
   отсутствующее окружение/драйвер/неподдержанная операция должны давать
   понятный UNSUPPORTED, а не успешный результат подставного запроса.
   Секреты получать из окружения; не включать их в Git, отчёты и журнал.
4. Сделать минимальный доверенный smoke-сценарий выбранного backend:
   записать два разных набора данных, прочитать их настоящим запросом,
   проверить фильтрацию и дробные значения, изменить один набор и прочитать
   повторно. Выполнить сценарий дважды с независимыми идентификаторами данных,
   проверить отсутствие состояния между запусками и очистку после ошибки.
   Проверяемые результаты передавать SBSL-движку для сравнения и оценки.
   Если применён SQL, явно назвать сценарий SQL smoke; он не подтверждает XBQL.
   Если окружение недоступно, реализовать проверяемый preflight и сохранить
   точную причину; не заменять интеграционный smoke моками и не объявлять PASS.
5. Разделить доверенную инфраструктуру и студенческий код. Студенческую логику
   продолжать выполнять только в Docker. Для локального backend организовать
   отдельную закрытую сеть без внешнего доступа и изоляцию данных на запуск;
   прежний режим mocks сохранить с `--network none` и действующими лимитами.
   Не выполнять студенческие модули на хосте, не импортировать их целиком,
   не передавать им административные полномочия. Не использовать рабочую БД.
6. Добавить проверки конфигурации, недоступного backend, неподдержанных операций,
   изоляции и очистки. Отрицательное ожидание должно давать FAIL в SBSL;
   ERROR/UNSUPPORTED не должны прерывать следующие проверки.
   Запустить всю текущую регрессию с Docker и отдельный интеграционный набор.
   Сохранить JSON/HTML и журнал в `result/poc-integration-environment`;
   документировать команды воспроизведения, выбранный backend и реальные исходы.
7. Обновить README и roadmap. По результатам прототипа подготовить следующее
   задание на запуск оригинальных обработчиков отгрузки с реальным хранением
   и запросом остатков, перечислив API, который ещё требуется реализовать.

## Критерии готовности

- Выбор backend оформлен с проверяемыми основаниями, возможностями runtime,
  требованиями к запуску и явной границей SQL/XBQL/объектного API.
- Интеграционный режим включается явно; текущие задания с mocks работают как прежде.
- Preflight различает недоступное окружение и неподдержанную операцию;
  эти состояния не превращаются в PASS и не останавливают остальные проверки.
- При доступном backend доверенный smoke подтверждает реальную запись, чтение,
  изменение, фильтрацию, дробные значения, изоляцию и очистку.
  Если backend недоступен, ограничение отражено как UNSUPPORTED и критерий
  реального smoke явно остаётся невыполненным.
- Сравнение и оценивание выполняются SBSL. Все 49 текущих тестов проверены
  с включёнными Docker-тестами; новые проверки добавлены сверх этого набора.
- Исходный архив неизменен. Конфигурация, отчёты и журнал не содержат секретов.

## Границы этапа

Это выбор окружения и минимальный интеграционный прототип. Полная реализация
XBQL, виртуальных таблиц, объектного API, транзакций и повторного проведения
не входит в текущую итерацию. Прототип не должен обещать такую семантику.

У `ПоступлениеТоваров` в исходном архиве нет `ПослеЗаписи`: не создавать
несуществующий обработчик прихода. Не менять бизнес-логику студента ради backend.
Массовые workers, кэш, LMS и расширение лексического анализа — отдельные этапы.
