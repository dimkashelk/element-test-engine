# Исходный query entry — №47

`type: runtime` принимает `querySource` вместо `target`/`args`. Общий вход
исполняет исходный литерал XBSL или отдельный XBQL через существующий storage AST.
Python выбирает исходник и генерирует адаптер; чтение, JOIN, CASE, агрегаты,
срезы и сравнение выполняются в Script/SBSL. Фиктивного метода в проекте или
execution plan нет. Исходный файл остаётся неизменным.

## Выбор и входы

```yaml
type: runtime
querySource:
  file: Data/Totals.xbql
  # range: [0, 180]             # точное исходное вхождение [start,end)
  # sourceHash: <SHA-256 файла> # проверка конкретной редакции
  # projectSourceHash: <SHA-256 проекта>
queryParameters:
  Keys:
    type: Массив<Строка>
    value: [a, b]
storage:
  idType: Ууид
  registers: [Data::Book]
  initial: []
  initialRegisters: []
runtimeProfile: '9.3'
```

Пример описывает входы механизма; `id`, `points` и независимое `expected`
задаёт автор задания. Исходник обязан действительно содержать соответствующий
query и параметр. Готовые строки результата во входном контракте отсутствуют.

Для `.xbsl` `range` охватывает `Запрос{…}`, для `.xbql` — весь текст после
удаления BOM. Позиции — символы, хэш — исходные байты. Без `range` допустимо
ровно одно вхождение. Равные тексты в разных методах не объединяются.
Путь обязан находиться внутри выбранного проекта, включая разрешение symlink.
XBQL требует однозначного metadata owner; namespace/import берутся из него.
Составные архивы и выбор библиотеки используют прежний `select_check_project`.

`queryParameters` содержит ровно внешние captured выражения AST: строковое
имя выражения → `{type, value}`. Коллекции и ссылки проверяются по типу и
владельцу. В самостоятельном входе значения сложных `%{…}` задаются явно как
captured входы; содержащий бизнес-метод не вызывается. Его обычный `target`
по-прежнему вычисляет исходное выражение. Системные captures можно задавать
прежним `queryContext`; правила чтения — `queryAccess`.

XBQL `&Имя` преобразуется в `%Имя` только в памяти, с сохранением длины и
позиций. Строки/комментарии защищены лексером. Plan хранит отдельно `text` и
`astText`, owner, диапазон, хэши файла/проекта и dependency hashes. Ожидания
и значения fixtures в `queryEntry` не записываются.

## Срез и смешанный результат

`.СрезПоследних` и `.СрезПервых` без скобок принимаются как отсутствие
параметров, с семантикой прежнего адаптера `()`. Диапазон и оригинальный текст
не меняются. Последний срез захватывает границу при создании query, а повторное
`Выполнить` читает свежее состояние по той же границе. WHERE применяется после
выбора среза по всем измерениям. Первый срез без границы использует минимум.

Неявная граница последнего среза учитывает явно заданный `clock`:
День → дата, Секунда → снимок даты/времени, Момент с fixed clock → UTC instant.
Без clock остаётся прежний runtime UTC. Для Момент с docker clock требуется
явная типизированная граница; неподдержанный случай возвращает точную причину.
Это контракт эмулятора, не свидетельство native поведения 1С.

CASE с разными скалярными и ссылочными ветвями получает union результатов,
например `Контрагенты.Ссылка|Строка|?` для «Нет поставщика» / ссылки поставщика.
Вложенные CASE объединяют конкретные варианты без повторов. Ссылочный вариант
копируется при проекции и сохраняет номинальный тип; смешанный результат
передаёт его как `{type: "CRM::Контрагенты.Ссылка", value: {Идентификатор: …}}`
через штатную сериализацию Script и нормализацию типов движка.
NULL сохраняет отдельный флаг во внутреннем AST, наружу
передаётся как `null`. Описания колонок содержат отдельные члены множества
типов. НЕОПРЕДЕЛЕНО также допускается в результате, но не получает SQL-флаг NULL;
пропущенное ИНАЧЕ означает NULL. Memory и PostgreSQL используют один адаптер.
Несовместимая арифметика/сортировка union и прочие неподдержанные формы
продолжают возвращать UNSUPPORTED, без преобразования цены в строку.

Целевая регрессия смешанного CASE — `tests/test_query_case_references.py`:
оба порядка ветвей, вложенный CASE, простой CASE, NULL/НЕОПРЕДЕЛЕНО,
пропущенное ИНАЧЕ, тип захваченного параметра, дескрипторы колонок,
повторное чтение после записи и одинаковые UUID ссылок разных владельцев.
Исполняемые сценарии запускаются в memory и PostgreSQL с независимым SQL-аудитом.
Исходные `ОтчетПоставщикиНоменклатуры` и `ПанельОтчетовГлавная` из
`Dvizhok-dev-final.xdump` проверяются на товаре с поставщиком и товаре без него,
включая `data` и `values` макета. В `data` смешанная ссылка имеет тег типа,
в динамических `values` — прежнее представление `{Идентификатор: …}`.
Архив остается неизменным. Это проверка данного сценария, не полная бизнес-приёмка дампа.

```sh
ELEMENT_TEST_DOCKER_TESTS=1 PYTHONPATH=tests python3 -m unittest test_query_case_references -v
```

## Действия и наблюдения

Без `queryActions` выполняется один query. Дополнительно можно задать:

```yaml
queryActions:
  - operation: execute
  - operation: write
    objects: []
    registers: []
  - operation: execute
```

`objects` использует формат `storage.initial`, `registers` —
`storage.initialRegisters`: `{type, filter, rows}`. Эти записи используют
существующий типизированный storage API; lifecycle исходного объекта и
enforcement metadata ограничений относятся к №50. Query создаётся один раз;
каждое execute возвращает отдельный снимок. Максимум 40 действий, минимум
одно execute. При `storage.transaction: true` действия атомарны.

Один результат имеет вид:

```json
{"result":{"rows":[],"cardinality":0,"columns":[],
 "resource":{"kind":"query-result","closed":true,"started":true}},
 "storage":[]}
```

При явном `queryActions` поле `result` содержит `actions` — последовательность
наблюдений execute; write наблюдается через последующее чтение и итоговый
аудит. Каждый query-result полностью материализуется и освобождается.
`columns` — прежние дескрипторы адаптера с `Имя`, `ТестТип`, `Типы` и
квалификаторами. Типы сериализуются именами Script, например `Std::Number`.
`storageTrace` и `storageDiagnostics` остаются отдельными техническими фактами.

`comparison: query-rows-unordered` сравнивает строки как мультимножество,
сохраняя кратность, NULL, значения, остальные наблюдения и порядок actions.
Прежний формат `result: [строки]` поддерживается. `record-sets-unordered`
сравнивает новое наблюдение с учётом порядка строк; storage в обоих режимах
аудируется независимо. Оценка и баллы вычисляются только в SBSL.

`test`/`run`/`batch` используют общий planner/render/runtime. Memory backend
изолирован на проверку; PostgreSQL читает staging и заменяет итоговый аудит
независимым чтением SQL. Контейнеры и сеть удаляются прежним integration API.
Некорректный селектор/хэш/вход даёт `invalid_test`; unsupported AST —
`unsupported_syntax`; недоступная среда — `backend_unavailable`.

## Стадии и границы

`queryEntry.stages` разделяет validation, planning, generation и execution.
Планирование/генерация модулей не являются компиляцией или исполнением;
execution остаётся `not-checked` в plan. Реальное исполнение записывается в
runtime-evidence, независимая оценка — в result/grading. Общая capability map
также оставляет adapter/technicalAcceptance исходников `not-checked`.

Все пять query-форм Dvizhok-final принимаются, валидируются, планируются и
генерируются с точной исходной идентичностью. Авторские сценарии, expected и
исполнение финального дампа не создавались. Техническая приёмка выполнена
на переиспользуемых fixtures механизма. Исходник 9.0 и executor current
хранятся раздельно; native XBQL, ACL/RLS и отображение отчёта остаются внешними
границами. Данные/формулы/макет отчёта относятся к №51.
