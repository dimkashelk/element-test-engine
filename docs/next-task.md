# Следующее задание: поступление на основании отгрузки

Цель: запустить оригинальный `ПоступлениеТоваров.ПриСозданииНаОсновании`
из `Движок.tar` в Docker и проверить перенос склада и строк отгрузки.
Продолжить существующую архитектуру: бизнес-логика исполняется Скриптом,
сравнение результатов и оценивание выполняются SBSL-движком.

## Исходное состояние

Этап движений завершён: `assignments/poc-movements` — 4/4 PASS,
семь неверных ожиданий — FAIL; после UNSUPPORTED выполнение продолжается.
Общая регрессия: 43 теста прошли, включая Docker.
Поддержаны объектный context, observe, fake-ссылки с `ЗагрузитьОбъект()`,
union-входы `{type, value}` и `ДатаВремя`.

По уточнению пользователя текущую дату/время получать в runtime внутри Docker.
Когда дата нужна сценарию, использовать `runtimeDateTime` и независимый снимок
до обработчика с маркером `__runtimeDateTime__` в ожиданиях; не вычислять дату
для ожиданий повторно на хосте. Этот обработчик дату не переносит.

## Порядок работы

1. Прочитать оригинальный обработчик и YAML отгрузки/поступления через безопасную
   загрузку архива. Он загружает отгрузку через fake-ссылку, присваивает склад,
   создаёт `новый ПоступлениеТоваров.Товары(...)` и добавляет строки в `этот.Товары`.
   В архиве у `ПоступлениеТоваров` нет `ПослеЗаписи`; не создавать студенту
   несуществующий обработчик и не подменять этот эксперимент тестом прихода.
2. Расширить обнаружение зависимостей типов из тела методов. В первую очередь
   поддержать проектные типы в выражениях `новый ИмяОбъекта.Тип(...)`, включая
   `ПоступлениеТоваров.Товары`. Анализировать код, исключая строки и комментарии;
   учитывать достижимые методы того же модуля, namespace и конфликты имён.
   Генерировать только необходимые YAML-контракты. Не импортировать целиком
   студенческие модули и не исполнять их на хосте. Неразрешённые, неоднозначные
   или неподдержанные типы должны давать UNSUPPORTED с понятным сообщением.
   Сохранить тело обработчика; если адаптация квалифицированных имён необходима,
   ограничить её разрешёнными токенами типов и описать явно.
3. Создать `assignments/poc-receipt` для реального обработчика:
   - пустая табличная часть;
   - одна строка;
   - несколько строк с разными товарами и сохранением порядка;
   - дробные количество, цена и сумма.
   Задать `mocks.objects` для `Отгрузка.Ссылка`, начальный context поступления
   и `observe: [Склад, Товары]`. Проверять склад и все четыре поля каждой строки:
   Номенклатура, Количество, Цена, Сумма. Задать сумму, отличающуюся от
   Количество × Цена: обработчик переносит готовую сумму, а не пересчитывает её.
4. Добавить сценарий с уже заполненной ТЧ поступления: исходный обработчик
   дописывает новые строки, не очищая существующие. Начальный склад поступления
   сделать отличным от склада отгрузки, чтобы проверить замену склада.
   Проверить две разные fake-ссылки с разными данными и отсутствие состояния,
   протекающего между сценариями. Не добавлять обработчику лишнюю бизнес-логику.
5. Добавить отрицательные проверки ожиданий: неверный склад, номенклатура,
   количество, цена, сумма и порядок строк должны давать FAIL в SBSL.
   Неизвестный fake-ID должен давать ERROR; неподдержанный контракт —
   UNSUPPORTED. После каждого такого случая следующие проверки продолжаются.
   Добавить модульные проверки обнаружения типов: строка/комментарий с `новый`,
   неизвестный тип, конфликт кратких имён и необходимый импорт типа из тела.
6. Запустить модульные и Docker-тесты, сохранить JSON/HTML-отчёты положительных
   и отрицательных сценариев и журнал тестов. Обновить README и roadmap:
   результаты, поддержанные формы ссылок на типы из тела и ограничения анализа.

## Критерии готовности

- Четыре основных сценария оригинального обработчика и сценарий дописывания
  существующих строк дают PASS в Docker.
- Отрицательные ожидания дают FAIL при сравнении в SBSL; ERROR и UNSUPPORTED
  не прерывают остальные проверки.
- Прежние сценарии движений, регистра сведений, запросов, fake-ссылок,
  объектного контекста, union-входов и runtime-даты продолжают проходить.
- Тело оригинального обработчика сохраняется, а подключение проектных типов
  из тела явно покрыто тестами и документацией.
- Исходный архив остаётся неизменным; студенческий код выполняется только
  в изолированном Docker-контейнере с действующими ограничениями.

## Границы этапа и дальнейшая работа

Проверяется создание поступления на основании в памяти. Хранение документов,
запись движений прихода, повторное проведение, транзакции, выполнение XBQL
и полноценное разрешение внешних методов/библиотек не входят в этот этап.

После этого отдельно выбрать интеграционное окружение для реального хранения
и XBQL: полноценное приложение Элемента либо PostgreSQL вместе с адаптером
необходимого API. Прямой доступ к SQL сам по себе не реализует объектный API
платформы, фильтры наборов и виртуальные таблицы регистров.
