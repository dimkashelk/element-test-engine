# Следующее задание: движения регистра накопления

Цель: запустить оригинальный `Отгрузка.ПослеЗаписи` из `Движок.tar` в Docker
и проверить сформированные движения `РегистрТовары` через журнал вызовов.
Продолжить существующую архитектуру: бизнес-логика выполняется в Скрипте,
сравнение и оценивание — в SBSL-движке.

## Порядок работы

1. Расширить генератор входных значений для `ДатаВремя` и типов объединения.
   В архиве `РегистрТовары.Регистратор` имеет тип
   `Отгрузка.Ссылка|ПоступлениеТоваров.Ссылка|?`. Для неоднозначных входов
   определить явное указание типа варианта; неправильные варианты отклонять.
   Дату задавать детерминированно, не брать текущее время из окружения.
2. Добавить моки `РегистрНакопления.НаборЗаписей`: фильтр по `Регистратор`,
   системные поля записи `Период` и `ВидЗаписи`, измерения и ресурсы из YAML.
   Поддержать используемый обработчиком `ВидЗаписиРегистраНакопления.Расход`.
   Сверить тип периода, значения по умолчанию и сигнатуру `Записать()` с API
   платформы. Не переносить автоматически контракт `Замещать` из регистра сведений.
3. Создать `assignments/poc-movements` для реального `Отгрузка.ПослеЗаписи`:
   пустая табличная часть, одна строка, несколько строк, дробное количество.
   Проверить порядок: установка фильтра, добавление движений, запись набора.
   У каждого движения проверить период, расход, номенклатуру, склад и количество;
   у фильтра — ссылку отгрузки. В пустом случае набор всё равно записывается.
4. Добавить отрицательные проверки: неверный регистратор, склад, количество,
   вид движения или порядок вызовов должны давать `FAIL`. Неподдержанный
   контракт должен давать `UNSUPPORTED`, последующие проверки должны продолжаться.
5. Запустить модульные и Docker-тесты, сохранить JSON/HTML-отчёт,
   обновить README и roadmap с результатами и ограничениями.

## Критерии готовности

- Четыре основных сценария реального обработчика дают `PASS` в Docker.
- Отрицательные ожидания дают `FAIL` при сравнении в SBSL.
- Прежние сценарии регистра сведений, запросов, fake-ссылок и объектного
  контекста продолжают проходить.
- Исходный архив остаётся неизменным; студенческий код исполняется только
  в изолированном Docker-контейнере.
- Тело обработчика сохраняется; адаптация типов и системных API описана явно.

Пока проверяется формирование движений и вызов записи. Хранение движений,
повторная запись, очистка по регистратору, пересчёт остатков и транзакции
не считаются реализованными этим этапом.

## После этого этапа

Следующий эксперимент — оригинальный
`ПоступлениеТоваров.ПриСозданииНаОсновании`: fake-ссылка отгрузки,
перенос склада и всех полей строк, пустая и многострочная табличные части.
Он потребует подключения проектных типов, используемых внутри тела метода.
В исходном архиве у `ПоступлениеТоваров` нет `ПослеЗаписи`; не добавлять
студенту несуществующий обработчик для теста прихода.

Затем отдельно выбрать интеграционное окружение для проверки реального
хранения и XBQL. PostgreSQL рассматривать вместе с необходимым адаптером API
либо использовать полноценное приложение Элемента.
