# План по техническому заданию

Основание: `ТЗ_система_тестирования_1С_Элемент.docx`, версия 0.1.

| Этап | Состояние | Дальнейшая работа |
|---|---|---|
| 1. Project Inspector | Первая реализация | Полная семантика namespace/import, валидация схем |
| 2. Structural Testing | Первая реализация | Группы критериев, более точные сообщения о свойствах |
| 3. XBSL Indexer | Лексический индекс | AST, модификаторы, зависимости методов и обращения к объектам |
| 4. Element Script PoC | ФИО, цикл и локальные зависимости подтверждены | AST, внешние методы и типы из тела |
| 5. Generated Project Types | Эксперимент №2 подтверждён | Заказ.Товары и полный Заказ.Объект/Данные с перечислением; далее union, namespace и циклы |
| 6. Object Context | Реальные обработчики подтверждены | `этот`, поля, void, пустые параметры записи и fake-ссылки; далее полная семантика API |
| 7. Platform Mocks | Fake-ссылки реализованы | НаборЗаписей, Фильтр, запросы; эксперимент №6 |
| 8. Mass Runner | Есть изоляция одного теста | Workers, кэш по хэшу, потоки событий |
| 9. LMS Integration | Запланировано | Контракт student/assignment/score/feedback |

Архитектура первого этапа:

```text
каталог/архив + assignment.yaml
  → Python: безопасная загрузка, YAML/XBSL → JSON IR
  → SBSL: структурные проверки, сигнатуры
  → Python: оригинальный метод + необходимые типы YAML → временные SBSL-модули + Docker
  → Script executor: выполнение оригинальной бизнес-логики
  → SBSL: сравнение результата и оценивание
  → Python: JSON/HTML-отчёт
```

Результаты первого эксперимента на `Движок.tar`: 40 объектов, 5 подсистем,
29 XBSL-модулей; структурные проверки 6/6, ФИО 3/3
(обычные значения, лишние пробелы, пустые строки).
Исходный архив в Git не включается; находится локально для повторного эксперимента.

Эксперимент №2: `ЗаказФормаОбъекта.РассчитатьИтоги(Массив<Заказ.Товары>)`
выполнен без UI-контекста и без изменения бизнес-логики. Генерируются
`Заказ.Товары` и `Номенклатура.Ссылка`; остальные типы проекта не нужны.
Пустой массив, несколько строк и дробные значения — 3/3 PASS.
Отрицательная проверка неверного ожидаемого итога даёт FAIL в SBSL.
В отдельном доверенном примере executor проверены минимальные `Объект`, `Данные`,
`Ссылка`, добавление строк и `Размер()`. Это ещё не эмуляция объектного контекста.
Эксперимент №3: полный контракт `Заказ.Объект`/`Заказ.Данные` из исходного архива
с перечислением `СтатусЗаказа` компилируется и создаётся в executor.
Эксперимент №4: доверенный объектный fixture проверяет `этот`, неявные поля,
затенение поля параметром, перечисления в сигнатуре, чтение табличной части
и обработчик без результата. Два сценария исполняются также в Docker;
неверное ожидаемое состояние даёт FAIL в SBSL.
Эксперимент №5: реальные `ФизическиеЛица.ПередЗаписью` и
`Заказ.ПриСозданииНаОсновании` — 5/5 PASS в Docker. Подключаются транзитивные
методы того же модуля (включая интерполяцию), генерируются пустые
`ПараметрыЗаписи`, fake-ссылки загружают типизированные снимки через
`ЗагрузитьОбъект()`. Квалифицированный тип из сигнатуры заказа разрешается
по поставщику, проекту и подсистеме. `observe` задаёт проверяемые поля состояния.
Неверное ожидание даёт FAIL; неизвестный fake-ID — ERROR; следующий тест продолжается.
Снимки при каждой загрузке создаются заново; хранение изменений и запись не моделируются.
Следующий этап — моки регистров и запросов: в архиве `Номенклатура.ПослеЗаписи`
использует `НаборЗаписей`, `Фильтр.Установить`, `ДобавитьЗапись`, `Записать`;
`Отгрузка.ПередЗаписью` — встроенный `Запрос{...}`, `Выполнить`, `ВСоответствие`
и проверку остатков. Для них потребуются системное поле `Ссылка`, захват вызовов
регистра и отдельная адаптация встроенного запроса.
