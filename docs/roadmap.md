# План по техническому заданию

Основание: `ТЗ_система_тестирования_1С_Элемент.docx`, версия 0.1.

| Этап | Состояние | Дальнейшая работа |
|---|---|---|
| 1. Project Inspector | Первая реализация | Полная семантика namespace/import, валидация схем |
| 2. Structural Testing | Первая реализация | Группы критериев, более точные сообщения о свойствах |
| 3. XBSL Indexer | Лексический индекс | AST, модификаторы, зависимости методов и обращения к объектам |
| 4. Element Script PoC | ФИО, цикл и локальные зависимости подтверждены | Конструкторы типов из тела поддержаны; далее AST и внешние методы |
| 5. Generated Project Types | Эксперимент №2 подтверждён | Заказ.Товары и полный Заказ.Объект/Данные с перечислением; union и квалифицированные типы поддержаны; далее namespace/import и циклы |
| 6. Object Context | Реальные обработчики подтверждены | `этот`, поля, void, пустые параметры записи и fake-ссылки; далее полная семантика API |
| 7. Platform Mocks | Fake-ссылки, регистры сведений/накопления и подставные запросы реализованы | Эксперимент №7: формирование расхода; далее хранение, периоды, дополнительные формы запросов |
| 8. Mass Runner | Есть изоляция одного теста | Workers, кэш по хэшу, потоки событий |
| 9. LMS Integration | Запланировано | Контракт student/assignment/score/feedback |

Архитектура первого этапа:

```text
каталог/архив + assignment.yaml
  → Python: безопасная загрузка, YAML/XBSL → JSON IR
  → SBSL: структурные проверки, сигнатуры
  → Python: оригинальный метод + необходимые типы YAML → временные SBSL-модули + Docker
  → Script executor: выполнение оригинальной бизнес-логики
  → SBSL: сравнение результата и оценивание
  → Python: JSON/HTML-отчёт
```

Результаты первого эксперимента на `Движок.tar`: 40 объектов, 5 подсистем,
29 XBSL-модулей; структурные проверки 6/6, ФИО 3/3
(обычные значения, лишние пробелы, пустые строки).
Исходный архив в Git не включается; находится локально для повторного эксперимента.

Эксперимент №2: `ЗаказФормаОбъекта.РассчитатьИтоги(Массив<Заказ.Товары>)`
выполнен без UI-контекста и без изменения бизнес-логики. Генерируются
`Заказ.Товары` и `Номенклатура.Ссылка`; остальные типы проекта не нужны.
Пустой массив, несколько строк и дробные значения — 3/3 PASS.
Отрицательная проверка неверного ожидаемого итога даёт FAIL в SBSL.
В отдельном доверенном примере executor проверены минимальные `Объект`, `Данные`,
`Ссылка`, добавление строк и `Размер()`. Это ещё не эмуляция объектного контекста.
Эксперимент №3: полный контракт `Заказ.Объект`/`Заказ.Данные` из исходного архива
с перечислением `СтатусЗаказа` компилируется и создаётся в executor.
Эксперимент №4: доверенный объектный fixture проверяет `этот`, неявные поля,
затенение поля параметром, перечисления в сигнатуре, чтение табличной части
и обработчик без результата. Два сценария исполняются также в Docker;
неверное ожидаемое состояние даёт FAIL в SBSL.
Эксперимент №5: реальные `ФизическиеЛица.ПередЗаписью` и
`Заказ.ПриСозданииНаОсновании` — 5/5 PASS в Docker. Подключаются транзитивные
методы того же модуля (включая интерполяцию), генерируются пустые
`ПараметрыЗаписи`, fake-ссылки загружают типизированные снимки через
`ЗагрузитьОбъект()`. Квалифицированный тип из сигнатуры заказа разрешается
по поставщику, проекту и подсистеме. `observe` задаёт проверяемые поля состояния.
Неверное ожидание даёт FAIL; неизвестный fake-ID — ERROR; следующий тест продолжается.
Снимки при каждой загрузке создаются заново; хранение изменений и запись не моделируются.
Эксперимент №6: `assignments/poc-platform` — оригинальный
`Номенклатура.ПослеЗаписи` проверяет фильтр номенклатуры, ссылку и цену записи,
`Замещать = Ложь` и порядок вызовов. Добавлено системное поле `Объект.Ссылка`.
Оригинальный `Отгрузка.ПередЗаписью` получает типизированные подставные строки
для `Запрос{...}`: достаточный остаток, точное равенство, недостаточный и
отсутствующий товар. Проверяются параметры запроса, его выполнение и тип/текст
исключения. Бизнес-логика проверки остатков и `ВСоответствие` выполняются Скриптом.
Моки не исполняют XBQL и не эмулируют хранение данных; полный интеграционный
тест платформенных регистров остаётся отдельным этапом.

Эксперимент №7: `assignments/poc-movements` — оригинальный
`Отгрузка.ПослеЗаписи`: пустая ТЧ, одна/несколько строк и дробное количество,
4/4 PASS в Docker. Фильтр проверяется по типизированному union-регистратору,
каждый расход — по периоду, номенклатуре, складу и количеству; порядок
событий сравнивается SBSL. API регистра накопления отдельно подтверждает
`Период: ДатаВремя` и `Записать(Замещать: Булево = Истина)`.
Семь неверных ожиданий дают FAIL; неподдержанный контракт — UNSUPPORTED;
следующая проверка — PASS. Отчёты: `result/poc-movements` и
`result/poc-movements-negative`.

По последующему уточнению пользователя текущая дата получается runtime внутри
Docker (UTC) и сохраняется перед обработчиком. SBSL подставляет этот независимый
снимок в ожидания; первоначальное требование фиксированной даты заменено.
Генератор также принимает фиксированные входы ДатаВремя и явные варианты
union `{type, value}`; неоднозначные/неправильные варианты отклоняются.
Хранение движений, очистка, повторная запись, активность, остатки и транзакции
не моделируются. Эксперимент №8 реализует
`ПоступлениеТоваров.ПриСозданииНаОсновании` с fake-ссылкой отгрузки и
проектными типами из тела (см. ниже). У этого документа в архиве нет `ПослеЗаписи`;
несуществующий обработчик прихода добавлять не следует.

Проверка этапа №7: `ELEMENT_TEST_DOCKER_TESTS=1 python3 -m unittest discover -s tests -v`
— 43 теста, все прошли; журнал: `result/poc-movements/tests.log`.

Эксперимент №8: `assignments/poc-receipt` — пять сценариев оригинального
обработчика поступления: пустая/одна/несколько строк, дробные значения и
дописывание существующей ТЧ. Проверяются замена склада, порядок и все четыре
поля строки, включая готовую сумму, отличную от количества × цены.
Обнаруживаются типы конструкторов `новый` в достижимых методах модуля,
включая namespace, полный префикс поставщика/проекта и generic-контейнеры.
Строки/комментарии исключаются, интерполяция анализируется; адаптация ограничена
токенами типов конструкторов. Тело исходного обработчика сохранено полностью.
Неизвестные/неоднозначные типы и конфликты кратких имён отклоняются.

Шесть отрицательных ожиданий проверяют склад, товар, количество, цену, сумму
и порядок; неизвестный fake-ID и неподдержанный контракт проверяют ERROR и
UNSUPPORTED. После каждого отрицательного сценария стоит успешная проверка.
Отчёты: `result/poc-receipt` и `result/poc-receipt-negative`.
Анализ остаётся лексическим: локальные объявления/приведения типов,
алиасы импортов и внешние методы/библиотеки не разрешаются.

Следующий этап — выбрать интеграционное окружение для хранения и XBQL:
полноценное приложение Элемента либо PostgreSQL с адаптером объектного API.
Прямой SQL-доступ не заменяет платформенные наборы, фильтры, виртуальные таблицы
и обработчики записи. В рамках этапа №8 хранение и приходные движения не добавлялись.

Проверка этапа №8: полная Docker-регрессия — 48/48, затем дополнительные
проверки типов из тела — 5/5; текущий набор без Docker — 40 PASS и 9 skip
из 49 тестов. Журналы: `result/poc-receipt/tests.log`, `body-types-tests.log`,
`unit-tests.log`. Поступление — 5/5 PASS; отрицательный набор — 6 FAIL,
1 ERROR, 1 UNSUPPORTED, 13 PASS с успешным продолжением после каждого отказа.

выбор backend, opt-in preflight и доверенный smoke реального хранения/запроса.
