# Контракты исходных транзакций и исключений (этап №30)

Контракт дополняет [универсальный runtime](universal-runtime.md). Его выбирают
по разрешённому API, виду метаданных и проверенным диапазонам AST. Имена
учебных объектов, имена методов, namespace и expected не выбирают адаптер.
Бизнес-условия, формулы, порядок вызовов и обработчики исполняет Script executor.
Python не вычисляет результат или откат. Сравнение и баллы вычисляет SBSL.

## Основания и реализация

Официальные страницы Элемента 9.1 прочитаны в авторизованной сессии;
native-пробы отдельно проверены на Script 9.0 (дистрибутив 10.0.2-1).
Это разные источники доказательств, а не утверждение о наличии платформенных
API в standalone executor. Матрица и журналы —
`result/transactions-and-business-exceptions/semantics.md` и `native-probes/`.

[Транзакция](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/Std/Database/Transaction_ru/)
закрывается в конце области видимости: обычный выход фиксирует, исключение
откатывает. Подтверждены конструктор объекта с `Ид: Ууид?`,
[загрузка ссылки](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/DeveloperName/ProjectName/SubsystemName/DocumentName.Reference_ru/)
с блокировкой до завершения активной транзакции и отдельный тип
[ИсключениеВалидации](https://1cmycloud.com/console/help/element/9.1/docs/stdlib/element/xbsl/Std/ValidationException_ru/).
API Транзакции и native ИсключениеВалидации в проверенном Script отсутствуют.
Используются явные общие адаптеры, без заявления полной эмуляции платформы.

## Поддержанная область

Безымянный `исп Транзакции.Начать()` и `Транзакции.ЕстьАктивная()` связываются
с сессией только после разрешения проектных владельцев и локальных имён.
Одноимённый проектный модуль продолжает исполнять свой источник.
Ресурс в IR содержит исходный файл/символ/диапазон, диапазон жизни, контракт,
backend и ограничения. Renderer оборачивает исходный суффикс лексической
ветви в try/catch/finally по проверенным диапазонам, сохраняя тело методов.
Ресурс заканчивается перед следующей ветвью if/catch/when или закрытием блока.

Обычный выход, ранний возврат, break и continue завершают область через native
finally. Исключение, покидающее область, восстанавливает снимок. Исключение,
перехваченное внутри неё исходным catch, не вызывает автоматический откат.
Исходные зависимые методы и оригинальные ПередЗаписью/ПослеЗаписи используют
ту же сессию: объекты, строки и наборы регистров изменяются совместно.
Новые источники с другими именами/схемами не требуют изменения алгоритма.

Доверенная `NonmatchingCatch.sbsl` обнаружила особенность Script 9.0:
неподходящие typed catch во вложенной попытке обходят внешний catch/finally.
`ExplicitRethrow.sbsl` подтверждает исправление явным повторным выбросом.
Для исходных попыток с typed catch и без базового Исключение planner добавляет
последний общий catch/rethrow по диапазону AST. Это сохраняет выбор исходных
обработчиков и обеспечивает откат при выходе неперехваченного исключения;
преобразование одинаково для всех достижимых методов. Finally без catch
проверен отдельно и не требует этой коррекции.

Именованный ресурс, явное Фиксировать/Откатить/Закрыть, ресурсы в лямбдах
и вложенные исходные транзакции пока `UNSUPPORTED`. Вложение проверяется
до исполнения по областям и замыканию зависимостей, включая обработчики;
динамическое достижение непроверенного вложения дополнительно охраняет backend.
Консервативная проверка не использует значения аргументов или expected
для исключения возможной ветви из графа. Недостижимый метод сам по себе
не подключается и не блокирует доступный корень.

## Исключения и идентификатор

Адаптер ИсключениеВалидации — самостоятельный native пользовательский тип
исключения с базой Исключение. Он отличается от ИсключениеНедопустимоеСостояние.
Поддержан конструктор с одним `Описание: Строка`, включая именованный аргумент;
типизированный/общий catch, типовые проверки/приведения и rethrow используют
одну идентичность типа во всех исходных модулях. Строки и комментарии не меняются.
Описание и интерполяция вычисляются исходным кодом. Reflection/Представление
адаптированного исключения и дополнительные перегрузки конструктора отвергаются.

`captureException` сохраняет `{result, exception}` и публичный тип
`ИсключениеВалидации`; техническое имя модуля не становится expected.
В эту оболочку входят только два поддержанных бизнес-типа. SQL/файловые ошибки,
timeout и сбои публикации не превращаются в успешную валидацию. SQL-сбой оставляет
необратимый для текущей тестовой сессии технический маркер отказа; даже исходный
общий catch не позволяет выдать успешный результат после такого сбоя.
Ошибки компиляции классифицируются как `UNSUPPORTED`, ошибки заданий отдельно.

Системный именованный `Ид` конструктора Справочника/Документа связывается с
native UUID и ссылкой именно разрешённого владельца. `Неопределено` создаёт
новый UUID. Требуется `storage.idType: Ууид`; прежний строковый fake-ID сохранён.
Обычный реквизит YAML с именем Ид не переписывается как системный параметр.
Ключ хранения состоит из полного типа/namespace и ID: одинаковые UUID разных
видов и владельцев не объединяются. Дополнительные формы конструктора вне
поддержанной генерации остаются недоступными.

`ЗагрузитьОбъект(Истина)` и именованный Заблокировать создают запись владения
типом/ID в реестре изолированной сессии. Отсутствие активной транзакции вызывает
отдельное ИсключениеНетАктивнойТранзакции, которое исходный typed catch может
перехватить. Существующий объект возвращает свежий снимок, отсутствующий —
Неопределено. Реестр освобождается при завершении/откате удерживающей транзакции.
Memory и PostgreSQL поддерживают эту гарантию изолированной сессии;
FOR UPDATE, конкуренция нескольких сессий и реальные взаимоблокировки не заявляются.

## Driver и PostgreSQL

`storage.transaction: true` остаётся дополнительной атомарной оболочкой
преподавателя. У неё и исходной области разные резервные файлы. Исходное
завершение внутри driver не публикует данные в SQL; публикация откладывается
до успешного завершения driver. Ошибка вызова откатывает его полный снимок.
Это контракт тестовой оболочки, а не реализация платформенных savepoint.

Без внешней оболочки каждая успешная исходная область публикует свой снимок
в отдельном настоящем SQL BEGIN/COMMIT; ранний возврат также публикует его.
Следующая отменённая область не удаляет уже завершённые операции.
Начальное состояние публикуется до вызова исходника. При отказе после INSERT
выполняется SQL ROLLBACK, а доверенная инфраструктура независимо читает БД.
Повторная публикация неизменённого снимка пропускается: driver, финальный аудит
и исходный commit не дают случайных повторных SQL-фиксаций.
Наборы регистров универсального staging-контракта хранятся как снимки в
smoke.objects; старый shipment-профиль сохраняет smoke.records и прежний аудит.

`storageTrace` и `storageDiagnostics` в runtime-evidence содержат границы
транзакций, получение блокировок и проверенные `active: false, locks: 0`
после успешного выполнения. Эти данные не добавляют оценочных требований
к expected. Public actual сохраняет `{result: прежнийActual, storage: [...]}`.
Исходная ссылка сама по себе не доказывает корректную запись.

## Воспроизведение

```bash
bin/element-test test --project Prakticheskie-primery-2026-09-30-15-20.xdump \
  --assignment assignments/transactions-real --output result/transactions-real
bin/element-test test --project tests/corpus/transactions/accounts \
  --assignment assignments/transactions-accounts --output result/transactions-accounts
ELEMENT_TEST_DOCKER_TESTS=1 ELEMENT_TEST_INTEGRATION_TESTS=1 \
  python3 -m unittest discover -s tests -p 'test_transactions.py' -v
```

Для SQL нужен случайный ELEMENT_TEST_INTEGRATION_PASSWORD в окружении;
пароль не записывается в исходники и публичный пакет. Переносимые задания
намеренно содержат PASS, FAIL и UNSUPPORTED; их общий exit code 1 ожидаем.
`transactions-accounts-sql` и `transactions-renamed-sql` требуют `--integration`.

Старые fixtures записи покупателя в трёх практических заданиях заменены
действительно недоступным общим XBQL поиска. В универсальных CRUD заданиях
граница блокировки заменена именованным исходным ресурсом. Прежние успешные
проверки/баллы сохранены; новая проверка записи явно сравнивает поля и строки.
