# Перечисления — полное соответствие

Эталон: `05. Перечисления/dump_practice.xdump`, проект и поставщик `Движок`,
версия проекта 1.0, режим совместимости 9.0.
Требования зафиксированы в `assignment.yaml` и `reference.json`.
При проверке студенческой работы эталон из неё не строится.

## Охват

220 структурных критериев на 220 баллов охватывают шесть перечислений
с 21 значением, семь документов, шесть справочников, все 60 явно объявленных
реквизитов и семь реально присутствующих модулей.
У каждого критерия есть пояснение при ошибке.

| Перечисление | Значения | Явное значение по умолчанию |
|---|---|---|
| `CRM::СтатусСделки` | Новая, ВРаботе, Выиграна, Проиграна, Заморожена | Новая |
| `CRM::ТипКонтрагента` | ФизЛицо, ЮрЛицо, ИП, Самозанятый | ФизЛицо |
| `Продажи::СтатусЗаказа` | Новый, ВРаботе, Закрыт | не задано |
| `Товары::ЕдиницаИзмеренияТип` | Штуки, Вес, Объем, Длина | не задано |
| `Финансы::СтатусОплаты` | НеОплачено, ЧастичноОплачено, Оплачено | не задано |
| `Финансы::ТипОплаты` | Наличные, Безналичные | не задано |

Проверяются вид `Перечисление`, подсистема, область видимости `ВПодсистеме`,
все значения и все восемь явно заданных представлений:

- `СтатусСделки.ВРаботе` и `СтатусЗаказа.ВРаботе` — «В работе».
- `ТипКонтрагента`: «Физическое лицо», «Юридическое лицо»,
  «Индивидуальный предприниматель», «Самозанятый».
- `СтатусОплаты.НеОплачено` — «Не оплачено»;
  `СтатусОплаты.ЧастичноОплачено` — «Частично оплачено».

У двух значений проверяется явное `ПоУмолчанию: Истина`.
Строгая проверка также обнаруживает лишние значения, дополнительные флаги
по умолчанию и любые другие настройки, отсутствующие в эталоне.

## Типы реквизитов

| Объект и реквизит | Ожидаемый тип |
|---|---|
| `CRM::Контрагенты.ТипКонтрагента` | `ТипКонтрагента` |
| `CRM::Сделка.СтатусСделки` | `СтатусСделки` |
| `Продажи::Заказ.СтатусЗаказа` | `СтатусЗаказа?` |
| `Товары::ЕдиницыИзмерения.ТипЕдиницыИзмерения` | `ЕдиницаИзмеренияТип?` |
| `Финансы::ПоступлениеДенежныхСредств.ТипОплаты` | `ТипОплаты?` |
| `Финансы::РасходДенежныхСредств.ТипОплаты` | `ТипОплаты?` |
| `Финансы::СчетНаОплату.СтатусОплаты` | `СтатусОплаты?` |

Проверяется точный тип, включая `?`. Обязательность заполнения остаётся
отдельным свойством: у статуса заказа, типов оплаты и статуса оплаты
проверяется `НезаполненноеЗначение: ЗапретитьВсегда`.

У `Сделка.СтатусСделки` больше нет строкового
`ЗначениеПоУмолчанию: Новая`, которое было в разделе 04.
Строгая проверка отклоняет сохранение этой старой настройки.
Значение по умолчанию теперь объявлено у элемента перечисления.

Включены проверки всей конфигурации этого дампа: реквизитов справочников
и документов, ссылок, ограничений чисел, обязательности заполнения,
значений по умолчанию, областей видимости, импортов, интерфейсных флагов

`СерииНумерации: [Префикс, Постфикс]`.

## Строгое соответствие

Шесть дополнительных проверок сравнивают все метаданные проекта,
состав и свойства подсистем, объектов, реквизитов и значений перечислений,
состав модулей, служебные YAML метаданные и отсутствие диагностик модели.

Лишние объекты, значения, реквизиты, табличные части, модули и настройки
дают `FAIL`. UUID (`Ид`), порядок ключей и именованных деклараций
(включая реквизиты и значения перечислений), отступы и комментарии
в модулях не учитываются. Отсутствующая настройка отличается от явно заданной.
Обычные списки настроек, включая `Импорт`, `Использование` и
`СерииНумерации`, сравниваются с учётом порядка и повторов эталона.

Все семь XBSL-модулей эталона пустые или содержат только комментарии.
Отдельных модулей перечислений и документов здесь нет — структурные
критерии не требуют их создавать.

Проверяется конфигурация из дампа. Запуск приложения, пользовательские
данные, отображение списков в браузере и поведение платформы не проверяются.

## Полная проверка

Из корня репозитория:

```bash
.venv/bin/python assignments/enums-full/check_full.py \
  --project '/path/to/dump_practice.xdump' \
  --output result/enums-full
```

Для другой работы замените путь `--project`. При необходимости можно
добавить `--project-name Поставщик::Имя`.

- `result/enums-full/report.html` — общий отчёт.
- `result/enums-full/full-result.json` — общий результат и строгие расхождения.
- `result/enums-full/structural/` — стандартные отчёты и пакет оценки движка.

Полное соответствие подтверждается только `status: passed` в
`full-result.json`. Структурные критерии выставляют баллы;
шесть строгих проверок баллов не добавляют. Например, лишнее значение
перечисления может оставить 220/220, но общий результат будет `failed`.

Код завершения: 0 — полное соответствие, 1 — расхождения,
2 — ошибка входа или недоступное исполнение. Исходный дамп не изменяется.
Общий механизм проверки находится в
`assignments/catalogs-full/check_full.py`; сохраните обе папки заданий.

## Только стандартные критерии движка

```bash
ELEMENT_TEST_PYTHON=.venv/bin/python bin/element-test test \
  --project '/путь/к/работе.xdump' \
  --assignment assignments/enums-full \
  --output result/enums-structural
```

Этот вариант выполняет 220 критериев. Обычный движок и его сервис
не сравнивают работу с `reference.json` автоматически:
для полного соответствия используйте `check_full.py`.

## Проверка самих тестов

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_*_full.py' -v
```

Проверены 220 отдельных ошибок по числу критериев и 83 изменения вложенных
настроек: 303 основные мутации с ожидаемым `FAIL`. Ещё 14 мутаций проверяют
изменение nullable-типа и подмену перечисления в каждом из семи реквизитов.

Дополнительно проверяются все значения строгого эталона, пропущенные,
лишние и повторяющиеся значения перечислений, дополнительные значения
по умолчанию, возврат старой строковой настройки, допустимые изменения UUID
и порядка деклараций, сохранность входных файлов и формирование отчётов.
Та же команда запускает регрессию разделов 03 и 04: всего 23 теста.
