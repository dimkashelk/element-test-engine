# Формы объектов — структура без браузера

Эталон: переданный `dump_practice.xdump`, проект `Движок::Движок`, версия 1.0,
режим совместимости **9.0**. SHA-256:
`3945476c3967316fb1968556a0b332c6bd2eff2985d1e17887e8dedeac102e30`.

Проверяется соответствие конфигурации дампу, включая объявления форм.
Ожидания зафиксированы в `assignment.yaml` и `reference.json`, при проверке
другой работы они не создаются из её исходников. Отдельного ТЗ на поведение
приложения не предоставлено. Браузерные проверки исключены, как согласовано
ранее; структура форм включена по запросу по теме «Формы объектов».

## Формы в эталоне

| Подсистема | Формы |
|---|---|
| `CRM` | `КонтрагентыФормаОбъекта`, `СделкаФормаОбъекта`, `ФизическиеЛицаФормаОбъекта` |
| `Продажи` | `ЗаказФормаОбъекта` |
| `Товары` | `ЕдиницыИзмеренияФормаОбъекта`, `НоменклатураФормаОбъекта`, `ОтгрузкаФормаОбъекта`, `СкладыФормаОбъекта` |
| `Финансы` | `ПоступлениеДенежныхСредствФормаОбъекта`, `РасходДенежныхСредствФормаОбъекта` |
| `Администрирование` | `ДанныеКомпанииФормаЗаписи`, `НастройкиФормаЗаписи`, `РабочиеДниФормаЗаписи`, `ФормаПриветствие` |

Для форм объектов проверяется точный `ФормаОбъекта<...Объект>`, для наборов
констант — `ФормаЗаписиНабораКонстант<...Запись>`. Также проверяются область
видимости, импорты, заголовки, способ открытия, шаблоны, группы, типы
полей/колонок, привязки к объекту, строке таблицы и записи констант,
источники таблиц, команды сохранения/копирования/удаления и команды строк.

Учитываются свойства доступности и состояния, например
`РедактированиеДанных`, `ТелефонАктивен`, `ПочтаАктивна`, свойство
`Приветствие` со значением «Здравствуйте», вложенные формы только для чтения.
У формы приветствия сравнивается вся заготовка, включая надписи, даты,
кнопку `КнопкаРасчитать` и сворачиваемые блоки. Названия сохраняются как
в исходнике; отсутствующие обработчики и вычисления не придумываются.

Формы для остальных объектов в этом дампе не созданы. Тесты не требуют
добавлять отсутствующие в эталоне формы банковского счёта, поступления
товаров или счёта на оплату.

## Строгое сравнение и ограничения

Шесть строгих разделов охватывают проект, подсистемы, объекты, модули,
служебные YAML и диагностику. Лишние/пропущенные формы, компоненты,
свойства, поля, команды и изменённые привязки дают `FAIL` с точным путём.

**В объявлениях форм порядок списков сохраняется**, включая поля,
колонки, группы и команды. Перестановка компонентов не скрывается
сортировкой именованных элементов. Для остальных метаданных прежнее
правило сохраняется: порядок именованных деклараций не учитывается;
обычные списки импортов и настроек сравниваются с порядком и повторами.

UUID `Ид` и комментарии не учитываются. В полном запуске UUID убираются
из модели форм в памяти перед структурной проверкой; исходники остаются
неизменными. Верхнеуровневые настройки `Интерфейс` объектов по-прежнему
исключены. Все декларации самих форм, включая вложенные настройки,
проверяются.

В исходнике нет исполняемых методов и обработчиков. Проверяется текст
формул и команд, их типы и расположение в объявлении. Это не исполнение
формул и не подтверждение работы встроенных платформенных команд,
открытия/сохранения формы, отображения в браузере или пользовательских
данных. Ветвевое runtime-покрытие неприменимо.

## Запуск

Из корня репозитория:

```bash
.venv/bin/python assignments/object-forms-full/check_full.py \
  --project '/path/to/dump_practice.xdump' \
  --output result/object-forms-full
```

Для другой работы замените `--project`; при необходимости добавьте
`--project-name Движок::Движок`. Поддерживаются XDUMP, архив и каталог.

- `result/object-forms-full/report.html` — общий отчёт;
- `result/object-forms-full/full-result.json` — итог и строгие расхождения;
- `result/object-forms-full/structural/` — стандартные отчёты и баллы.

Полный успех — только `status: passed` в `full-result.json`. Обычный
`bin/element-test test --assignment assignments/object-forms-full` выполняет
326 критериев, но не запускает строгое сравнение и нормализацию UUID форм.
Для полного соответствия используйте `check_full.py`.

Коды завершения: 0 — успех; 1 — расхождения; 2 — ошибка входа или недоступное
исполнение. Нужны зависимости репозитория, Java 17, локальный Script executor
и `assignments/catalogs-full/check_full.py`. Docker не нужен. Дамп не меняется,
приложение не разворачивается.

## Проверка тестов

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_object_forms_full.py' -v
PYTHONPATH=tests .venv/bin/python -m unittest \
  test_object_forms_full test_constants_full test_table_sections_full -v
```

Новый набор использует общие проверки из двух предыдущих тестовых модулей.
Проверяются все 1144 скалярных ожидания, пропуски и лишние элементы,
дубликаты, неверные типы и значения, все привязки и перестановки списков
форм, сохранность исходников, отчёты и коды завершения.

В реальном SBSL-движке проверяются **1049 изолированных мутаций**:
по одной ошибке на каждый из 326 критериев и 723 изменения вложенных
настроек, в том числе форм. Каждый вариант обязан получить `FAIL` и ноль
баллов. Сквозные проверки дополнительно меняют компоновку, удаляют форму,
добавляют вложенные UUID и проверяют константы.

Результат предоставленного дампа: **326/326**, все шесть строгих разделов
`PASS`, недоступных критериев нет. Самопроверка нового набора: **19/19**;
все 1049 мутаций обнаружены. Совместный прогон с двумя предыдущими
наборами: **44/44**, без пропусков и ошибок. SHA-256 исходного дампа после
проверок совпадает с исходным.
