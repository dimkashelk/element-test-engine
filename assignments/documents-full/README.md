# Документы — полное соответствие

Эталон: `04. Документы/dump_practice.xdump`, проект и поставщик `Движок`,
версия проекта 1.0, режим совместимости 9.0.
Ожидания зафиксированы в `assignment.yaml` и `reference.json`;
при проверке работы студента они не строятся заново из его дампа.

## Охват

176 структурных критериев на 176 баллов проверяют семь документов,
шесть справочников, все 60 явно объявленных реквизитов и их настройки.
Для каждого критерия задано пояснение при ошибке.

| Документ | Реквизиты |
|---|---|
| `CRM::Сделка` | Дата, Номер, Клиент, СтатусСделки, Сумма, ДатаЗакрытия, Архивный |
| `Продажи::Заказ` | Дата, Номер, Клиент, СтатусЗаказа, ДатаДоставки, АдресДоставки, Сделка, Архивный |
| `Товары::Отгрузка` | Дата, Номер, Склад, Номенклатура, Количество |
| `Товары::ПоступлениеТоваров` | Дата, Номер, Склад, Номенклатура, Количество |
| `Финансы::ПоступлениеДенежныхСредств` | Дата, Номер, Основание, Клиент, Сумма, ТипОплаты |
| `Финансы::РасходДенежныхСредств` | Дата, Номер, Клиент, Сумма, ТипОплаты |
| `Финансы::СчетНаОплату` | Дата, Номер, Основание, Контрагент, Сумма, СтатусОплаты |

Проверяются точные типы, включая nullable-ссылки и составной тип
`Заказ.Ссылка|СчетНаОплату.Ссылка|?` у основания поступления денег.
Обязательность заполнения проверяется отдельно от nullable-типа ссылки.

Проверяются все явно заданные значения по умолчанию и ограничения:
`СтатусСделки = Новая`, `Архивный = Ложь`, обязательные статусы,
контрагенты, склад и номенклатура; два дробных разряда и минимум 0
для сумм; минимум 0 и обязательность количества.
Нулевое количество допускается настройкой эталона — тест не требует
строго положительного числа.

## Нумерация

У всех документов номер строковый, уникальный, с периодичностью `Год`
и включённой автонумерацией. Проверяются длина номера, префикс,
постфикс, длины частей формата и разделители `-` и `/`.

| Документ | Длина номера | Префикс | Постфикс | Явная ДлинаНумерации |
|---|---:|---|---|---:|
| Сделка | 12 | СК | CRM | 5 |
| Заказ | 13 | ЗК | ПР | 7 |
| Отгрузка | 13 | ОТГ | ТВ | не задана |
| ПоступлениеТоваров | 12 | ПТ | ТВ | не задана |
| ПоступлениеДенежныхСредств | 13 | ПДС | ФН | не задана |
| РасходДенежныхСредств | 13 | РДС | ФН | не задана |
| СчетНаОплату | 13 | СНО | ФН | 6 |

Для пяти документов, у которых заданы серии нумерации, проверяется
`СерииНумерации: [Префикс, Постфикс]`.
Вложенные словари `Автонумерация` сравниваются целиком.
Это проверка деклараций; фактическое присвоение номера платформой
при записи документа не выполняется.

## Остальные настройки

Проверяются справочники `Контрагенты`, `ФизическиеЛица`, `ЕдиницыИзмерения`,
`Номенклатура`, `Склады`, `БанковскийСчет` со всеми настройками этого дампа.
В отличие от раздела 03 у `Контрагенты` теперь область видимости `ВПроекте`.
У `Сделка` и `Заказ` также задана `ВПроекте`, у остальных объектов —
`ВПодсистеме`.

Проверяются импорты объектов и два интерфейсных флага у `Отгрузка`,
`ПоступлениеТоваров`, `РасходДенежныхСредств`:
`ВключатьВАвтоИнтерфейс` и `ИспользоватьСозданиеПриВводе` равны `Истина`.

В дампе семь XBSL-модулей: корневой и модули шести справочников.
Они не содержат исполняемого кода. Модулей документов, форм,
табличных частей и движений по регистрам в эталоне нет.
Структурные критерии требуют только реально присутствующие модули.

## Строгое соответствие

Шесть дополнительных проверок сравнивают:

1. Все метаданные проекта, включая имя, поставщика, версию и языки.
2. Подсистемы `CRM`, `Продажи`, `Товары`, `Финансы` и их настройки `Использование`.
3. Точный состав и свойства всех объектов и реквизитов.
4. Точный состав модулей и отсутствие исполняемого кода.
5. Состав служебных YAML метаданных.
6. Отсутствие диагностик модели.

Лишние объекты, реквизиты, табличные части, модули и настройки дают `FAIL`.
UUID (`Ид`), порядок ключей и именованных деклараций, отступы и комментарии
в модулях не учитываются. Отсутствующая настройка отличается от явно заданной.
Обычные списки настроек, в том числе `Импорт`, `Использование` и
`СерииНумерации`, сравниваются точно, с учётом порядка и повторов эталона.
Пустой `CRM/Подсистема.yaml` принимается загрузчиком.

Проверяется конфигурация из выгрузки. Данные приложения, поведение браузера,
проведение и запись документов в работающем приложении не проверяются.

## Запуск полной проверки

Из корня репозитория:

```bash
.venv/bin/python assignments/documents-full/check_full.py \
  --project '/path/to/dump_practice.xdump' \
  --output result/documents-full
```

Для другой работы замените `--project`. При необходимости выберите
приложение через `--project-name Поставщик::Имя`.

- `result/documents-full/report.html` — общий отчёт.
- `result/documents-full/full-result.json` — общий результат и строгие расхождения.
- `result/documents-full/structural/` — обычные отчёты и пакет оценки движка.

Полное соответствие подтверждается только `status: passed` в
`full-result.json`. Баллы выставляются структурными критериями;
шесть строгих проверок баллов не добавляют. Лишний реквизит может оставить
176/176 баллов, но общий итог будет `failed`.

Код завершения: 0 — полное соответствие, 1 — расхождения,
2 — ошибка входа или недоступное исполнение. Исходный дамп не изменяется.

Общий механизм строгого сравнения используется из
`assignments/catalogs-full/check_full.py`; для полной проверки необходимо
сохранить обе папки заданий в репозитории.

## Только стандартные критерии движка

```bash
ELEMENT_TEST_PYTHON=.venv/bin/python bin/element-test test \
  --project '/путь/к/работе.xdump' \
  --assignment assignments/documents-full \
  --output result/documents-structural
```

Этот вариант проверяет 176 критериев. Обычный движок и его сервис
не запускают сравнение с `reference.json` автоматически:
для полного соответствия используйте `check_full.py`.

## Проверка самих тестов

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_*_full.py' -v
```

Проверены все 176 критериев на отдельных ошибках и ещё 79 изменений
вложенных настроек: всего 255 изолированных мутаций с ожидаемым `FAIL`.
Дополнительно проверяются все значения строгого эталона, лишние и
пропущенные сущности, допустимые отличия UUID и порядка реквизитов,
сохранность входных файлов, коды завершения и формирование отчётов.
Предыдущий набор для справочников проверяется той же командой.
